# Beacon: guidance for agents

Beacon is a "What's that?" button for San Francisco, built for the Meta Muse Ember Hackathon. Read [HACKATHON.md](HACKATHON.md) first: the rules, the $10 budget, and the banned project types constrain every change. [README.md](README.md) says what exists today and how to run it.

## Layout

- `web/`: React + Vite + TypeScript PWA. Package manager is pnpm. Tests are Vitest with Testing Library, lint is oxlint, format is Prettier. See [Working on the app](#working-on-the-app).
- `server/`: Python 3.12 + FastAPI, managed with uv. Tests are pytest, lint and format are ruff (config in the root `ruff.toml`). The package is `beacon`; every route is under `/api`.
- `scripts/`: repository scripts. Python scripts import `beacon` and run with `uv run --project server python scripts/<name>.py`. Keep their logic in `server/beacon/` so it is tested; the script is a thin entry point.
- `data/`: local runtime data (SQLite files, recordings, downloads), ignored by Git. The Ember client writes under `data/ember/`. `BEACON_DATA_DIR` moves it and must be an absolute path (`beacon.ember.client.default_data_dir`); code that stores data must honor it.

Each `server/beacon/` package has one concern, so parallel pull requests stay apart. When you add a package, add it to this list and to the README's layout table.

- `api/`: HTTP routes, one module per resource, each exposing a `router` that `beacon.main` mounts under `/api`.
- `ember/`: the Meta Model API client, its ledger, replay cache, and trace.
- `evidence/`: the evidence store. Every poller writes to it and every reader of what a source said reads from it. See [Using the evidence store](#using-the-evidence-store).
- `incident/`: the incident engine, which reads evidence rows as incidents and stores nothing. `calls` decides which radio calls are one incident, `build` attaches what else was said about the place and words every line, `inforce` says what is in force, `aircraft` makes tracks and says what circles, `places` is the list of blocks that gives a radio call's place a point, and `engine` is the reader (`open_engine`). See [Using the incident engine](#using-the-incident-engine).
- `ingest/`: one module per source (`nws`, `adsblol`, `traffic511`, `recordings`, `notices`), the `Runner` that polls them, `paid` (what a poller that pays Ember for each item keeps to), and `setup`, which reads `BEACON_LIVE_SOURCES` once to open the right store (`open_store`) and make the pollers (`build`).
- `investigate/`: the investigator, which answers a tap. `tools` is what Ember may look at and what it is told, `loop` is `investigate_tap` and the check of its answer, `card` the words a person is shown, `store` the file runs and crisis decisions are kept in (`Runs`), `desk` when a tap is paid for (`InvestigationDesk`), `stand_in` the stand-in that investigates with no key, and `setup` opens the desk (`open_investigations`). See [Using the investigator](#using-the-investigator).
- `mapping/`: the map of one incident. `features.drawn(incident, store.get)` is what is drawn: the incident's place, the version in force of each 511 event, the aircraft of its timeline, and the area of each alert in force, each a `Feature` with the sentence, confidence, and sources of the timeline line it is (an aircraft also names the row of every position that is drawn). It asks no model and stores nothing.
- `notice/`: what is kept of an official notice (`Notice`), and the Ember call that reads one from its PDF (`read_notice` in `read`).
- `places/`: saved places. `read` reads the places a request holds, each rounded to about a block, and `check` says which open incidents are within a kilometre of one and words the distance (`near`, `NOTHING_NEAR`, `NOT_AN_AREA`). It keeps nothing: a saved place lives on the person's device.
- `push/`: web push, the one thing Beacon keeps that is tied to a device. `store` is the file of subscriptions (`Subscriptions`: an address, up to five rounded places with when the server was first told of each, what was sent, and the single-use permits an address is given with), `endpoint` the check that an address is a browser maker's push service's (`checked`), `vapid` the key a push is signed with, one for each mode, `desk` the pass that sends (`Notifier.notify`), `notice` the words (`notice_of`, `ABOUT`), and `setup` opens it (`open_push`, and `Push.work`, the pass that deletes what ran out whether or not anything is sent). See [Working on notifications](#working-on-notifications).
- `radio/`: the closed vocabulary a radio call is kept in and the lists a unit or a street has to be on (`vocabulary`), the Ember call that hears one (`extract_transmission` in `extract`), and the in-memory, confined decoding of its audio (`audio`), whose `Ffmpeg` also draws a tap's photo again.
- `redact/`: the redaction pass. `screen` lets Ember's reading of a notice through only when every word of it is an ordinary word or a listed name (`reading`), and an issuer only when it is a listed public body (`Names.public_body`); `vocabulary` is the words. It passes nothing a model wrote in Beacon's own voice: there is no such text.
- `scale/`: the scale run, a command (`scripts/scale_run.py`) and no part of the server. `datasf` is DataSF's record of a day's dispatched calls (`Record`), `lists` the streets, blocks, and units made from DataSF, `generate` the calls generated from the records (`BEACON-GENERATED`), `run` one run in a directory of its own (`Layout`, `Settings`, `hear`), `score` which of DataSF's calls Beacon has an incident for (`fits`, `match`), `taps` the replayed taps, `results` the numbers, each with its sentence (`Number`, `basis`), and `cli` the command. See [Working on the scale run](#working-on-the-scale-run).
- `scenario/`: the mock scenario, an invented San Francisco fire served to the pollers in each source's own format, with its radio calls and the stand-in for Ember that "hears" them (`radio`), and its notices, written as PDFs (`pdf`), with the stand-in that "reads" them (`notices`).
- `story/`: the points Ember picks to tell an incident by. `merge` is the Ember call (`merge_incident`), the check of each point against its rows, and the sentences code writes for them; `store` is the file stories are kept in (`Stories`), `desk` when one is paid for (`StoryDesk`), `stand_in` the stand-in that chooses with no key, and `setup` opens the desk (`open_stories`).
- `taps/`: taking a tap. `desk` checks one, rounds its place, and stores its row (`Taps.take`); `media` has a photo drawn again as a new JPEG and a clip written out again as its samples, and keeps them for an hour (`Taps.media` reads them back).

`beacon/errors.py` is a module beside them, with `raise_bare`: how an error about something private is raised with nothing chained under it. `beacon/api/body.py` has `read_body`, which a route that takes something private reads its body with. So is `beacon/files.py`, with `begin_file`: how a SQLite file that is the mock store's or the live store's, in one shape, is opened or refused.

## Commands

```sh
scripts/check            # everything CI runs; run it before pushing
scripts/check server     # ruff format --check, ruff check, pytest
scripts/check web        # prettier, oxlint, vitest, tsc + vite build
amp orb services ensure  # in an Amp orb: start the API and the web dev server, print the portal URL
```

Run one server test with `cd server && uv run pytest tests/test_health.py -k name`, and one web test with `cd web && pnpm test src/App.test.tsx`. Server pytest sets `REPLAY=1` and removes `MODEL_API_KEY` itself; `pnpm test` run directly does not change the environment, and `scripts/check web` does. After changing dependencies, commit the lockfile (`server/uv.lock`, `web/pnpm-lock.yaml`): CI installs with the lockfiles frozen.

## Rules

- **Only `server/beacon/ember/` may call the Meta Model API.** Every model call goes through `EmberClient.respond`, which records tokens and cost for each call, replays recorded responses when `REPLAY=1`, and refuses a call past the spending stop. No other module imports `openai` or another model SDK, or sends a request to `api.meta.ai`. Do not raise the stop's default or the ceiling in `beacon/ember/pricing.py`, do not give `EMBER_SPENT_BEFORE_USD` a default, and do not delete `data/ember/ledger.sqlite3` or point two processes at different ledgers: going over $10 disqualifies the entry. See [Using the Ember client](#using-the-ember-client).
- **Tests and CI never call the Meta Model API or a live data source.** Tests replay recorded or hand-written responses. `server/tests/conftest.py` removes `MODEL_API_KEY`, sets `REPLAY=1`, and patches Python's `socket.connect` and `socket.connect_ex` to raise `NetworkBlockedError` for an address that is not this machine. The patch is a backstop: a test that catches the error still passes, and native code that opens its own sockets is not covered, so the rule is yours to keep. Do not weaken the guard; give the code under test a fake transport instead.
- **Never commit secrets, raw radio audio, or downloaded source data.** The repository is public. Keys come from the environment (`MODEL_API_KEY`). Runtime data stays under the Git-ignored `data/`. Beacon publishes summaries, never raw radio audio.
- **Say what is mocked.** Until real keys and permissions exist, features run on mock data. Anything a stand-in produced is labeled as such in the API reply and in the app, and the README's status says so. Never present a stand-in's output as Ember's. An evidence row says it itself: `row.stand_in` is true when it came from the mock scenario (`origin == "mock"`) or a fake Ember wrote it (`model == "fake"`), and whatever is built from such a row is a stand-in's too. The live evidence store refuses those rows; do not add a way around that.
- **Mock data is invented, never copied.** The repository is public and holds no real radio traffic, transcript, recording, or notice. What the mock scenario says is made up and says so in its text (`beacon.scenario.INVENTED`).
- **Nothing a radio call said is stored as text, and its audio is never written to disk.** This is what ingest guarantees, and later code builds on it and must not undo it. A call reaches the evidence store only as a `beacon.radio.Transmission`: tags from fixed lists, a hundred block, and unit ids and street names that are on the lists the caller gives (`beacon.radio.Known`; a shape alone is not enough, and with no list none is kept). Do not add a transcript, a summary, a note, or any other free-text field to it, to its form (`beacon.radio.extract.SCHEMA`), or to a radio row's `data`; a new thing worth keeping is a new tag in `beacon/radio/vocabulary.py`. A medical call is kept as `"medical response"` with its units and block, and no status, details, or alarm; so is every call on an EMS-only talkgroup. A recording Beacon is given is the operator's file in the operator's directory (`beacon.ingest.recordings.Directory`): Beacon reads it into memory, through no symbolic link and up to a call's size, and never copies, changes, or deletes it, and keeps nothing of its JSON but the talkgroup, the start, the length, and the two flags (never `srcList`, the radios that transmitted). Do not write radio audio to a file, a temporary one included, or put it in a log or an error, and do not run a decoder on it outside the confinement in `beacon/radio/audio.py`, or widen what that confinement shows (`_SYSTEM_DIRS`). `extract_transmission` is always a `sensitive=True` call. Two limits are known and stated in `vocabulary.py`: a listed name is kept whatever Ember meant by it, and nothing checks that Ember heard the call right.
- **A notice's words are kept only when it is a notice to the public, and its document is never stored.** A notice reaches the evidence store only as a `beacon.notice.Notice`. Everything a model could write freely (`issuer`, `title`, `areas`, `streets`, `instruction`, `summary`) is kept for the types in `beacon.notice.TEXT_TYPES` and left empty for a press release and for anything Ember does not take for a notice, which is where a victim is named and a home described. A text is kept whole or left out and named in `incomplete`, never cut: a cut instruction can say the opposite. A notice row is a model's reading, so its confidence is `high` and never `official`. Do not widen `TEXT_TYPES` to those types, do not add a field that holds the document's text for them, do not cut a text to make it fit, and do not store, cache, or log a PDF or parse one in Beacon's process: Ember reads it, from bytes Beacon fetched from a host the operator named, in a `sensitive=True` call.
- **Work that is paid for per item claims the item first.** `EvidenceStore.claim(source, ref)` is True for one caller only, for good. Claim before the paid request, never ask about an item whose claim is not yours, and give a claim up (`release`) only when the paid request is known not to have been sent (`EmberClosedError`, `ReplayMissError`, or a `BudgetExceededError` that is not a `LedgerReplacedError`). The rules that follow once Ember has been asked (when a claim may be given up, the hold after a failure, the stop after a replaced ledger, `close` and `drain`) are written once, in `beacon/ingest/paid.py` (`PaidDesk`): a new paying poller uses it and does not write them again. `beacon/ingest/recordings.py` and `notices.py` are the examples; their clients have no pacer, because each retry is a paid request and a claim covers one. Each names the label of its own `SpendScope` (`SCOPE` in its module, `ingest:<source>`), and `PaidDesk` refuses a live client that pays under none or under another poller's. A poller that pays also offers `close` and `drain` (`beacon.ingest.runner.PaidWork`), which `Ingest.stop` uses so that shutting down admits no new paid work and stores the answer to work that is out. Only `stop` answering True is a complete stop.
- **A poller's request goes through `beacon.ingest.http.fetch`,** which caps what is read, follows no redirect, and fails with a `SourceError` whose text is fixed. Never log or raise a request's address (511's holds the token), a reply's body, or an exception from the HTTP library, and never leave one chained under your own error: `raise ... from None` only hides it from a printed traceback and keeps it in `__context__`. Raise outside the `except` block, with `beacon.errors.raise_bare`, which also drops an error your *caller* is handling. The same goes for any error about what a source or a person sent: the parsers and the evidence store raise that way.
- **A source is polled for real only with the right to.** Read a source's terms before you write its poller, and say in the poller's module what they ask and what Beacon does about each, as `beacon/ingest/adsblol.py` does. When the terms ask for permission, or the right to the data is the operator's to have, `setup.source_pollers` refuses the source until a setting says so, as it does for recorded radio (`BEACON_RECORDINGS_PERMITTED=1`): do not remove such a check, and give a new source one like it. A key is not permission, and neither is having the file. **Beacon asks nobody for radio audio.** OpenMHz was asked whether Beacon may use its API and said not to: there is no client for it, `live_sources` refuses its name with that sentence, and no setting, script, or test requests anything from it, its recordings included. Do not write one, and do not write a client for Broadcastify, from which Beacon has no license. `beacon.ingest.http.fetch` refuses an address of either (`never_asked`, `NEVER_ASKED_DOMAINS`), and one whose host the client cannot read, before anything is sent, whoever names it, and a notices feed that names one is refused at startup before any paying client is made (`_refuse_never_asked`); the host is compared as `httpx2` reads it, never as another parser does: do not take a domain off that list, and send a poller's request no other way. Radio is recorded calls on the machine Beacon runs on (`beacon/ingest/recordings.py`); Beacon does not use a recording downloaded from either service, and does not request LiveATC's audio. Say of these services only what Beacon does, not what their terms allow. **OpenSky is not polled and has no poller**: its terms require a written license for calling its REST API from a running service, which nobody has. Do not add one back; aircraft come from adsb.lol, whose API is open to everyone under the Open Database License.
- **What is shown from a position adsb.lol answered with carries the notice its license asks for, and nothing else does** (`CREDIT_ADSBLOL` and `credit_of` in `beacon/incident/build.py`, the words in `beacon/ingest/adsblol.py`). The notice says the thing shown contains information from adsb.lol, which is true only of a row adsb.lol answered (`source == "adsblol"` and `origin == "live"`): a position of the invented scenario has no notice and is labeled "Aircraft positions" (`label_of(..., invented=True)`), and a row an earlier feed left in a store keeps that feed's name. **Never work a credit out from the kind of a signal, a ground, or a tool**: read it from the rows. `source_of` puts it on a row's source, so a line, a signal, a story's sentence, and a map feature carry it through their sources. Where something rests on aircraft rows without listing them, what is kept names the feed (`credited` in `build.py`): `nearby_incidents` keeps `aircraft_credits` and `rotorcraft_credits` for each incident, `get_aircraft` and `get_official` keep `credits`, and the routes turn those names into credits (`card.ground_feeds`, `_ground_credits` and `_credits` in `api/taps.py`); `nearby_incidents`' own call in the trace carries the credit of every feed those two name, whether or not a ground came of it; and a decision keeps the feeds of each signal it cited (`Cited.credits`, filled in `_crisis` from the signal's sources), which `cited_credit` in `api/incidents.py` turns into a credit without reading a row. A new thing shown from an aircraft's position does one or the other. A credit whose terms ask for several links has them in `Credit.parts`, and `CreditLine` gives each its own link. **Beacon's live aircraft rows are licensed under the ODbL, and [`docs/aircraft-data.md`](docs/aircraft-data.md) is where that is said and where the method is offered** (ODbL 4.4 and 4.6): what is asked and how often, what is kept, each conversion, how a row is stored. The notice links it. Change it in the same commit as `parse_aircraft` or the poller's interval. **The live aircraft poller keeps to adsb.lol's allowance across restarts, and across the processes on one data directory**: before it asks, it promises in the evidence store not to ask again for one interval (`EvidenceStore.reserve`, kept as `not_before`), counted from the real time and not from the moment the runner's step began. The store reads the clock it is handed inside the write transaction, after any wait for the file, and the look and the write are that one transaction: do not read the clock before the call, and do not read the state and write it in two. A promise further off than the cap is written down as the cap once, so the cap does not begin again at every look. A wait adsb.lol asks for (`Retry-After` on an answer that is no success) moves the promise on (`postpone`), never back, and up to the week the runner waits at most (`MAX_WAIT_SECONDS`). When that write fails, the error raised stays adsb.lol's with its wait, and the poller keeps the moment (`_pending`) and writes it before it asks again. A poll that finds the time not come asks nothing and answers `PollReport(again_in=...)`: the runner polls it again then, logs nothing, and leaves the source's status as it was, because nothing was learned of the source; do not raise an error for it. The poller takes no interval from its caller (`interval_seconds` is refused for a client that asks the network). Do not add a way to set how often adsb.lol is asked other than what a key allows, and take a key to allow 500 a day until `BEACON_ADSBLOL_REQUESTS_PER_DAY` says more.
- **Product lines that keep Beacon inside the hackathon rules** (see HACKATHON.md, "Constraints for Beacon"):
  - The answer to a tap is the product. The map is secondary and opened from an incident card.
  - A photo only adds evidence to a tap and its incident. There is no "analyze this photo" feature.
  - EMS traffic is "medical response" with crews and a block-level location only. Strip patient details, names, and house numbers before anything is stored or shown. That includes what the Ember client stores: a call whose input is EMS traffic is made with `sensitive=True`.
  - Beacon relays official orders and never tells anyone to stay or go on its own. Official notices outrank radio traffic, and every claim carries its source and a confidence label.
  - Use only data we have the rights to use.

## Using the Ember client

```python
import base64

from beacon.ember import EmberClient

schema = {
    "type": "object",
    "properties": {"units": {"type": "array", "items": {"type": "string"}}},
    "required": ["units"],
    "additionalProperties": False,
}


def extract_transmission(ember: EmberClient, wav: bytes) -> str:
    answer = ember.respond(
        task="extract_transmission",  # labels the call in the ledger and the trace
        effort="low",  # required; low unless an eval shows a gain
        max_output_tokens=1024,  # required, 16 to 524,288; reasoning tokens count against it
        sensitive=True,  # required; True when the request or answer can hold what must not be stored
        instructions="You log dispatch radio.",  # the stable prefix first, so it is cached
        input=[
            {
                "role": "user",
                "content": [
                    {"type": "input_text", "text": "Which units were dispatched?"},
                    {
                        "type": "input_audio",
                        "input_audio": {"data": base64.b64encode(wav).decode(), "format": "wav"},
                    },
                ],
            }
        ],
        text={  # structured output
            "format": {
                "type": "json_schema",
                "name": "transmission",
                "strict": True,
                "schema": schema,
            }
        },
    )
    # answer.usage, answer.cost_usd, and answer.source ("live", "replay", or "fake") are there too.
    return answer.output_text


# Replay-only unless REPLAY=0, with MODEL_API_KEY and EMBER_SPENT_BEFORE_USD set.
ember = EmberClient.from_env()
```

- **`sensitive` is required on every call.** `True` when the request or the answer can hold what Beacon must not store: any EMS radio traffic, and anything else that can name a person or a home. The ledger and the trace then keep the call's accounting and none of its text, and the answer is not recorded or replayed, so the call is paid for every time and replay-only mode refuses it. `False` stores the request's text and the answer in full, with media replaced by a digest. The client returns the full answer either way; stripping what your own code stores is still yours to do. An error from a sensitive call is one of the client's own with a fixed text and nothing chained under it, so its message can be logged; never log a traceback's local variables, which hold the request.
- `task` and a `SpendScope` label are stored and printed as given, for sensitive calls too. They name the kind of work or its id (`extract_transmission`, `tap:1842`), never an address, a person, or anything read from a request.
- Arguments are the Responses API fields of the same names. Media goes in as inline bytes (`input_audio` with base64 `data`, a `data:` URL, or `file_data`) or a `file_id`; a remote URL is refused, so fetch a PDF or image yourself and send its bytes. Only function tools are allowed, and there is no `tool_choice`.
- A tool loop sends `answer.output` back unchanged as input on its next round, followed by one `function_call_output` item per function call.
- Give a piece of work a cap of its own with `EmberClient.from_env(scope=SpendScope("tap:<id>", budget_nanousd))`, with `SpendScope` from `beacon.ember`. A scope's budget is the most its label may hold in the ledger over every run that uses the label. Money is whole nano-dollars (`beacon.ember.pricing`). To hold several calls of one client to a cap of their own, as one tap's investigation is, pass each `respond(limit_nanousd=cap - spent)`: a live call that could cost more is refused with `CallLimitError` (a `BudgetExceededError`) before its paid request, and any client refuses a limit of zero or less. A limit only refuses; it replaces neither the stop nor a scope. A call with a limit sends its paid request once: a paced client does not try it again after a 429, because the refused attempt keeps its reservation and the caller has no accounting of it to take off its cap.
- Build clients with `EmberClient.from_env`. A live client keeps the stop of the process's environment however it is built, and is refused until `EMBER_SPENT_BEFORE_USD` is set there. Both spending settings are read from `os.environ` only; do not add a way to pass them in. Before it sends the request that generates, a live client sends the same input to Meta's token-counting endpoint.
- Catch `beacon.ember.EmberError` and its subclasses (`BudgetExceededError`, `ReplayMissError`, `InputTooLargeError`, `EmberCallError`, `EmberClosedError`, ...), never an SDK error. Do not retry a failed call yourself: it may have been billed. `LedgerReplacedError` (a `BudgetExceededError`) means the ledger file was deleted or replaced under the process: stop making paid calls and tell the operator, who has to compare Meta's Usage page with the ledger.
- Build a client once per process and share it; it is safe across threads. It reads the spending settings when it is built, so a change to them needs a restart. When the process shuts down, call `ember.close()`: from then on no call is admitted, and one that had not been raises `EmberClosedError`, having cost nothing. A call that was already admitted, at the last check before its paid request, still sends it, possibly after `close` returns; only `ember.drain(timeout)` answering True says nothing more is sent. `ember.mode` says what a client is: `live`, `replay`, or `fake`. The client follows no HTTP redirect, so a request's audio or document goes to Meta's address and nowhere else. A refusal (`BudgetExceededError` that is not a `LedgerReplacedError`, `ReplayMissError`, `EmberClosedError`) means no paid request of the call was sent, for a client with a pacer too.
- To point at a call's ledger row later (a tap's token count, say), keep `answer.ledger_ref` and read it back with `ember.ledger_calls([ref])`. A row id alone does not name a call.
- **In tests**, use `EmberClient.fake(Storage.under(tmp_path), Script([fake_response(text="...")]))` from `beacon.ember`; `fake_response` also takes `function_calls` and token counts. It checks requests the way a live client does and spends nothing. `server/tests/test_ember_audio_rate.py` is a short example.
- **With no key**, a feature runs on a responder passed to `EmberClient.fake`. Its answers have `source == "fake"`: carry that to the API reply and the app, and label the result as a stand-in's.
- No real Ember call has been made yet, so the request shapes are from Meta's documentation and unverified. When a key exists, run `scripts/measure_audio_rate.py` first (README, "Measure the audio token rate").

## Using the evidence store

```python
import os
from datetime import timedelta

from beacon.evidence import EvidenceStore, NewEvidence, Point
from beacon.ingest import open_store

store = open_store(os.environ)  # the mock store unless BEACON_LIVE_SOURCES names a source

# Read: what any source said near a place in the last ten minutes, plus rows with no
# point, such as a city-wide alert. Oldest first.
rows = store.search(
    kinds=["radio", "aircraft", "alert", "traffic", "notice"],
    start=now - timedelta(minutes=10),
    end=now,
    near=Point(37.7766, -122.4236),
    radius_m=500,
    include_unlocated=True,
)
for row in rows:
    row.kind, row.source, row.ref  # ("alert", "nws", "urn:oid:...")
    row.occurred_at, row.until  # aware datetimes in UTC; until is None for most kinds
    row.point, row.place  # Point | None, and the place in words | None
    row.confidence  # "official", "high", "medium", or "low"
    row.stand_in  # True for the mock scenario's rows and a fake Ember's
    row.data  # a dict whose shape belongs to the row's kind and source

# Write: only a poller or an ingest route does. The same source and ref is stored once.
store.add([NewEvidence(kind="tap", source="app", ref=tap_id, occurred_at=now,
                       confidence="low", origin="live", point=where)])  # as `Taps.take` does
```

- **A row is one thing one source said, and it is never changed.** A revision is a new row: an NWS update names the alerts it replaces in `data["replaces"]`, and each version of a 511 event is a row whose `data["event_id"]` is the same.
- **`search` returns history, not what is in force.** The store applies no revision for you, and the rows that end something can lie outside your window or your radius: an alert issued an hour ago is found by its span long after a later row said it was replaced, cancelled, or no longer listed. To decide what is in force at a moment, take the candidate rows and then look up, with no upper bound on age and no distance filter, the later rows of the same source that name them: `data["replaces"]` (NWS), a later version with the same `data["event_id"]` (511), an NWS row whose `data["message_type"]` is `Cancel`, and rows with `data["change"]`.
- **An item that stops being listed has not been officially ended.** NWS and 511 answer with what is active now, and mostly an alert or a closure that is over is just missing from the next answer. When an item has been missing from two complete answers in a row, the poller stores a row with `data["change"] == "not_listed"` and `data["about"]` holding the `ref` of the row it is about. It records what Beacon saw, at `medium` confidence: it is not an official all-clear, and must not be shown as one. If the item is listed again, a `"listed_again"` row follows, and the latest change row about a `ref` is the one that holds. An alert that simply ran to its `until` gets no change row. What *is* official is an explicit cancellation: an NWS row whose `data["message_type"]` is `Cancel` is the authority saying the alerts in its `data["replaces"]` are over, and it stays `official`.
- **Rows carry what the source said, not a judgment.** Grouping rows into incidents, deciding that an aircraft is circling, and weighing a notice against radio are the incident engine's, and stay deterministic and tested.
- `search` finds a row with an `until` when its span touches the window, and any other row when it happened inside it. Pass `include_unlocated=True` with `near` unless you want only rows that have a point. Aircraft are one row per position, about every 30 seconds each, so give an aircraft query a short window or a larger `limit` (default 500).
- **A `radio` row** (`source == "recordings"`) is one call, named by its recorder's system and file name (`row.ref`, by which a call is found, ordered, and claimed); `row.occurred_at` is the start its JSON gives, which can be later than the name's. A reader is of one system (`Directory(root, system)`): talkgroup numbers are a system's own. A call is claimed only once its audio plays about as long as its JSON says (`_whole` in `ingest/recordings.py`), because trunk-recorder writes the JSON first: do not claim, and so pay for, a call whose files may still be being written, and do not give an unready call a terminal state, which a backlog's later pass would then never hear. A pass is counted over all its polls (`RecordedRadio.last_pass`, a `PassCount`): `unready` calls are unclaimed and looked at again, `unusable` ones were claimed and are not, and `PollReport.unreadable` is one poll's sum of both, so never read a clean poll as a clean pass. A `Directory`'s mark is checked when it is opened, at each listing, and after each file is read (`_read`): keep the check after the read. `data` is `Transmission.as_data()` plus the call's `system`, `talkgroup`, `seconds`, and `emergency`: `event` (`"medical response"` for a medical call, else the `category`), `category`, `clarity` (`clear`, `partial`, `unintelligible`), `status`, `details` (a list of tags), `units` (ids such as `E36`), `alarm` (1 to 5 or null), `street`, `block` (the hundred block), and `cross_street`. Units and streets are only ones on a list (`beacon.radio.Known`): the story's own in the mock scenario (`beacon.scenario.radio.KNOWN`), and for real radio the operator's files, without which a row has no units, no street, and so no `place`. The lists of categories, statuses, and details are `CATEGORIES`, `STATUSES`, and `DETAILS` in `beacon/radio/vocabulary.py`. `row.place` is the place in words (`400 block of Hayes St`) and `row.point` is always None, so a `near` search finds radio only with `include_unlocated=True`: placing a block on the map is not done in ingest. `row.model` says which Ember heard it, and `confidence` is `medium` for a call heard `clear` and `low` otherwise. Units are how calls of one incident are tied together; a call often names units and no place.
- **A `notice` row** (`source == "notices"`) is **Ember's reading** of one document an authority published (`beacon.notice.read_notice`), and not the document. `row.url` is the PDF, which is the authority speaking; `row.model` says which Ember read it (`live` or `fake`); and `row.confidence` is `high`, not `official`, for that reason (`low` when Ember says the document is no notice). `row.occurred_at` is when the feed says it was published, and `row.until` is `effective_until` when the document gives one. `data` is `Notice.as_data()` plus `page` (the feed item's page, or null): `notice_type` (`evacuation_order`, `evacuation_warning`, `shelter_in_place`, `road_closure`, `all_clear`, `advisory`, `press_release`, `other`), `hazard`, `issuer`, `title`, `issued_at` and `effective_until` (ISO 8601 with an offset, or null), `areas`, `streets` (street names without numbers), `instruction`, `summary`, and `incomplete`. `beacon.notice.ORDERS` are the types that tell people to do something or that they may stop. How to use one:
  - **Never show a reading as the authority's words, and never tell anyone what to do from one.** Say that an authority issued a notice of this type, show the reading labeled as Beacon's reading of it, link `row.url` beside it every time, and send people to the document for the instruction. A reading can be wrong, and can leave out the exception that changes its meaning.
  - `data["incomplete"]` names the fields that are not all there: a text or the areas were more than Beacon keeps and were left out whole (never cut), or the streets were cut to the first thirty. When `instruction` or `areas` is in it, say that the notice has more and link it; do not present what is there as the whole.
  - `issuer`, `title`, `areas`, `streets`, `instruction`, and `summary` are empty for a `press_release` and for `other`, by design: those rows say that a document of that type was published, when, and where to read it. Do not put text back into them.
  - A notice row has no `place` and no `point`. Match it to an incident by `data["streets"]`, `hazard`, and time. An order's `areas` and `instruction` can name addresses finer than a block, as the order does; they are shown only as part of the reading, and never become a row's or an incident's `place`.
  - Nothing lifts an order but another row: an `all_clear` is a separate notice. Which order it lifts is not worked out from the rows, by the incident engine or by anything else: a row keeps streets and no blocks, so both are shown as published, each with its link.
  - The redaction pass (`beacon.redact.reading`) reads a notice's text before it is shown: Ember is told to leave private people out, which is not a guarantee. The incident engine applies it (`Official`); read a notice's words from there, not from the row.
- **A `tap` row** (`source == "app"`) is one press of the button, written by `POST /api/taps` through `beacon.taps.Taps.take`. The route takes a tap only when its `Beacon-Mode` header names the mode the store is in, and refuses any other before it reads the body or holds a place (`400` for none, `409` for the other mode): do not make the header optional or move the check after `admit`, and send it from any script that posts taps. `row.ref` is the tap's id, `row.occurred_at` the server's time, `row.point` the position rounded to three decimals (about a block), and `row.confidence` is `low`. Its `origin` is `live` in the mock store too: a person's tap is nobody's stand-in, so `row.stand_in` is False, and what makes an answer a stand-in's is the other evidence it is built on and the store's `mode`. `row.data` has `accuracy_m` (metres, or null), `photo` (`{"bytes", "width", "height"}` or null), `clip` (`{"bytes", "seconds"}` or null), and `media_kept_until`. The files themselves are read with `request.app.state.taps.media(tap_id, "photo" | "clip")`, which returns the JPEG Beacon drew from the photo (at most 2048 pixels on a side) or the WAV of the clip, or None once the row's `media_kept_until` has passed, for a tap with no row, and for a kind its row does not say it sent: handle None, do not copy the bytes anywhere that outlives the hour, and keep only what was concluded from them. A call to Ember that sends a tap's photo or clip is `sensitive=True` (it can show or record a person), so it is paid for every time and cannot run in replay-only mode; test it with `EmberClient.fake`. Do not store or log the position a phone sent, and do not add anything to a tap that says who sent it.
- What `data` holds is documented where it is written: `beacon/ingest/nws.py` (`_alert`), `adsblol.py` (the module's docstring), `traffic511.py` (`_event`), for radio `beacon/radio/extract.py` (`Transmission.as_data`), and for a notice `beacon/notice/read.py` (`Notice.as_data`). Units are SI: metres, metres per second, degrees clockwise from north. A 511 row keeps the event's `schedule` as 511 sent it; the poller asks only for events in effect now.
- Anything shown from a `511` row carries the words "data provided by 511.org" with a link to https://511.org beside it: 511's data agreement requires it.
- The mock store and the live store are separate files, and a store is one or the other for life. Code that reads evidence takes an `EvidenceStore` as an argument; only an entry point (the server's startup, a script) calls `open_store`. In the server, the store the pollers write to is `request.app.state.ingest.store`, and `request.app.state.taps.store` is the same file, opened for the taps, which is there with `BEACON_INGEST=0` too. It is closed when the server shuts down: `store.close()` makes every later `add` raise `EvidenceStoreError`, while reading goes on working.
- **In tests**, make a store with `EvidenceStore(tmp_path / "evidence.sqlite3", "mock")` and add rows, or play the scenario: `build({"BEACON_DATA_DIR": str(tmp_path)}, Clock(lambda: moment)).catch_up()` from `beacon.ingest` stores everything the invented fire's sources said up to `moment`, where the story began twenty minutes before the `build`. `server/tests/test_ingest_setup.py` shows the whole story and when each row appears. The story's radio is in `beacon/scenario/radio.py` (`CALLS`): to hear a call of your own in a test, hand `extract_transmission` an `EmberClient.fake` whose responder answers with a filled-in form, as `server/tests/test_radio_extract.py` does.
- **A new source** is a module in `beacon/ingest/` that copies `nws.py`: a class with `name`, `interval_seconds`, a read-only `origin` property that returns its client's (`self._http.origin`; for the one poller that reads files and asks no network, what its shelf is: `RecordedRadio.origin` is `live` only for a `Directory` on this machine that is not marked `BEACON-GENERATED`, and `mock` for any stand-in for one), and a `poll(store, now)` that begins with `store.refuse_stand_in(self.origin)` and returns a `PollReport` (with `partial=True` when it did not read the source's answer to its end), a pure `parse_...` function that turns the source's reply into `NewEvidence` and counts what it could not read, the source's answers added to `beacon/scenario/`, and its name added to `SOURCES`, `source_pollers`, and the mock pollers in `setup.py`. Its tests answer through `SourceHttp(httpx2.MockTransport(...))` and write to a mock store. A poller does not choose its rows' origin: it is `http.origin`, which is `mock` for a client built with a transport and `live` only for one that asks the network, so what a stand-in answers cannot be stored as `live`.

## Using the incident engine

```python
from beacon.incident import open_engine

engine = open_engine(os.environ, store)  # in the server: request.app.state.incidents
for incident in engine.incidents():  # the last twelve hours, newest first
    incident.id, incident.title, incident.status, incident.open
    incident.place, incident.point  # no finer than a block; the point can be None
    incident.stand_in  # True when any row under it is a stand-in's
    for entry in incident.timeline:
        entry.text, entry.confidence, entry.sources  # what one source said, and which
    incident.official  # alerts and notices, each with its state
    incident.signals  # what code can say makes it more than an everyday call
engine.get(incident_id)  # one incident, or None
```

- **An incident is derived, never stored.** It is a function of the evidence rows (`build_incidents`), worked out again when the store has a new row. Do not add a table of incidents: a second record can disagree with the first. What a model writes about an incident is kept under the incident's id and a digest of the lines it was written from, beside the engine and not in it (`beacon.story.Stories`).
- **The engine asks no model.** Grouping, what is in force, circling, and signals are plain code with tests. Change a rule in `calls.py` or `build.py` with a test that fails without the change.
- **Every line names its rows.** An `Entry`, an `Official`, and a `Signal` carry the sources they rest on (`Source`: the feed, the row's id, its link, its credit), and an entry's confidence is its row's. A new kind of line does the same, with `source_of(row)`; a line that rests on several rows is trusted as little as the weakest (`weakest`).
- **Medical stays medical.** A medical call is grouped only with medical calls, its entry is "Medical response", units, and block, and its incident has no alarm, no official list, no signals, and no taps. Nothing downstream adds them back.
- **A notice's words are shown only through the redaction pass, as a reading.** A notice's timeline entry says only that a document of its type was published, with its link. `Official.issuer`, `headline`, `instruction`, `summary`, and `areas` hold a notice's words only when `beacon.redact.reading` let the whole text through; what did not pass is named in `Official.withheld`, and nothing is read of a type outside `TEXT_TYPES`. Show them as Beacon's reading beside `source.url`, never as the authority's words. Do not show a notice's text by any path that does not go through the pass.
- **Official outranks radio, and code says so.** `Incident.conflicts` lists where the radio and an official source disagree, with a text that says the official source holds and why, and a confidence that is the weakest row's. Finding and wording a conflict is code's (`_conflicts` in `build.py`); no model weighs one source against another. Two sources disagree only in the order of their times: an all-clear on the radio is set against an alert or an order issued before it, and a notice against a call made before it. Do not pair rows without their times.
- **`published` is not `in_force`.** Beacon has read a document; it does not know that an order still holds. Say that an authority published it. An all-clear is another published document, and no code says that it lifts an order: a notice's row keeps streets and no blocks, so an all-clear for one block of a street cannot be told from one for another. Show both with their links; there is no `lifted` state, and do not add one.
- **`not_listed` is what Beacon saw.** Keep the words "not an official all-clear" with it.
- **No text says who spoke on the radio.** A radio row keeps what was said and the units that were named, and not the speaker: a dispatcher relaying an all-clear leaves the same row as a crew giving one. A line, a signal, a conflict, and a story's sentence say that something was said or reported on the radio, never that crews said it or did it.
- **A point from 511 carries 511's credit.** `incident.point_from == "closure"` says the point is a 511 event's, and `incident.point_source` is that row's `Source` with the credit. Show the credit wherever the point is shown, a map included; a point from the list of blocks has no `point_source`. **A point from 511 is approximate, and every sentence about it says whose working out it is**: the 511 poller keeps the middle of the box around what 511 drew for an event (`ingest.area.centre`), which need not lie on the road, and the radio need have named no block. So it is "an approximate point Beacon took from a 511 event", never "where 511 listed the closure" and never "the block" (`_PLACE_FROM_511` and `_EVENT_POINT` in `mapping/features.py`, `_FROM_511` in `places/check.py`). What 511 reported (its headline, that it lists a road as closed) stays 511's and `official`.
- **A signal names what its rows say and no more.** A warning is an "evacuation warning", never an order. Notices are not said to have come before or after one another. A closure is a signal only while the version in force closes a road of the incident's or lies near its point. A message that revises a revision is not said to have changed an alert that applied here.
- **Taps are counted, as taps.** Nothing tells one sender from another, so three taps are never "three people". An incident holds how many taps came from near it and none of their ids, because a tap's id is what its sender reads the answer with. Do not put a tap's id or point into an incident.
- An incident's `id` is a digest of the source and reference of the row of its that was stored first. It is this store's own: another store that took the same calls in another order can name the incident by another row. It changes when that row leaves the engine's twelve hours, or when a call stored late regroups the incident.
- **Answer from one `engine.snapshot()`.** It holds the incidents, `as_of`, and `partial` of one reading of the store; a route that reads `engine.incidents()` and then the time has put two readings together. A search made as part of a reading passes `up_to_id`.
- **A text that may have been cut is not relayed.** A stored text as long as its poller keeps (`nws.MAX_TEXT`, `nws.MAX_HEADLINE`, `traffic511.MAX_HEADLINE`) is left out whole, and an alert names the field in `Official.incomplete`. An alert applies to a place only when its drawn area holds the place.
- **`unknown` is not `in_force`.** When the rows that could end an old alert were not all read, the alert's state is `unknown`, the reading is `partial`, and no signal is made of it.
- **In tests**, `server/tests/incident_rows.py` has `Rows`, which stores one row of each kind in a mock store, and `open_engine({}, store, clock=...)` reads it at a moment of your choosing. `server/tests/test_incident_engine.py` plays the whole mock scenario through the engine.

## Using the redaction pass and stories

```python
from beacon.redact import reading
from beacon.story import merge_incident, point_claim

names = engine.names  # the listed streets, units, and public places, or None
reading(notice_text, names)  # the text, or None when it does not pass
names.public_body(issuer)  # the issuer, or None when it is not one listed body

desk = request.app.state.stories  # a StoryDesk, or absent when no stories are made
found = desk.latest(incident)  # (Story, current) or None; asks Ember nothing
```

- **No sentence a model wrote is shown in Beacon's voice. Code writes every one.** A model that has a part in what Beacon says chooses from a closed list and cites rows; code checks the choice against those rows and writes the words (`point_claim` and `_sentence` in `story/merge.py`). Do not add a free-text field (a headline, a summary, a note, a reason) to a form a model fills in for something Beacon says, and do not try to make such a text safe with a list of words: "Exit the building." is made of ordinary words. A new thing worth saying is a new kind in `POINT_KINDS` with its check and its sentence.
- **The one text of a model's that is shown is a reading of a notice, through `beacon.redact.reading`**, labeled as Beacon's reading beside the document's link. A listed name is listed whole or left out (`Names.kept` says how many were): never list the readable words of a name that is not written plainly. A text passes whole or is left out whole: never cut one, and never show one that failed. When a word plainly belongs, add it to `vocabulary.py` after asking whether it can describe a person; never add a way past the lists.
- **A point is kept only when every line it cites shows it.** The check reads the cited rows' own fields (`Entry.details`), not the line's words and not the model's. A point that fails is left out and counted (`Draft.left_out`), never mended. A sentence says no more than its cited rows show, as of the newest of them: cited alarm levels have to agree; a version of a 511 event that is not in force is told only as having been listed, never as listed here, changed, or ended, which a row the point does not cite would have to show; and a row that records a change is told as what Beacon saw at that check, in the past tense (`CHANGE_SAID`), as a detail a call gave is told as what was said on the radio (`DETAIL_SAID`), with no word for who said or did it: a row keeps the detail and not the speaker, so never "Crews requested police." A story's sentence is read apart from its line, so do not reuse a timeline line that is in the present tense for anything but the version of a 511 event that is in force.
- **A model is given no official text to retell.** `merge_incident` sends only radio, closure, aircraft, and tap lines (`LINE_KINDS`), and no kind of point is about an order, an alert, or a notice. What an authority said is shown by code from `Incident.official`.
- **Code derives a claim's sources, confidence, and time.** A `Claim` gets them from the lines it cites (`weakest`). Do not let a model state its own confidence or source.
- **A change to what a kept file holds raises its number, whether or not the rows of before can still be read.** When they can be read as they are, name the old number in `_READABLE` and not in `_EARLIER` (`begin_file(readable=...)`): the file keeps every row and gets the new number, so that an older Beacon, which would read the new rows without what they gained, refuses it. The stories file went from 3 to 4 that way when a credit gained its pieces, and the investigations file from 2 to 3 when a run began to keep feeds. A feed that is renamed or replaced is by itself no reason to drop stories: a kept story names each source by the feed, label, and credit its row had when the story was written, and they stay true of the rows it cites; dropping it would lose a story whose basis is claimed and cannot be paid for again.
- **A story is paid for once per basis.** `Stories.claim(incident_id, basis, ...)` before `merge_incident`, inside `PaidDesk.working()` so that a shutdown waits from before the claim to the story's row, as `StoryDesk` does; the rules after Ember has been asked are `PaidDesk`'s. A refresh checks that the desk is not closed after it enters `working()` and before it claims, so a claim is never made that a closed stories file could not give up. `StoryDesk` pays under the scope `story:merge`, and a pass counts paid attempts, not stories. Reading a story (`desk.latest`, the incident route) never asks Ember.
- **A shutdown closes everything that pays before it waits for anything** (`_close_paid` in `main.py`). Something new that pays is added there.
- **Only what code wrote is in the stories file**, and the live file refuses a stand-in's story. A story is shown in the words it was kept in, so when you change what `_as_json` in `story/store.py` writes **or any sentence code writes for a story** (`story/merge.py`, and the engine's timeline lines for a 511 event, an aircraft, and taps, which a story reuses and the test below does not watch), raise `_FORMAT` and add the old number to `_EARLIER`: a file of an earlier number then has its stories emptied when it is opened and keeps its claims. `test_the_words_of_a_story_are_not_changed_without_the_files_number` fails until you do. A file is looked at and changed under one write lock (`beacon.files.begin_file`), and nothing of a file that is refused is written, its journal mode included: do not read a file's number or mode outside that transaction, and do not use `_connect`, which sets the journal mode, before a file is accepted. Never advise deleting or moving a stories file: it is the record of what was paid for. `merge_incident` is a `sensitive=True` call: nothing of Ember's answer but its points is read, and none of it is in the ledger.
- **In tests**, hand `merge_incident` an `EmberClient.fake` with a `Script` of answers, as `server/tests/test_story.py` does, or use `stand_in_writer`.

## Using the investigator

```python
from beacon.investigate import open_investigations

# The file of what was investigated, and the desk, which is None when taps are not
# investigated (the live store with no budget). In the server they are
# request.app.state.runs, which is always there, and request.app.state.investigations.
runs, desk = open_investigations(os.environ, engine, taps)
desk.submit(tap_id)  # hand a tap in; never raises, and waits for no worker (a full queue costs one write)
desk.state_of(tap_id)  # "queued", "running", or None: whether its answer is still coming
found = runs.get(tap_id)  # (claimed_at, Run | None) or None; asks Ember nothing
runs.crisis(incident_id)  # the decision that turned crisis mode on (Decision), or None
```

- **The routes are the interface for the app**: `GET /api/taps/{id}` (the answer) and `GET /api/taps/{id}/run` (the trace), in `server/beacon/api/taps.py`, where every field is commented. An incident's `crisis` is on every incident route (`crisis_of` and `summary_of` in `api/incidents.py`). The README's "The investigator" says what each field means. Show `text`, `investigator_text`, `stand_in_text`, `since_text`, `nearby_text`, `cost_text`, and a crisis's `text`, `decided_by_text`, and `signals_text` with what they are about: they are how the answer says what is the investigator's reading, whether the investigator was a model or a stand-in, what is built from a stand-in's rows, and what nobody investigated. Show a ground's `credit`, a call's `credits`, and an answer's `nearby_credit` and `since_credit` beside what they are about: they are 511's, and its data agreement requires them. The routes read `app.state.runs`, with or without a desk: what was investigated and paid for is read on a server that investigates nothing.
- **Whether a tap's answer is still coming is the desk's to say** (`InvestigationDesk.state_of`), never a timer's: `_kept` in `api/taps.py` asks the desk first and reads the file after, and the desk stops counting a tap only after its run is written. `lost` is a claim with no run that no desk is working on. Do not put a time limit back.
- **A tap is investigated on the evidence as it stood when it came**: the desk builds the run's `Scene` from `Engine.at(row.occurred_at)`, and every tool reads from that snapshot or from the store up to its `as_of` and `last_id`. An incident that began after the tap is no part of its run; it is listed in `since`, by code. Do not hand a run `Engine.snapshot()`.
- **A tap's id is what its sender reads its answer with.** Do not put a tap's id in anything shown of an incident or in a log, and do not add a route that lists taps.
- **Ember is never told where a tap is or when it came, and a tool takes no place.** A tool's arguments are picked from short lists (`RADII_M`, `MINUTES`) or are an incident id a tool of the same run returned (`_checked` in `tools.py`). What a tool tells Ember is ids, counts, numbers, and tags that are on their lists (`_tag`): no street, unit, callsign, headline, instruction, or link. A tool shows only what is near the tap: `get_radio` is the calls of the incidents `nearby_incidents` returned in this run. For a medical response Ember is told an id, its category, and its distance only: not whether it is going on, no radio call, nothing official. A new tool keeps to that, returns `(told, kept, paid)`, and keeps less than it tells: `kept` is what goes to disk. What `kept` counts from a source with a credit (511's closures, a place from one) carries the credit where it is shown (`_credits` in `api/taps.py`).
- **Ember answers with closed lists, and code checks them** (`_outcome`, `_holds`, `_fits`, `_crisis` in `loop.py`). Do not add a free-text field to `SCHEMA`, to a tool's parameters, or to `Run`, `Call`, or `Outcome`: a new thing worth saying is a new value in `GROUNDS`, `THINKING`, `WHY`, `SOUNDS`, or `SIGHTS`, with its check and its sentence in `card.py`, and for a sound or a sight the categories it is evidence of (`_FITS`). A match needs `near`, or a ground that ties this tap to the incident (`LINKS`) together with one other; `going_on` and `other_taps` are true whoever tapped and are no match by themselves. `aircraft_overhead` is one aircraft over the incident and in reach of the tap (`tools.overhead`), not one over each. Do not lower any of that, and do not let a match's confidence be more than `medium`. An answer is read only when it is the whole form (`_whole`): one with a field missing is `no_answer` and counts toward the desk's hold, and a value that is not on a list is dropped from a form that is whole. A ground's sentence says what its check checked and no more: `going_on` is "open, or an update in the fifteen minutes before", and a clip or a photo with several tags says "at least one of these fits".
- **Crisis mode stands only on signals the engine found for the incident, and never for a medical response.** It is checked when it is decided (`_crisis`) and again when it is shown (`crisis_of`). The decision kept is the first that turned it on, with each signal as it was then (`Cited`: kind, confidence, evidence ids, and the feeds whose credit goes with it); what the incident has now is shown apart from it and said to be that. A cited signal carries its credit itself (`cited_credit(cited)`, from `Cited.credits`, with 511's for every `closure`), because the signal that would carry it can be gone; showing a decision reads no evidence row. Its text says it is the investigator's decision and no authority's, and tells nobody what to do; no text about a tap or a crisis says "stay", "go", "leave", or "evacuate".
- **A stand-in is never called a model, and a model never a stand-in.** `card.investigator_text(model)` says who investigated, `card.stand_in_text(model, evidence=...)` says what a stand-in had a part in, and the fixed sentences say "the investigator's". An answer is a stand-in's when a stand-in investigated or when anything it shows is built from a stand-in's rows.
- **Sentences are written when a run is read, never stored** (`card.py`). The investigations file holds ids, counts, tags, times, and each call's accounting, so a change of wording needs no change to the file. When what `_run_json` in `investigate/store.py` writes changes, raise `_FORMAT` and add the old number to `_EARLIER`, or to `_READABLE` when a run of the old shape is read as it is (a key a reader takes as absent, as the feeds a run names are): its runs and decisions are then kept, and the number still goes up.
- **Every Ember call of a run is `sensitive=True`**, the tools' own included, and a run keeps nothing of an Ember error but its class's name. A tap's photo and clip are read with `Taps.media`, sent in one call each, and only the tags from `SIGHTS` and `SOUNDS` are kept.
- **A tap is claimed before Ember is asked, inside `PaidDesk.working()`, after the desk is seen not to be closing**, and the claim is never released: a run makes several paid calls. A tap older than `STALE` when its turn comes is passed over and never claimed, so a tap whose claim was swept (`KEPT`) is not paid for twice. One hold is shared by the desk's threads (`InvestigationDesk._hold`, under `_holding`); do not read the hold from the file for each run, or a run that ends well takes off the hold another run just put on. A hold is never made shorter by a later failure (`_later` in `ingest/paid.py`). The desk pays under the scope `investigate:tap`. **One tap's cap is held by the Ember client**: every call of a run, a tool's included, passes `limit_nanousd=TAP_BUDGET_NANOUSD - spent`, and the client refuses a call that could cost more before its paid request (`CallLimitError`, which ends the run as `budget`); a check of what was spent so far is not enough, because the next call can cross the cap. A call that ends in an error after it may have been sent is counted in `Run.unaccounted`, and the routes then say the totals may be incomplete (`card.COST_INCOMPLETE`; `card.COST_LOST` for a run nothing was kept of). Neither sentence says a call failed that may never have been made, or that a cost is in the ledger, which a replaced ledger does not have. The desk takes a tap in, and a stop empties the queue, under one lock (`_tracking`), so no tap is taken in after the stop; a tap has one place in the queue and one run under way, and only the thread making a run takes its mark off. `main._close_paid` closes the desk before anything is waited for at shutdown, and it is stopped before the taps are closed, because a run reads a tap's media. `main._sweep_runs` deletes what is older than a day every minute.
- **`beacon/files.py` (`begin_file`) is how a SQLite file that is one mode's, in one shape, is opened**: the look and the change in one write transaction, a refused file left as it was to the byte. The stories file and the investigations file both use it; a new file of the kind does too. Never advise deleting or moving such a file.
- **In tests**, hand `investigate_tap` an `EmberClient.fake` with a `Script` of `fake_response(function_calls=[...])` and a final `fake_response(text=json.dumps(form))`, and a `Scene` built from `Rows` (`server/tests/test_investigate.py` has `scene_of`, `asks`, and `form`). For the desk and the routes, build an `InvestigationDesk` with `workers=0` and call `desk.investigate(tap_id)` by hand (`server/tests/test_investigate_desk.py`, whose `World.app` sets `app.state.runs` as the server does); `stand_in_investigator` answers by rule. What only a live client does (the cap, the ledger, a failed paid call) is tested with a live client over a fake transport, `MetaApi` in `server/tests/test_ember_client.py`, as `live()` in `test_investigate.py` does.

## Working on the app

`web/src/` has one concern to a directory:

- `api/`: one module per server resource, with the route's types field for field as the server's `api/` module documents them, and its `fetch` functions over `fetchJson`.
- `lib/`: what is not a component. `router` (the views, named in the URL's fragment), `poll` and `cadence` (asking again), `tapStore` (the taps this device sent), `placeStore` (the places a person saved), `push` (whether this device wants notifications, and the one way the server is told, `syncPush`) and `pushSync` (`usePushSync`, which `App` runs), `geo`, `recorder`, `wav`, and `photo` (what a tap sends), `labels` (short names for the server's closed lists), `tiles` (the street map's tiles, their credit, and where a position falls among them), `marks` (where a thing's dot and its number go on the map's picture), `logging` (a tap's id taken out of a line before it is logged), `time`.
- `components/`: what several views show. `Provenance` is how a claim says where it is from (`ConfidenceLabel`, `Sources`, `CreditLine`, `StandInTag`, `WhoNote`, `Line`); `IncidentCard`, `IncidentBody`, and `IncidentLive` are an incident; `MapCanvas` is the picture of its map; `Notifications` is the panel that turns notifications on and off, on the places' page.
- `views/`: one module per view: `Home` (the button), `TapView` (the answer), `TraceView` (the agent trace), `IncidentView`, `MapView` (the map of one incident), `PlacesView` (saved places).
- `test/`: `fixtures.ts` (answers of the server's routes, captured from the mock scenario), `server.ts` (`serve`, which stands where the server is), and `locks.ts` (the browser's lock, which jsdom lacks and `setup.ts` gives every test).

The rules the app keeps:

- **The app writes no sentence about an incident, an order, a match, or an investigation.** It shows the server's (`*_text`) as given. A label in `lib/labels.ts` names a value of a closed list and claims nothing: "Published" for a notice, never "in force"; "Official order or warning published" for `official_notice`, never "order". When the app needs to say something new about what happened, add a field to the route, with its sentence written by code on the server, as `status_text` is.
- **Every claim is shown with its confidence and its sources** (`Line`, or `ConfidenceLabel` with `Sources`), and 511's credit goes wherever something from 511 is shown: a line, a ground (`credit`), a cited signal, a tool's answer in the trace (`credits`), and the incidents listed as near a tap when a place is 511's (`nearby_credit`, `since_credit`). adsb.lol's notice goes wherever something rests on a position adsb.lol answered with, through the same fields and the trace outcome's `credits`: the app shows whatever credit the server sends (`CreditLine`, which gives each of a credit's `parts` its own link) and names no feed itself. A source's `label` is shown as the server gives it: the server labels a row a stand-in wrote by its feed alone, and never "as Ember heard it" (`label_of`, and `SourceOut` for a label a story kept). **`IncidentCard` shows only what the incident's radio calls gave** (title, `status_text`, place, units, alarm, `opened_at`), under the route's `radio` (the calls' sources and the least confidence among them). Do not put a fact from another source on the card (`taps`, `updated_at`, a closure's point): give it a source of its own in the route first, or leave it to the timeline.
- **`open` is the state of Beacon's record, not of the place.** A record closes when the radio clears the call and also when the radio has only been quiet for 45 minutes. Label it "Open/Closed in Beacon's record" (`labels.recordState`) and never as "going on", "over", or "ended"; the same goes for an inactive crisis, of which the app says only that crisis mode was on.
- **Nothing is shown of an incident the server answered 404 for**, the last reading and a tap's summary of it included (`IncidentLive`). A count in the trace is named for what the server counted: `round.calls` are the calls that were kept, `ember_calls` the requests that answered, and what may be missing is said only in the server's `cost_text`.
- **A notice is shown as Beacon's reading, beside its document's link, every time.** An alert's instruction is shown as the authority's own words. No component shows a notice's text without the label and the link, and none words what to do.
- **A stand-in is never shown as a model.** Show `stand_in_text` and `investigator_text` with what they are about (`WhoNote`), mark a stand-in's rows (`StandInTag`), and name who answered a request from its `source`: "Muse Ember" only for `live`.
- **The answer to a tap is the product.** The first view is the button. Do not add a view that lists incidents, a feed, or a dashboard, and do not add a control that sends or looks at a photo apart from a tap. The map is of one incident and is opened from that incident's card (`IncidentLive`): do not link it from the button's page, and do not make it show a second incident.
- **A medical response is its title, its crews, and its block**, with the source of those. `IncidentCard` shows nothing else of one, whatever the route sent: no status, no alarm, no taps, no time, and not whether its record is open. Its own page is that card (`IncidentLive` leaves its timeline out, which would add the times of its calls), and a card of one links nowhere.
- **A tap's id is its sender's.** It is kept in local storage (`tapStore`) and named only in the URL's fragment, which no server is sent. Do not put it in a path or a query of a page, in anything logged, or in a request to anything but the tap's own routes. Those routes do carry it in their path, so anything that proxies `/api/taps` must not log the path: `vite.config.ts` gives Vite a logger that leaves it out (`lib/logging.ts`), and a production proxy needs the same (README, "The app"). An id is deleted from storage when it runs out (`sweepTaps`, started once in `App`), not only hidden; `tapStore` hears other tabs through the `storage` event and writes back only when what it was told of holds a tap that ran out, and a write storage refused is not tried again on a timer. The list a view shows is `tapsSnapshot`, which leaves a tap out from the moment it runs out whether or not storage let it be deleted; `sweepTaps` tells the views at that moment. The router takes a tap's id only for the tap's views: `#/incident/<id>` and its map need an incident's id (`INCIDENT_ID` in `lib/router.ts`, `inc-` and sixteen hex digits), so a tap's id is never put in an incident route's path. A new view that asks a route by an id from the fragment checks the id's shape the same way.
- **No tap is taken before the server's mode is known** (`ready` in `Home`; `App` hands `Home` no mode while the latest health request failed, whatever an earlier one said), or while a chosen photo is still being drawn (`drawing`). A tap that is waiting when `mode` changes, to another mode or to null, is called off (`Home`'s layout effect on `mode`), and `tap` asks after every wait whether it was (`unlessCalledOff`) before it sends anything. Between two askings of the health the app cannot know of a change, so `sendTap` names the mode that was shown at the press (`Beacon-Mode`) and the server refuses a tap made for the other mode unread; on that `409` `Home` shows the server's sentence and `App` asks the health again at once (`onOtherMode`): a tap goes with what its sender was told and what they chose.
- **The map draws only what the server placed, and words nothing.** `GET /api/incidents/{id}/map` gives each thing as a `Feature` (`beacon.mapping`): a sentence written by code, a confidence, and sources. `MapView` lists every feature under the number it has on the picture, with `text`, `note`, `ConfidenceLabel`, and `Sources` (which shows 511's credit); `MapCanvas` draws shapes and numbers and no words about the incident. A new thing to draw is a new `kind` in `mapping/features.py` whose sentence is a line the timeline already has, or is written there, with its test. Only what holds is drawn: the version of a 511 event that is in force, and an alert whose state is `in_force` (never `unknown`). **An area is drawn whole or not at all**: `_polygons` answers None when any ring cannot be read, a hole included, and the feature then has no polygons and a `note`; never skip a ring to draw the rest, because an area without a hole shows a place as inside it that the alert leaves out. **An area is polygons, each with its own holes, and is filled that way** (`Area` in `MapCanvas`, a mask for each polygon): a place is in it when it is inside some polygon's outline and in none of that polygon's holes, as `build._inside` reads it. Never flatten the polygons into one list of rings or fill several rings in one path by parity. **A dot is a thing's own point and is never moved** (`marksOf` in `lib/marks.ts`): only its number gives way, joined to the dot by a line and kept whole inside the picture. Do not move a dot to make room. An area's number is about a point of its outline that is in view (`anchorOf`), never a corner of the box around it; an aircraft's is about its newest position in view, or with none in view a point of its drawn line that is, with no dot, because nobody saw it there: whatever is drawn in the view has its number, and only a real position has a dot; an area with no outline in view that holds the picture gets no number and the sentence under the picture (`coversView`), which is about the picture and is the only sentence `MapCanvas` writes. **A feature's sources name every row that put something on the picture**: an aircraft's are the rows of all its plotted positions. **A source's credit is in the picture's own frame** (`.map-credits`, a strip along the lower edge of `.map-canvas`, under the square that is drawn on and not laid over it, because a credit can be a sentence long) whenever a feature with that credit is drawn, with tiles or without (`creditsOf`), and in the list too. **Never draw a tap or a saved place**, and never give a medical response a map (the route answers 404, and `IncidentLive` offers no link). On the mock store the picture carries its own "Invented scenario" tag whatever it is drawn on; do not word it by the background.
- **Map tiles are OpenStreetMap's, on its tile policy's terms** (`lib/tiles.ts`, README "The map"): the credit stays in the picture's frame, along its lower edge, only tiles in view are loaded (`frameOf`, at most sixteen), nothing prefetches or stores tiles (do not add tile hosts to the service worker's caching), and the tile `<img>` keeps `referrerPolicy="strict-origin-when-cross-origin"`, which sends the site's origin, as the policy requires, and never a fragment or a path. Other tiles are a build setting (`VITE_MAP_TILES` with its credit), and tiles are never shown without a credit. Do not add a map library or a tile source that needs a key without recording its terms the same way.
- **A saved place is the device's, and a check of one keeps nothing on the server.** The one copy the server has is a subscription's, for a device that turned notifications on ([Working on notifications](#working-on-notifications)). Its name and where it is live in local storage (`placeStore`), at most five. `checkPlaces` sends where each is, rounded, and never a name; `POST /api/places/check` stores nothing, logs nothing (`PRIVATE_PATHS`), and repeats nothing in an error. Do not add another server-side record of a place, a field for its name, or a place to a request's address. The view asks only when the mode is known, names the mode it was shown (`Beacon-Mode`), and on a `409` has `App` ask the health again (`onOtherMode`). An answer is matched to its place by position, so one that has not an entry for each place is shown under none (`fits` in `PlacesView`), and `usePolled`'s key holds where the places are, so an answer for another list is never shown. `PlaceList` shows the places and their Remove controls and asks the server nothing, so a place can be removed before the mode is known; only `Checked` sends anything. `savePlace` and `removePlace` are async: each reads and writes the whole list inside `alone`, the browser's lock shared by the app's tabs, and reads only once it holds it. Do not read the list outside the lock for a change, and do not make a change without the lock: where the browser has none, the change fails and the view says so (tests have one from `test/setup.ts`). A place outside `geo.COVERED` is not saved and not read from storage; `COVERED` is the server's `SAN_FRANCISCO`, and `test_the_app_saves_places_in_the_area_the_server_answers_for` fails when they differ. The route holds a place in `Admission` (`app.state.place_checks`) from before the body is read until the answer is made, and refuses one more with `503`: keep the admission ahead of `read_body`, and give the place back from the worker, not the request.
- **What is near a saved place is a distance, in the server's sentence.** `near[].text`, `places[].text`, and `caveat_text` are shown as given, with `caveat_text` beside every answer. A distance measured from a 511 closure's point says so in `text`, and the view shows `incident.point_source` (its confidence, its label, and 511's credit) beside that distance and no other; the card's own confidence is its radio calls'. Nothing in the app or the route says that a place is inside or outside the area of an order or an alert, that it is safe, or that nothing is happening: `NOTHING_NEAR` says what the reading lists and that it is no all-clear, never that there is no incident: a medical response at the place and a partial reading get the same sentence, and it must stay one sentence that does not depend on what was left out. A medical response, an incident with a closed record, and one with no point are not listed (`places.check.near`). The view lists only what is near a place the person saved; it is not a list of the city's incidents, and must not become one.
- **Nothing finer than a block leaves the phone.** A position goes through `geo.rounded` before it is sent or kept, a photo through `photo.drawPhoto`, and a clip is written by `wav.encodeWav`. The microphone is let go of however a recording ends: everything after `getUserMedia` answers is inside the `try` whose `finally` stops its tracks, and a tap that is called off stops them at once, whatever the recorder is waiting for. Every promise the recorder starts is waited for (`context.resume()` with the samples), so none fails with nobody listening.
- **Asking again is `usePolled` with a cadence from `lib/cadence.ts`.** A view keeps its last answer on the screen when a request fails, and says that it may be out of date.

## Working on notifications

```python
from beacon.push import open_push

push = open_push(os.environ, engine, runs)  # in the server, request.app.state.push; always there, with this mode's file open
push.sends  # False with BEACON_PUSH=0 and with no BEACON_VAPID_SUBJECT: it then only deletes
push.work(engine.snapshot, now)  # one pass, answered in counts (`Pass`); the server makes one every 15 s
```

README "Notifications" says what a person is told. An address is kept by the routes in `beacon/api/push.py` and by nothing else: only on a server that sends (`push.sends`), only an address `checked` passed, and only with a permit `Subscriptions.permit` gave that is not None (it is None when as many are out as may be). `Subscriptions.put` called without a permit keeps what it is handed, which is for tests; do not call it so from code that serves a request. The rules:

- **A push carries no content.** It is a POST with no body, signed with the server's key. Do not add a payload, and so do not keep a browser's `p256dh` or `auth` key. The words a device shows are `notice_of(mode)`, handed to the app in `GET /api/push` and kept on the device (`keepNotice`) **before** the server is given the address, so no push arrives ahead of its words. They name no incident, say the decision is the investigator's and no authority's, tell nobody what to do, and on the mock store say first that the scenario is invented and a stand-in decided. A change to them reaches a device when it next syncs.
- **`ABOUT` names everything the file holds, and every lifetime.** A person reads it before they turn notifications on. When you add a column to `store.py`, or change `KEPT` or `SENT_KEPT`, change `ABOUT` in `notice.py` with it; `test_a_subscription_is_an_address_and_places_and_a_place_keeps_when_it_was_added` lists the columns. Do not add a column that says who or what the device is (a name, a browser, an address a request came from, a tap's id), and do not join a subscription to a tap. Say what the push service is sent and what it learns, never that it learns nothing.
- **What is kept is deleted on time whether or not anything is sent.** `Push.work` sweeps this mode's file and the other mode's on every pass, each by itself and before the incidents are read, on a server that sends none too, and `POST /api/push/unsubscribe` deletes on any server that has a file. Do not put a deletion behind `push.sends`, a key, a contact (`open_push` reads the contact only for a server that is to send), a reading of the incidents, or the other file's sweep. A file that could not be swept is counted (`Pass.unswept`) and logged.
- **An address is kept only with a permit, and a deletion takes permits away** (`Subscriptions.permit`, `put(..., permit=)`, `remove(endpoint, permits)`). It is what makes `204` final: a request to be notified that arrives after its sender's deletion was answered keeps nothing (`410`), and an older request cannot follow a newer one, because the request for a permit takes the earlier ones away (`revoke`). The permit is used up, and permits are withdrawn, in the same write as the row they guard: do not check a permit in one transaction and write in another, do not add a way to `put` from a route without one, and do not tie a permit to an address or a place in the file. In the app, a permit is noted in `out` before its request is sent, leaves `out` when the request is answered or refused with `PERMIT_SPENT`, and is named by `forgetHere` and by the next `permitPush`. `tell` asks `fence()` once more after the permit and the address are noted, immediately before `subscribePush`. **The service worker's deletion on `pushsubscriptionchange` names no permit and is best effort**: it reads nothing the app keeps, so do not describe it as final; the app's next sync is what mends a late request after it.
- **A send is claimed only for a subscription whose time is not over** (`claim` tests `renewed_at` as `_sweep` does), so that a sweep that failed sends nothing to what it would have deleted.
- **The subscriptions file has a shape number** (`_FORMAT` in `push/store.py`). When what a row holds changes, raise it, add the old number to `_EARLIER`, and say in `_EXPIRE` what becomes of the rows of the earlier shape: they are a device's, so they are deleted rather than kept in a shape nothing sweeps. `ABOUT` says a place's time is when *this server was first told of it*, and that a deletion happens when the server receives the request: do not write it as when the person saved the place, opened the app, or pressed a control, none of which the server knows.
- **`204` from the unsubscribe route means this mode's file does not hold the address, and nothing else does.** The route refuses a request for the other mode unread (`409`), and a busy or stopping server answers `503`. So does one with no file open: `open_push` opens this mode's file on every server, `BEACON_PUSH=0` included, so that no server says `204` without having looked; do not bring back a server that runs without the file. The app drops an address from `forget` only on `204` from the server of the address's own mode (`forgetHere`), writes an address to `told` before the server is given it, and says "deleted" only then (`Notifications`). Do not treat any other answer as a deletion, and do not make the app say that nothing can arrive: it says what the browser did and what the server answered.
- **A push is sent only to an address `endpoint.checked` passed**, at subscribe time, and `Notifier` sends through `beacon.ingest.http.fetch`, which follows no redirect. The address is a stranger's: do not widen `_SHAPE`, and add a host only for a browser's push service, with where its maker names it. An address is never logged, raised, or put in a request's path or query, by the server or the app (`unsubscribePush` sends it in the body).
- **Each mode is apart.** The mock store and the live store sign with a key each, and no setting names a key. In the app each mode has a service worker registration (`scopeOf(mode)`), a subscription, and words of its own, and `push-sw.js` takes its mode from its scope alone: do not make it read which mode is current from anything that is kept, and do not share one cache entry between modes. `on` in `lib/push.ts` is a mode, not a flag: a choice made for one mode is never carried to the other (`tell` retires it). On the mock store a push does go to a real push service, for the invented fire, with the invented scenario's words.
- **Who is due a push is code's, in one place** (`Notifier.notify`): an open incident that is no medical response, with a point that is its block's (`point_from == "blocks"`: never a 511 event's point, which a notification could not credit), whose crisis decision (`Runs.crisis`) still has a signal of a kind it cited, within `REACH_M` of a place this server was told of before the decision (`Place.added_at`, strictly: when the file first had the place under that address, not when the person saved it). Never from a model's word alone, and never for an incident without the investigator's decision. Change a condition with a test in `server/tests/test_push.py` that fails without it.
- **Sending is best effort, and the words say so.** A send is claimed (`Subscriptions.claim`, which also checks that the subscription still names the place) and settled by the push service's status alone (`read_body=False`). `again` (not reached, `429`, `5xx`) and a claim that was never settled (`CLAIM_STALE`) are tried again, `MAX_TRIES` in all; `404` and `410` delete the subscription. Do not call it exactly once anywhere, and do not rely on the notification's tag to hide a repeat. A pass has a budget, not a hard end: `PASS_SECONDS` from the entry of `Push.work` (`Notifier.deadline`), looked at before each subscription, before a claim, and again after it, with `SEND_SECONDS` for one push and `MAX_SENDS` in all; do not call it a wall-clock guarantee, since a write to the file and the reading of the incidents are not cut off. It passes over what needs no send without a write (`Subscriptions.tries`, read only for the incidents a push is due for), and keeps at most `MAX_TOKENS` signed tokens, one for each push service an hour (`TOKEN_REUSED`: Apple asks for no more).
- **A push names a contact, and a server with none sends none** (`subject_of`, `setup.NO_CONTACT`): Mozilla's push service requires one. A key is in its file whole or not at all (`vapid._keep`), and what is signed with is what was read back from the file.
- **Nothing is logged of a pass but its counts** (`_send_pushes` in `main.py`), and `/api/push` is in `PRIVATE_PATHS`. The routes read their own bodies, hold a place in `Admission` (`app.state.push_requests`) from before the body is read, and answer with fixed sentences.
- **In the app, `syncPush` is the only way the server is told anything**, under the browser's lock `beacon.push`. It reads the places with nothing waited for between the reading and the sending, and keeps no memory of what this tab told the server before. `turnOn`, `turnOff`, and a change of places only change what is wanted. Subscribe `usePushSync` to `onPushWanted`, never to `onPushChange`: a sync changes what views listen to, and one that listened to it would run for ever. **Turning off needs no server and waits for no sync**: `Notifications` shows the control whenever notifications are on, and `turnOff` writes a mark (`OFF_KEY`, a new one each time, never removed) outside the lock, from which on `read` says off in every tab. Everything else that is kept (`KEY`) is written only under the lock, with the mark it was read with (`seen`). `tell` asks `fence()` after everything it waits for on the way to giving the server an address, and after the server was given it; keep a fence after any new wait there. `turnOn` takes the mark when it is pressed, before the browser is asked anything, turns nothing on when the mark is another under the lock, and writes from that one reading (`writeWanted(change, now)`), so the `seen` it writes is never a later mark than the one it compared: do not read again between the comparison and the write. Every wait of a sync is inside `within` (`SYNC_MS` for one telling; `BROWSER_MS` in all, as one moment passed down, for what `letGo` asks of the browser, the deleting of the kept words included), which aborts the request's signal: do not add an `await` on the server, the browser, or its cache without it, and do not give each step a time of its own.
- **What the app does not know of the browser or the server it does not say.** `letGo` answers that the browser holds nothing only when the browser said so: a lookup that failed, an `unsubscribe` that did not answer, and an address it could not note down first all leave `held` set, and `HELD` says a notification already sent can still arrive. No address leaves `forget` but on its server's `204`: none is dropped to make room (`FORGET_MOST` stops a new address from being given instead, `Unanswered`). On a server that answers `enabled: false`, `tell` has it delete the address an earlier server was told, because such a server takes no change of places.
- **The sentences `Notifications` writes are about this device, this browser, and what the server answered** (on, blocked, held, not yet answered, answered that it deleted). What is kept, when a push is sent, and what a notification says are the server's (`about_text`, `notice`), shown as given.
- **The notifications' service worker is `web/public/push-sw.js`**, registered by the app at each mode's scope, apart from the generated worker (which does not precache it). It reads nothing a push holds, always shows a notification (a browser takes the permission away from a site whose push shows none), and on `pushsubscriptionchange` asks the server to delete the old address. It shares names with `lib/push.ts` (`NOTICE_CACHE`, `NOTICE_URL`, the scopes), which a test holds equal. Vite's dev server serves it, so notifications can be exercised under `pnpm dev` on `localhost` or over HTTPS.
- **In tests**, the server's are `server/tests/test_push.py`: `open_push({..., "BEACON_VAPID_SUBJECT": CONTACT}, ..., transport=httpx2.MockTransport(...))` stands where the push services are, and a pass is made by hand with `push.work(engine.snapshot, now)`. No test reaches a push service. The app's are `web/src/Push.test.tsx`, whose `browser()` stands where the registrations, the push managers, the permission, and the cache are, and whose `workerScope` runs `push-sw.js`.

## Working on the scale run

```sh
uv run --project server python scripts/scale_run.py --name NAME --day YYYY-MM-DD  # a stand-in on generated calls
```

README "Scale run" says what a run is, the three kinds, and the commands for a paid one. A run lives under `data/scale/<name>/` and its results are `results.json` there, read with `beacon.scale.results.read(Layout.under(env, name))`. The rules:

- **A sentence about a run says what the run is set up to do, and a number what was done.** `basis` is the same for a run that has heard nothing yet, so it says Ember "is paid for each one it is asked to hear", never that it was paid; a sentence about a stop names who was asked (`_stopped`, `_taps_stopped`: the stand-in is not called Ember, and nothing a stand-in did is called paid).
- **No number is shown bare.** A result is `basis_text`, then `caveats`, then numbers, each a `Number` with a `text` that code wrote: what was counted and what the count does not show. Whatever shows a result (the command line's `results.lines`, a route, a page, a document) shows `basis_text` first and each number's `text` beside the number. Do not copy a value out of `results.json` into anything without its sentence and the run's basis.
- **A stand-in's number is not a measurement of Ember, and a number from generated audio is not a measurement of radio.** A stand-in's run has `None` for cost, time per investigation, and lead time, with a sentence beginning "Not measured"; do not fill one in from a stand-in's zero cost or a script's speed. Generated calls are scored against the records they were generated from: the sentences say "a check of the pipeline, not a measure of accuracy", and a paid run of generated speech says "not of real radio". A new number gets a wording for each kind of run (the `meaning` each `_..._numbers` function in `results.py` picks by `generated` and `live`), and its test in `server/tests/test_scale_run.py`.
- **One invocation at a time, in one ledger.** The command holds `run.alone(env)`, an operating-system lock under `data/scale/`, for as long as it runs, a stand-in's too: do not add a path that begins, prepares, hears, or replays outside it. A paid run keeps the name of the ledger file it began to pay in (`pin_ledger`, by `EmberClient.ledger_file`: generation, device, inode) and is refused in another; every paying client is made before anything is heard, the taps' first, and the ledger is pinned with it, so a ledger replaced part of the way stops both. A spend is read only from a client that is already pinned, beside `EmberClient.ledger_replaced()` before the read and after it (`scope_spend`, `hearing_spend`): never from the ledger's path (`read_scope_spend`), which can be another file by the time a client is made. The command asks `ledger_replaced` of every client once more when everything is done. A run that saw its ledger replaced says `LEDGER_REPLACED`, reports no cost of hearing, and is not gone on with (`lose_ledger`): never tell the operator to give the command again after that.
- **A run is one kind for good** (`Settings` in `run.json`; `begin` refuses a mismatch). Do not add a way to go on with a run under other settings: its rows would be of two kinds that nothing tells apart afterwards.
- **A tone is never sent to a paid Ember, and a recording is never heard by a stand-in.** Recordings need `BEACON_RECORDINGS_PERMITTED=1`, are read where they lie, and get rows in a live store of the run's own; generated calls are marked `BEACON-GENERATED` and their rows are `mock` whoever hears them. Beacon requests no audio from OpenMHz, Broadcastify, or anyone else: do not add a downloader.
- **Nothing is paid for twice, over every invocation.** Hearing is `RecordedRadio(backlog=True, scope=hearing_scope(settings))`, which claims a call before Ember is asked; a replayed tap is claimed in the run's `Runs` file before `investigate_tap`, and that claim is never given up. Every claim of a replay has one stamp (`taps._CLAIMED_AT`), because `Runs.claim` deletes what is a day older than the stamp it is given: do not stamp a replay's claim with the time. **A hold is the whole run's**: the command asks `taps.held_for` before it has anything heard, and while that hold is on it asks nothing and leaves `results.json` as it was. **The hearing is closed when the replay first begins** (`close_hearing`, before the first claim): from then on `hear` is not called for the run, so every tap is answered against one evidence; do not add a way to hear more into a run whose taps have answers. The replay keeps the pollers' holds through `PaidDesk` (`check` before a claim, `hold_after` and `count_answer` after a run, saved with the run by `Runs.write(run, state=...)`), and does not begin a tap its scope could cut short (`_short`). A claim with no row is counted (`EvidenceStore.claimed_without_row`) and not asked about again. Taps are replayed only after the hearing is complete, and a run is `complete` only when its replay did not stop and no planned tap is waiting (`heard_complete` is the hearing alone). `complete` means nothing is left for the same command to do, not that every call has a row or every tap an answer: say it that way. Results are written inside the lock. Do not add a "retry what failed" option: a failed call may have been billed.
- **The caps are the build plan's**: `RADIO_BUDGET_NANOUSD` ($1.25 for hearing) and `TAPS_BUDGET_NANOUSD` ($0.50, scope `scale:taps`). Hearing has a scope for each kind of audio, `scale:radio` for recordings and `scale:speech` for generated speech, so that a cost read from the ledger is one kind's; `radio_ember` gives a run's scope the budget less what the other holds, which is what holds the two to one cap: it reads the other's spend from the pinned client it is made `beside` and refuses a hearing client that is on another file. A run whose hearing is closed makes no hearing client and is not refused for a hearing budget that is used up. Do not pay for both kinds under one label, and do not give each a whole budget. An option lowers a cap and cannot raise it; do not raise the constants, and do not give a run a ledger of its own: every call, a stand-in's too, is booked in the one ledger under the data directory.
- **Only an answer is counted as an answer.** A run that was cut short, refused, or ended in no form is kept as "unconfirmed" and is in `taps_unanswered`: `_answered` in `results.py` decides, and the counts of answers, the cost per investigation, and its time are over answered runs only.
- **A replayed tap is not a tap.** It is never stored as a `tap` row, in the run's store or the server's, so it adds to no incident's count and is no evidence for another. The run's stores are its own files: a run never opens `data/evidence/` or `data/investigate/`.
- **DataSF's medical calls are kept as medical, DataSF's call number, crews, intersection, and times.** Generated medical calls go on `generate.EMS_TALKGROUP`, which a run hears as EMS-only, and `generate._words` says everything a form holds, so that calls which sound the same say the same: keep both when you change what is generated. `datasf.COLUMNS` is everything that is requested: do not add the disposition, the priority, the call type group, or any other column that says how a patient was. A medical record is matched only to a medical response, and no tap is planned at one. A row that names no call is counted as a row (`Unread.rows`), never as a call. Downloaded records and lists stay under `data/`; none is committed, and the tests' day (`server/tests/scale_day.py`) is invented.
- **The matching rule is code, stated beside the result** (`score.py`'s docstring, `NOT_CHECKED`). A sentence about a count says what the rule paired and never why: "found" is a fit by the rule, "taken to be inside" is a guess, and a further incident "fits and was paired with none". Change `fits`, `EARLY`, `LATE`, `OPEN_FOR`, or `NEAR_M` with a test that fails without the change, and change README's "How a call is matched" with it. Do not tune them to a run's numbers.
- **The incidents that are scored are read from the run's rows, not from DataSF's times** (`score.read_incidents`): at moments from the first radio row to the last, because the engine looks back twelve hours, and readings that share a row, or are joined by readings between them that do, are one incident. Do not bound the reading by the records, and do not count a reading again because it shares no row with the one that was kept. An answer names its incident by the id it had at the tap's moment, which can be any of the incident's rows' (`Reading.kept_as` holds one for every row): do not compare an answer's id with the ids of the readings alone. A plan holds each question once (`plan` leaves out a tap whose id it already has): do not count, replay, or price one investigation twice. Replayed taps are spread over the whole day's calls, the first and the last among them (`taps.plan`), and a tap "away from every call" is away from what DataSF records and no more: the last time a record gives is the latest of its dispatch, a unit on scene, and its last unit available (`taps._last_recorded`), which the number's sentence says.
- **What a run fetched or generated is written whole**: to a `.part` file that then takes its place (`run._write`, `lists._write_whole`), with the file a later invocation looks for (`blocks.csv`, `script.json`) written last.
- **Errors are fixed sentences** (`ScaleError`): nothing of a call, a recording's path, or a source's reply. DataSF is asked through `beacon.ingest.http.fetch`.
- **In tests**, `tests/scale_day.py` has `call(...)`, which makes DataSF rows of an invented day, and `DataSf`, which stands where data.sf.gov is; `main(argv, env, out, http, paid)` runs the command over it, with `paid` making the live client over `MetaApi` for a paid run. No test asks DataSF or Meta.

## Conventions

- Match the code that is there: a new route copies the shape of `server/beacon/api/health.py` and its test; a new web API module copies `web/src/api/health.ts` and uses `fetchJson`.
- A route that fails says why in a fixed sentence in `detail`, and never repeats what the client sent (see `_validation_error` in `server/beacon/main.py`): a tap can carry a location, a photo, or a microphone clip. A route that takes something private reads its body itself, with `read_body` in `server/beacon/api/body.py`, as `api/taps.py` and `api/places.py` do, and its path is added to `PRIVATE_PATHS` in `main.py`, which keeps it out of uvicorn's access log and FastAPI's telemetry. Do not add another logger, tracer, or middleware that records requests without leaving those paths out. Work on what a stranger sent is bounded before it is done: admission and rate limits first, decoding after, and decoding of media only by the confined ffmpeg (`beacon.radio.audio.Ffmpeg`), never by a library in Beacon's own process. `Ffmpeg` raises `ConversionUnavailable` when the host could not run it just then, which says nothing about the file: answer `503` or try again later, and never count the file out for it. The server marks itself not dumpable before it serves a request (`forbid_core_dumps` in the lifespan), and does not start when that fails on a host with a core collector; a program it starts does not inherit the mark, so one that is handed private bytes is started only where `core_dump_problem()` is None. `TapMedia` holds a lock on its directory, so build one per data directory per process, and `close()` it.
- Deterministic code decides and is tested; Ember writes and judges. Keep model calls out of code that groups, measures, or filters.
- Comments say why, in plain sentences. Test names are sentences that state the behavior.
