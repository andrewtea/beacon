# Beacon design decisions and tradeoffs

The design calls made while building Beacon, and what each one cost. The agents that built Beacon were asked to make their own judgment calls and to write the tradeoffs down when the building was done; this is that record. [README.md](../README.md) and [AGENTS.md](../AGENTS.md) say how the result works. This file says why.

Beacon was built in six phases, from Nov 26 to Nov 28, 2026, through 24 pull requests, each reviewed by openai/gpt-6.2-astra before it merged. Each phase has a section below, written by the agent that built it when the phase's last pull request merged. For each decision a section says what was chosen, what was rejected, why, and what would make us revisit it, and it marks what ran on mock data or a stand-in and what a real key or source would change.

**A section describes Beacon as it stood when its phase ended, and a later section supersedes an earlier one.** The sections are not corrected where they stand. These are the things an earlier section says that are most likely to mislead. The list is not complete: [README.md](../README.md) and the code say what is so now.

- The OpenSky and OpenMHz pollers of Phase 2 were removed in Phase 5. Aircraft come from adsb.lol, and radio is recorded calls on the machine Beacon runs on.
- "No real Ember call has been made" (Phases 1 to 4) stopped being true on Nov 27, 2026, late in Phase 5, when a key arrived.
- The audio token rate that Phase 1 could not measure was measured in Phase 5, on generated tones.
- Phase 2 says that deleting the mock store restarts the story. That holds only for a store a stand-in told. A store Muse Ember worked on is never deleted: it is set aside whole, because it holds the claims on what was paid for (Phase 6).
- Phase 4 says the words of a push on the mock store say that a stand-in decided. They now say first that the incident is invented, and do not say who decided.
- Phase 5 says the server has never run with a live Ember and that its desks have only run on stand-ins. In Phase 6 a server that is not public ran with Muse Ember doing the model's work, on the invented story's evidence only. No server has run its paying pollers on the live store.

The phases follow a build plan that is an Amp artifact only its owner can open ([Beacon build plan](https://ampcode.com/artifacts/beacon-build-plan-83629289-729b-471f-9a27-798e8b3ee734)). Where a decision departs from the plan, its section says what the plan said.

## The decisions that shape Beacon most

Each is argued in the section of the phase named beside it.

| Decision | What it costs | Phase |
| --- | --- | --- |
| Nothing a radio call said is kept as text. Ember fills in a form of fixed tags, and a call's audio is never written to disk. | Detail that fits no tag is lost. An answer about radio audio is never recorded, so it cannot be replayed: a run or a telling begun anew pays to hear its calls again. | 2 |
| No sentence a model wrote is shown in Beacon's voice. Ember picks points from closed lists, and code checks each against its rows and writes the words. | Stories are plain, and the agent trace shows fixed sentences, not the model's own reasoning. | 3 |
| Incidents are derived from the evidence and never stored. The engine works them out again whenever its in-memory copy is more than a few seconds old. | An incident's id is its store's own and can change when a call is regrouped. | 3 |
| One ledger with a $3.00 stop. A call is reserved at its most before it is sent, and an item is claimed before it is paid for, for good, so a store or a run that goes on does not ask about a claimed item again. | The ledger is an upper bound. A claimed item whose process dies before its row is written is lost, and may have been charged. A store or a telling begun anew has none of the claims and pays again. | 1 and 2 |
| Mock and live evidence are two stores. A poller takes a row's origin from its HTTP client and is handed none, the live store refuses a row a stand-in had a part in, and a stand-in's output is marked wherever it is shown. | Naming any live source turns the invented scenario off for all of them. | 2 and 4 |
| Ember is never told where a tap is or when it came. Its tools look from the tap and answer with ids, counts, and tags. | Ember reasons over less than a person would. | 3 |
| Crisis mode is the investigator's decision, checked by code, and made only when a tap near an incident is investigated. | An incident nobody taps near is never in crisis mode, and so brings no notification. | 3 |
| One button, and the answer to one tap is the page. There is no feed of incidents and no map of the city. | Somebody who taps nowhere sees nothing of an incident except through a saved place. | 4 |
| A saved place's name stays on the device, and a check of a place stores nothing on the server. Notifications are the exception, for a device that opts in: the server then keeps the push address with up to five places rounded to about a block. A push carries no content. | Places do not follow a person to another device, and a notification cannot say which incident it is about. For a device that opted in, the address and its places are kept for 30 days from the last renewal, and a send ties the address to an incident for up to 48 hours. | 4 |
| Beacon asks nobody for radio audio. OpenMHz and Broadcastify are refused in code, and radio is recorded calls on the machine Beacon runs on. | Beacon has heard no real radio, so no number it reports is about real radio. | 5 |
| The paid scale run is of a sample: a day's first 100 dispatched calls, generated as synthesized speech. | A day's first 100 calls need not be like the rest of it: 66 of them were medical. The speech is clean and synthetic, so the run's costs and times are Muse Ember's, and its accuracy is a check of the pipeline with a model in it, not a measurement of Beacon. | 5 |
| The public deployment takes nothing of a visitor's own, and runs on stand-ins with no key. | Judges cannot try their own microphone, camera, location, or a notification on the public URL, and no answer shown there is Muse Ember's. | 5 |
| For the video, Muse Ember does the model's work on the invented story, in the mock store, and no clock is ever held or moved. | A telling costs about two cents and cannot be shown again without paying. A missed moment is a new telling. | 6 |

## Where Beacon stood when the building ended

As of `38bfbd7`, on Nov 28, 2026:

- **Every incident Beacon has shown is invented.** The fire on the 400 block of Hayes St is made up, and its notices are invented PDFs. Its radio calls are generated audio: tones where a stand-in "hears" them by lookup, and, where Muse Ember hears them, synthesized speech of invented words, with generated noise for the two calls in which nothing is said.
- **Muse Ember has been asked only about invented or generated material**: 637 paid requests for $0.119825 of the $3.00 stop, every one answered, in one ledger. [What the story costs with Ember](#what-the-story-costs-with-ember) has the parts.
- **Never done:** hearing a recording of real radio, reading a real notice, polling 511 with a token, delivering a notification to a phone, taking a clip or a photo from a phone, meeting a `429` from Meta, and an investigation that takes all four of its rounds.

The first four were put to Andrew through the thread that coordinated the phases, and none had an answer when this file was written. The last two are follow-ups the phase sections name, and nobody has put them to him.

1. **May the server the video is filmed from take his own phone's location, microphone, camera, saved places, and push address?** That server is behind an Amp orb portal, which opens for everybody its thread is shared with, so the question came with a second: that he confirm the thread stays private. The server takes only the invented scenario's two places today, because the reviewer would not clear the option on an assumption (Phase 6, PR #22). A yes covers his phone and that portal and nothing else, and is one small pull request that names his approval. Without it, a video filmed from that server shows no real microphone, camera, or notification. With it, each still has to be tried and seen before the run sheet scripts it.
2. **Will there be recordings of real radio that Beacon has the right to use?** The code reads recorded calls in trunk-recorder's layout, on the machine Beacon runs on, once the operator says Beacon may (`BEACON_RECORDINGS_PERMITTED=1`). Nothing has been paid to hear recorded radio (`scale:radio` holds nothing). The scale run's $1.25 for hearing is shared with generated speech, which holds $0.034488 of it, so $1.215512 of it was left when this file was written (Phase 5).
3. **Should the public URL take a visitor's own location, clip, photo, and push address?** That is `BEACON_FRONT_END=verified`, which is the operator's word that the host keeps the private paths out of its records. Nobody has checked what Amp's and Google's front ends write down (Phase 5, PR #19).
4. **Should the agent trace show Muse Ember's own reasoning?** It shows fixed sentences written by code, because an investigation keeps none of the model's free-form reasoning (Phase 3, PR #9). A redacted, labeled excerpt would be a new design and a privacy decision.
5. **Getting in touch with adsb.lol** before Beacon is run for the public, as an older page of theirs asks (Phase 5, PR #14).
6. **Whether Muse Ember's telling should stay up through judging**, Dec 3 to 6. Today it runs only while somebody films from it. Keeping it up means a private Box with the key and the paid data directory moved there once (Phase 6, PR #22).

## Phase 1: scaffold and Ember client

Landed on `main` at `ddb81c7` through [PR #1](https://github.com/andrewtea/beacon/pull/1) (scaffold) and [PR #2](https://github.com/andrewtea/beacon/pull/2) (Ember client). The repository's `README.md` and `AGENTS.md` describe how the result works; this section records why.

### What runs on mocks

- **No real Ember call has been made.** There is no Meta Model API key. The client is tested through the real OpenAI SDK with its HTTP transport replaced by a mock of the API, so URLs, headers, and bodies are the ones the SDK sends, and nothing has been checked against an answer of Ember's.
- **Request shapes, limits, and prices come from Meta's documentation**, read on Nov 26, 2026: `input_audio {data, format}` with WAV or MP3, a largest output of 524,288 tokens, `POST /v1/responses/input_tokens` for counting, and the per-token rates in `pricing.py`. A real key would confirm or correct each of them.
- **The audio token rate is unmeasured.** The plan's 25 to 30 input tokens per second is still a guess. `scripts/measure_audio_rate.py` has only run against a mock that billed by clip length, where it recovered the mock's rate. With a key it makes ten paid calls under a $0.05 budget.
- **Two billing assumptions are unverified**: that the token-count endpoint is not billed, and that an error response may be billed. The first comes from Meta's documentation; the second is the cautious reading of its silence.
- **The web app is a shell.** It shows whether the server is reachable and nothing else.

### Scaffold

- **Stack and layout taken from Forte.** Chose React, Vite, TypeScript, and `vite-plugin-pwa` with pnpm, Vitest, oxlint, and Prettier for `web/`, and Python 3.12, FastAPI, uv, ruff, and pytest for `server/`, as the plan says to reuse Forte. Rejected: choosing a stack afresh, which was not evaluated. Why: Andrew wrote both projects and the plan names the reuse. Revisit if a later phase needs something this stack lacks, such as a background worker for ingest.
- **The shell is dark only and has no "What's that?" button.** Rejected: a disabled button, which would be a control that does nothing. Revisit in Phase 4, which builds the app.
- **The server reads settings from the process environment and does not load `.env`.** Rejected: loading a `.env` file in code. Why: after review, the two spending settings must come from the process and from nothing a caller can substitute, and one rule for all settings is simpler than two. Revisit if a deployment needs a file; load it into the environment before the process starts, not in code.
- **Tests are kept offline by the missing key, with a socket patch as a backstop.** `conftest.py` removes `MODEL_API_KEY`, sets `REPLAY=1`, gives each test its own data directory, and patches `socket.connect` and `connect_ex`. Rejected: calling the patch a sandbox, which the first draft of the docs did. It does not cover DNS, subprocesses, or native sockets. Revisit if a dependency opens sockets outside Python's `socket` module.
- **A validation error never repeats what the client sent.** Rejected: FastAPI's default 422 body, which echoes the input. Why: a tap will carry a location, a photo, or a microphone clip. Revisit if the app needs field-level errors; add field names, never values.
- **`scripts/check` is the one definition of "passing".** CI runs it, and it sets `REPLAY=1` and unsets the key itself. Rejected: separate CI steps that could drift from the local check.

### Ember client

- **Ported Forte's client; did not write a new one.** Changes from Forte: the ledger label is `task` (not `tier`), the schema has `scope` and a row `token` from the start with no migration, and the stop is configured (below). Rejected: a fresh client. Why: Forte's already had the reserve-and-settle ledger, replay cache, pacing, and scopes with tests. Revisit when the first real call shows a request shape is wrong.
- **The stop is $3.00 of live spend in Beacon's own ledger.** `EMBER_STOP_USD` defaults to `3.00`. This is the recorded assumption for the plan's "$3 above today's Usage page total": the ledger counts only Beacon's calls, so $3.00 in the ledger is $3 above whatever the page showed, and the absolute number is not needed. Rejected: a default expressed as an absolute Usage-page total, which nobody has read. Revisit once Andrew reads the page.
- **Earlier spend has no default.** `EMBER_SPENT_BEFORE_USD` must be set before any client that can spend is built, `0` is accepted, and it plus the stop may not pass a $9.00 ceiling. It is the total for every model, not the Ember filter. Rejected: a default of $0.00, which was my first choice. Review showed that an account that had already spent $8.00 would be allowed $3.00 more. Rejected: Forte's fixed $6.00 stop. Revisit the $1.00 margin under the $10.00 credit after the ledger has been compared with the Usage page a few times.
- **Both spending settings are read from `os.environ` by every paying client.** `stop_nanousd` can lower the stop for one client and cannot raise it. Rejected: a `stop` argument and, later, an `env` mapping on `EmberClient.live`; review showed each let code replace the operator's stop. Cost: changing either setting needs every paying process restarted.
- **A call is reserved at its most before it is sent, and an unanswered call stays booked at that amount.** The check and the insert share one SQLite transaction. Rejected: booking after the answer, which lets parallel calls pass the stop together. Rejected: releasing the reservation on an error response, because Meta does not say which errors are free. Cost: the ledger is an upper bound, and errors use up the stop on paper. Revisit when the Usage page shows how errors are billed.
- **Input tokens are counted by Meta before every live call, and the SDK's retries are off.** Calls over 150,000 input tokens are refused, and `max_output_tokens` must be 16 to 524,288. Rejected: estimating input size locally, because audio's token rate is the unknown this phase could not measure. Rejected: SDK retries, because a resent request may be billed again under one reservation. Cost: every live call is two requests, and the input is sent to Meta twice. Revisit if the count turns out to be billed, or the rate limit binds in the scale run.
- **Replay is the default mode, keyed by a SHA-256 of the request.** Media is replaced by a length and a digest in everything written to disk. Rejected: live by default.
- **Every call must say whether it is `sensitive`.** A sensitive call leaves its accounting, the request's hash, and field sizes in the ledger and trace. It is never recorded or replayed, and it fails only with the client's own fixed-text errors with nothing chained under them. Rejected: redacting only media, which leaves the words of an EMS extraction on disk. Rejected: a default for the flag, since either value would be wrong silently. Rejected: per-field digests, because a short text such as a name can be guessed from its digest. Rejected: keeping the response id or model for sensitive calls. Cost: anything built on EMS traffic is paid for on every run and cannot run in replay-only mode, so tests and keyless development use `EmberClient.fake`. Revisit in Phase 5 if paying again for EMS calls strains the budget; recording them would need a design for storing them safely.
- **A ledger is recognised by its generation and by which file is at the path, and a row by generation, id, and a random token.** A deleted, replaced, or renamed-in ledger stops a running client's paid calls. Rejected: generation alone, which an older copy put back by rename shares. Rejected: another check to close the gap between the last check and the send, which review agreed cannot be closed that way. Known limits: a ledger rolled back in place is undetectable, and a file replaced while a paid request is out needs the Usage page compared with the ledger by hand. Revisit if the ledger moves to storage with snapshots, or off SQLite.
- **`BEACON_DATA_DIR` must be absolute.** Rejected: resolving a relative path against the repository root, which review offered as an alternative. Why: a refusal cannot be misread, and two ledgers would be two $3.00 stops.
- **Money is whole nano-dollars, and dollar settings are parsed digit by digit.** Rejected: `Decimal`, which rounded `8.99…9` to exactly $9 at its working precision, and floats.
- **The audio measurement fits a line through ten clips of known length and sends generated tones by default.** The slope is the rate and the intercept is the per-request overhead. Rejected: tokens divided by seconds per clip, which the overhead inflates. Rejected: real radio clips by default, because the repository holds no audio. `--clips DIR` sends WAV files as sensitive calls. Revisit if real calls do not fall on a line, which would mean Ember does not bill audio by length and only real recordings give the number.
- **`Pacer` and `SpendScope` are kept from Forte though nothing uses them yet.** Rejected: dropping them until needed. Why: per-tap caps and the scale run need them, and they came with tests. Revisit if Phase 5 does not use the pacer.
- **No route builds an Ember client.** Phase 2 builds the first one, through `EmberClient.from_env`.

## Phase 2: ingest

Landed on `main` at `40481b1` through four pull requests: [PR #3](https://github.com/andrewtea/beacon/pull/3) (evidence store, the NWS, OpenSky and 511 pollers, and the mock scenario), [PR #4](https://github.com/andrewtea/beacon/pull/4) (dispatch radio and `extract_transmission`), [PR #5](https://github.com/andrewtea/beacon/pull/5) (the tap route with its photo and clip), and [PR #6](https://github.com/andrewtea/beacon/pull/6) (`read_notice` and the notice poller). The plan suggested three; radio got a PR of its own because it is the first code that spends money and stores what people said. The repository's `README.md` and `AGENTS.md` describe how the result works; this section records why.

### What runs on mocks

- **Every source runs on the invented scenario by default.** With `BEACON_LIVE_SOURCES` unset, the real pollers are fed by `beacon.scenario` through a mock HTTP transport, and every row is stored as `origin="mock"` in `data/evidence/mock.sqlite3`. A real key or permission changes configuration only: naming a source in `BEACON_LIVE_SOURCES` with its settings runs the same poller against the network and writes to `live.sqlite3`.
- **NWS** needs no key. An early version of its poller was run once against the real API; nothing since has been.
- **511** has run only against mocked HTTP, because there is no token. Its response shape and pagination come from 511's documentation. A token (`BEACON_511_API_KEY`) would confirm or correct `parse_events`, above all the `pagination` fields the poller is strict about.
- **OpenSky** has run only against mocked HTTP and may not be pointed at the real API: its terms require a written license for a running service, which nobody has asked for. `BEACON_OPENSKY_PERMITTED=1` is how an operator says the license exists.
- **OpenMHz has never been asked anything.** Its API shapes are read from the source of the server it runs and are unverified. Unknown until a real answer is seen: the ordering of `/calls/newer`, how many calls an answer holds (`PAGE_SIZE = None`, so every live poll that ends in a call reports `partial`), the host its audio is served from, and San Francisco's talkgroup numbers. Permission (`BEACON_OPENMHZ_PERMITTED=1`) is needed first.
- **No real Ember call has been made.** Radio calls and notices are "heard" and "read" by stand-ins that look the audio or the PDF up by digest and return the story's form, so those rows are `model="fake"`. A key would show how well Ember hears a call and reads a notice, whether `input_audio` and `input_file` are accepted as sent, and what each costs. Nothing has been measured.
- **No real notices feed exists.** The notice poller reads a JSON Feed with PDF attachments. No San Francisco agency is known to publish one, so going live needs a feed first.
- **No list of San Francisco streets or fire units is in the repository.** Real radio rows name a street or a unit only from files an operator supplies; without them a real radio row has no place.
- **Mock data is invented.** The radio calls are generated tones, the notices are PDFs written by `beacon/scenario/pdf.py`, and every text a person could read says "Invented for Beacon's mock scenario". The story is a three-alarm fire on the 400 block of Hayes St that runs 95 minutes and is played for 105: twenty radio calls, a circling helicopter, a shelter-in-place alert that is issued, narrowed and dropped, a 511 closure that widens and stops being listed, an evacuation order, its all-clear, and a press release.

### What ingest guarantees about private details

The plan puts the full redaction pass in Phase 3. This is what Phase 2 decided ingest must already guarantee about what reaches the disk, so that Phase 3 has nothing to take back out.

- **Nothing a radio call said is stored as text, and its audio is never written to disk.** Chose a closed vocabulary: Ember fills in a form, and a row keeps tags from fixed lists, a hundred block, and unit ids and street names that are on a list (`beacon.radio.Known`). Rejected: storing a transcript and redacting it in Phase 3, which leaves names and patient details on disk between the two phases and in every backup. Rejected: keeping anything that merely has the shape of a unit or a street; review showed `BP 180` and `Ann 72` pass as units and a spelled-out house number passes as a street. Cost: detail that does not fit a tag is lost, and a row is only as good as Ember's hearing. Known limits: a listed name is kept whatever Ember meant by it (`M72` could be a man of 72), and the hundred block is a number Ember gave. Revisit when real calls show which tags are missing; add a tag, never a free-text field.
- **EMS traffic is "medical response", its crews and its block.** Status, details and alarm level are dropped for a call Ember hears as medical and for every call on a talkgroup the operator marks EMS-only (`BEACON_OPENMHZ_EMS_TALKGROUPS`), whatever Ember made of it. Rejected: relying on Ember's category alone, which a mishearing defeats. Revisit if the EMS-only list turns out to hide fire traffic that shares those talkgroups.
- **Every Ember call on radio audio or a notice is `sensitive=True`.** The ledger and trace hold the call's cost and none of its content, so the call is paid for every time and cannot be replayed. Rejected: recording them for replay, which would put what was said on disk. Cost: Phase 5 pays again for every call it re-runs.
- **A tap keeps where to about a block, when by the server's clock, and nothing about who.** The position is rounded to three decimals before it is stored, no header is read, and the tap route is left out of the access log and telemetry. Rejected: storing the precise position for better matching, and a per-sender rate limit, which needs an address kept at least in memory. Cost: the rate limit is global, so one sender can use up a minute for everybody. Revisit if abuse shows up in the demo; a short-lived salted hash of the address is the next step, and it is a privacy decision for Andrew.
- **A notice is kept as Ember's reading of it, in words only when it is a notice to the public.** See Notices below.
- **Errors and logs repeat nothing a source or a person sent.** Every such error is a fixed sentence raised with `raise_bare`, which also drops the exception the caller was handling. Rejected: `raise ... from None`, which review showed keeps the reply in `__context__`.

### Evidence store

- **One SQLite table of immutable rows, one row per thing a source said.** A revision is a new row under a new reference. Rejected: updating rows in place, which loses what was known when. Cost: `search` returns history, and a reader has to work out what is in force; `AGENTS.md` says how. Revisit if Phase 3's "what is in force" lookups are slow or error-prone; a derived view is the fix, not mutable rows.
- **Two store files, mock and live, and the live store refuses any row a stand-in had a part in.** Rejected: one store with a flag, where a single unfiltered query shows invented data as real. Consequence: naming any source in `BEACON_LIVE_SOURCES` turns the mock scenario off for all of them. Revisit for the Phase 6 demo, which replays a recorded incident and may want live alerts beside it; that needs a third kind of origin, not a relaxed check.
- **A row's origin comes from the HTTP client and cannot be set.** `SourceHttp` built with a transport is `mock`; a poller reads `origin` from it. Rejected: an `origin` argument, then a writable attribute. Each let a test or caller label a stand-in's answer as live; this took four review rounds to close, including the case where an inferred "no longer listed" row lost its stand-in provenance.
- **Claims sit beside the rows.** A poller that pays per item claims the item (`EvidenceStore.claim`) before it pays, and a claim is for good. Rejected: checkpointing after the answer, which review showed pays twice after a failed write or a crash. Cost: an item whose process dies between the answer and the row is paid for and lost. Revisit if lost items are common in the scale run; a two-phase claim that records the ledger reference would allow recovery.
- **WAL mode, with `close()` that makes a waiting write give up.** Chosen so reading never waits for a write and shutdown cannot leave a writer running. Cost: three files per store, and backups need SQLite's `.backup`.

### Pollers for NWS, OpenSky and 511

- **Disappearing from a listing is not an official ending.** After two complete answers without an item, the poller stores a `not_listed` row at `medium` confidence, and a `listed_again` row if it returns. Rejected: an `official` "cleared" row, which would be Beacon announcing an all-clear no authority gave. An NWS `Cancel` stays `official`. Revisit if two misses turn out too slow or too jumpy against real feeds.
- **An answer that cannot be read in full counts no miss.** Unknown statuses, unclear 511 pagination and the page cap make a poll `partial`, which is shown in `GET /api/sources`. Rejected: treating a short or odd answer as complete, which produced false clears in review.
- **511 is asked for events in effect now and keeps the schedule as sent**, at one request per two minutes however many pages a poll needs. Rejected: a fixed interval, which at four pages is twice 511's quota.
- **OpenSky keeps aircraft that are airborne below 3,000 m.** Rejected: every aircraft in the box, most of which nobody on the street notices. Revisit with real data: medical and news helicopters may need a callsign list.
- **OpenSky is refused without `BEACON_OPENSKY_PERMITTED=1`.** Rejected: treating an account as permission. The plan's fallback to airplanes.live is not built; the evidence kind `aircraft` allows a second source.
- **One HTTP path for every poller**: a body cap applied while unpacking gzip, no redirects, a 60-second deadline for the whole exchange, and `Retry-After` honored up to a week. Rejected: the library's own decompression and timeouts, which bound neither memory nor total time.
- **The pollers run on one thread inside the server process.** Rejected: a separate worker process, which the hackathon does not need and which would be a second process on the ledger. Cost: run one server worker. Revisit if a poll's latency ever delays another's; radio's paid calls are the likely cause.

### Mock scenario

- **The scenario stands where the network is, and the real pollers run on it.** Rejected: writing rows straight into the store, which would leave parsers, paging and failure handling untested and need a second code path for live. Cost: the scenario has to serve each source's wire format.
- **The story starts twenty minutes before a mock store is first opened and plays in real time**, on a held clock in ten-second steps, checkpointed after each complete step. Rejected: an instant dump of the whole story, which gives Phase 3 and the app nothing that changes while they watch. Deleting the mock store restarts it. Revisit in Phase 6: the demo replay will want to start, pause and scrub the story, which `Ingest.catch_up` and the held clock already allow.

### Radio

- **The poller hears only named talkgroups, at most 20 calls every 30 seconds, each between one second and two minutes long, under a budget of its own** (`BEACON_OPENMHZ_BUDGET_USD`, scope `ingest:openmhz`, no default). Rejected: a default budget; every call is paid for, so the operator names the number. Revisit after the audio rate is measured; the caps were chosen without knowing what a call costs.
- **Trouble with Ember holds the poller for ten minutes, kept in the store.** The same after three answers in a row that were no form, and for the life of the process after a replaced ledger. Rejected: retrying, because a retry is a second paid request under one claim; the radio client therefore has no pacer. Cost: calls older than fifteen minutes when the hold ends are never heard.
- **Every call is decoded before it is sent, in memory, by ffmpeg confined by bubblewrap.** Ember gets a WAV Beacon made, so the length paid for is known. Rejected: sending the file as it arrived, trusting the listing's length. Rejected: a decoding library inside Beacon's process, which puts a parser of untrusted audio where the ledger and the keys are. Cost: real radio needs Linux, ffmpeg and bubblewrap, and a host that hands core dumps to no collector. Swap is left to the operator.
- **A poll says `partial` when it cannot prove it saw every call.** Nothing is concluded from a page's length unless the page size is known, and for OpenMHz it is not. Rejected: guessing the size from the fullest answer seen, which hid a call when answers shrank. Cost: every live poll that ends in a call reports `partial` until `PAGE_SIZE` is set from a real answer.
- **Shutting down admits no new paid call and waits up to about two minutes for one that is out.** Rejected: promising that nothing is sent after `stop` returns, which review showed the client cannot keep; only a `stop` that answers True is complete.
- **A radio row has a place in words and no point.** Nothing in ingest geocodes. Phase 3 needs a block-to-point lookup, or it groups radio with located evidence by street name and time.

### Taps

- **JSON with base64, not multipart.** Chosen for one body cap, no new dependency, and a body the route reads itself so nothing echoes it in an error. Cost: a third more bytes on the wire.
- **A photo is kept only as a new JPEG Beacon drew from it; a clip only as its samples.** The photo is cut to the segments a decoder needs, decoded strictly by the confined ffmpeg, scaled to 2048 pixels and re-encoded, so no byte of the upload is copied. Rejected: stripping Exif with a library and keeping the rest, which leaves thumbnails, comments, trailing data and a parser in Beacon's process. Rejected: converting colours to sRGB before dropping the profile, which needs more code parsing the profile inside the sandbox; a wide-gamut photo comes out slightly flat. Cost: a server without the confined ffmpeg, or on a host with a core collector, takes taps without photos (`503`).
- **Clips are WAV only.** Rejected: accepting what a browser's recorder writes (WebM, MP4), which would need a decoder for uploads. Cost: the Phase 4 app has to record samples and write the WAV itself.
- **Media is kept for one hour, under a 500 MB cap, in files beside the store.** The hour is from the plan's default that a photo is evidence for one tap. Rejected: keeping media in SQLite, and keeping it until the incident closes. Revisit if the investigator needs a photo after the hour; keep what was concluded from it, not the file.
- **A tap is `origin="live"` in the mock store too.** A person's tap is nobody's stand-in; the receipt's `mode` says which store it went to. Rejected: marking it `mock`, which would make a real person's tap a fabrication.
- **Order of work: shape and place, then the rate limit, then decoding.** A tap from outside San Francisco is refused before anything is decoded. Limits: 8 at once, 120 a minute for everybody, 10 MB, 20 seconds.
- **The server marks itself not dumpable before it serves a request, and does not start where that fails on a host with a core collector.** Rejected: a warning, then a route that answers `503`; review showed the HTTP server holds the request body before any route runs. Cost: on such a host the whole server is down, not only taps.
- **One server process per data directory, enforced by a lock on the media directory.** Rejected: letting a second process share it, which double-counts the cap; and advising a second data directory, which would split the Ember ledger and the claims and let two servers pay for the same calls. `python -m beacon.taps` sweeps expired media when no server runs.
- **Nothing answers a tap yet.** The route stores the row and returns a receipt. Phase 3 reads media with `request.app.state.taps.media(tap_id, kind)`.

### Notices

- **Ember reads the PDF; nothing in Beacon parses it.** `read_notice` sends the bytes inline and gets a form back. Rejected: extracting text with a PDF library and sending that, which puts a PDF parser in the process and loses scanned documents. Cost: one paid, unreplayable call per document, and a reading nobody can check deterministically.
- **A notice row is a model's reading, at `high` confidence, never `official`.** The document is the authority speaking; the reading can be wrong. `url` links the PDF, `model` says a model read it, and `AGENTS.md` tells Phase 3 to show the reading as a reading, link the document every time, and send people there for the instruction. Rejected: `official`, which was my first choice because the label would describe where the document came from; review showed a consumer that trusts the label would relay a misreading as an order. Consequence: an NWS alert, which is structured data from the authority, outranks a notice. Revisit when real readings can be compared with their documents; a second, independent check of the type and the instruction could justify more.
- **A text is kept whole or not at all.** A text longer than Beacon keeps (1,500 characters for an instruction), or more than twelve areas, is left out and named in `data.incomplete`. Rejected: cutting to a length, which review showed turns "residents may return, except to these addresses" into "residents may return". Cost: a long order's row has no instruction, only the link. Revisit if real orders are routinely longer than the limits.
- **Words are kept for notices to the public and for nothing else.** For an order, warning, closure, advisory or all-clear the row keeps issuer, title, areas, streets, instruction and summary. For a press release or anything Ember does not take for a notice, it keeps the type, the hazard and the times, and nothing a model writes freely. Rejected: a closed vocabulary as for radio, because what an order tells people cannot be a tag. Rejected: keeping a press release's summary, then its issuer and street names; review showed a name and a spelled-out house number pass through both. Cost: a press release row says only that one was published, about what, and where to read it. Known limit: an order's text is not checked for a private person's name; Ember is told to leave them out, and the Phase 3 redaction pass still has to read it. Revisit when real notices show what orders contain, or if a trusted list of agencies and streets is available to check those two fields against.
- **An order's addresses stay in its words and never become a place.** A notice row has no `place` and no `point`. Rejected: deriving a block from Ember's reading, which would present a model's guess as the row's location. Phase 3 matches notices to incidents by `data["streets"]`, hazard and time.
- **The source is a JSON Feed with PDF attachments, named by the operator.** Rejected: scraping a specific agency's pages, which would be written blind against a site nobody has permission or a spec for, and RSS/Atom, which needs an XML parser hardened against untrusted input. This is the largest gap between mock and live in the phase: the format was chosen for being simple and checkable, not because a San Francisco feed exists. Revisit when a real source is chosen; an adapter that turns its listing into `ListedNotice` items is the only new code needed.
- **A notice must say when it was published, at a plain address.** The row's time is the feed's date, never the moment Beacon saw the item, so an undated item is not read. A document address with a query is not read either: the address names the document in the store and is shown as its source. Rejected: reading undated items as new, my first choice on the grounds that missing an order is the worse mistake; review showed an archived all-clear would then look newer than a current order, and an undated archive would spend the budget. Rejected: hashing the raw URL, under which a signed link is a new notice at every poll and its signature is stored. Cost: a feed without dates, or one that links documents through signed or query-string URLs, yields nothing until it is fixed or adapted.
- **A document is paid for once, newest first, four a poll, nothing dated more than a day ago, under its own budget** (`BEACON_NOTICES_BUDGET_USD`, scope `ingest:notices`). A document changed in place is not re-read. Rejected: re-reading on a changed `ETag`, which lets a site that touches its files daily spend the budget. Revisit if agencies revise notices in place.
- **A document that cannot be had is asked for again; only one over 5 MB is given up.** Untried documents go first, and a host that asks for a wait gets it. Rejected: claiming a missing document, which would lose an order whose PDF was uploaded a minute after its feed item. Cost: a broken link is fetched again every few polls for a day.
- **What could not be read is counted once, in the next report that is made.** A feed lists the same items at every poll, so the poller remembers the last 2,000 things it counted, and a count made in a poll that ended in an error (a host asking for a wait, an Ember failure, a hold) is carried to the next report. A document whose Ember call failed is not counted: that poll is reported as the poller's failure, and the claim that stays only prevents a second charge. Rejected: counting at every poll, which fills the log with one broken item. Cost: the memory is the process's, so a restart counts them once more.
- **The process that reads live notices marks itself not dumpable, and is refused where it cannot on a host with a core collector.** The same policy as the server's for taps, applied in setup so `python -m beacon.ingest` is covered. Rejected: no guard, on the grounds that a notice is a public document; a document at an address a feed lists can be anything.
- **The payment rules live in one place.** `beacon/ingest/paid.py` holds what radio and notices share: when a claim may be given up, the holds, the stop after a replaced ledger, `close` and `drain`, and the rule that a client that can spend pays under the poller's own scope, checked by its label (`ingest:openmhz`, `ingest:notices`), so that one poller cannot spend another's budget. Rejected: a second copy in the notice poller. The radio poller's earlier tests pass unchanged on it. Review added the label check: my first version accepted any scope, so the notice poller could have been built on radio's budget.

### Left for later phases

- Geocoding a block or a street to a point, which radio and notice rows lack.
- The redaction pass over notice text, and any wording shown to people.
- The airplanes.live fallback, the Broadcastify fallback and the Wikimedia glossary images, which the plan lists and Phase 2 did not need.
- Measuring the audio token rate and a notice's cost, which need a key and decide whether the caps above are right.

## Phase 3: incident engine and investigator agent

Landed on `main` at `67f7345` through three pull requests: [PR #7](https://github.com/andrewtea/beacon/pull/7) (the incident engine), [PR #8](https://github.com/andrewtea/beacon/pull/8) (the redaction pass, conflicts, and `merge_incident`), and [PR #9](https://github.com/andrewtea/beacon/pull/9) (the investigator, its routes, and crisis mode). The repository's `README.md` and `AGENTS.md` describe how the result works; this section records why.

### What runs on mocks

- **No real Ember call has been made.** In mock mode a stand-in chooses a story's points (`beacon/story/stand_in.py`) and a stand-in investigates a tap by rule (`beacon/investigate/stand_in.py`). Both say so in every answer (`model` is `fake`, `stand_in` is true, `investigated_by` is `stand_in`), and code checks their answers exactly as it checks Ember's. A key changes configuration only: `REPLAY=0`, `MODEL_API_KEY`, `EMBER_SPENT_BEFORE_USD`, a live source, and the two budgets below.
- **Whether Ember accepts the investigator's request shape is unverified.** The loop sends function tools together with a strict JSON schema for the final answer, sends Ember's own output back with one `function_call_output` per call, and ends with a request that carries earlier tool calls and offers no tools. All of that is from Meta's documentation. The first real run would confirm or correct it, and would show whether Ember fills the closed-list fields sensibly.
- **Nothing is known about quality.** The stand-in hears and sees nothing (asked about a clip or a photo it answers `none`), so no clip, photo, or model judgment has been exercised outside tests with scripted answers. How often Ember picks the right incident, and whether its crisis decisions are sensible, is unmeasured.
- **Both paid features have a budget with no default on the live store**: `BEACON_STORY_BUDGET_USD` (scope `story:merge`) and `BEACON_INVESTIGATE_BUDGET_USD` (scope `investigate:tap`). Unset, no story is made and no tap is investigated; a tap's answer then says it has no investigation. The per-tap cap of $0.01 and the story limits were chosen without knowing what a call costs.
- **There is no list of San Francisco blocks.** An incident's point comes from the story's own block list in the mock scenario. For real radio it needs the file `BEACON_BLOCKS_FILE` names, which nobody has made; without it an incident is placed only by a 511 closure on its road, and an incident with no point cannot be the answer to a tap. The redaction pass likewise needs an operator's lists of streets, units, and public places (`BEACON_PLACES_FILE`); on the live store with no lists, no notice reading that names a street is shown.

### Incident engine (PR #7)

- **Incidents are derived from evidence each time they are read, and never stored.** The engine is plain code over the evidence store, cached in memory for a few seconds. Rejected: an incidents table that `open_incident` and `update_incident` write to, as the plan's tool list implies. Why: stored incidents are a second source of truth that goes stale when a later row revises an earlier one, and everything a stand-in touched would need labeling twice. Cost: an incident's id is a digest of its first-stored row, so it is this store's own and changes if that call is regrouped or the incident outlives the twelve-hour window. Revisit if the engine's read (twelve hours, at most 20,000 rows) is too slow on real radio volume; cache longer or index, before storing.
- **Radio is grouped by street and block, then by units; no geocoding.** A call that names a place joins the incident there; a call that names only units joins the incident those units are on, and a unit is on one incident at a time. Rejected: geocoding every call and clustering by distance, which needs a geocoder Beacon has no rights or key for and makes a mishearing a wrong place. Known limits: two incidents on one block within 45 minutes are one, and a unit Ember misheard pulls a call into the wrong incident. Revisit with real radio.
- **A point comes from a list of blocks, else from a 511 closure on the incident's road, else there is none.** Rejected: guessing a point from a street name alone. A point from 511 carries 511's credit (`point_source`).
- **Medical calls are grouped only with medical calls and get nothing attached**: no closure, alert, notice, taps, aircraft, signals, story, or crisis mode. Rejected: letting a medical call join a fire at the same block, which would put patient-adjacent traffic into a public timeline.
- **"In force" is worked out by the engine, and a notice is only ever `published`.** Alerts and 511 events are resolved from later rows. The engine never says an order is in force or that an all-clear lifts one. Rejected: pairing an all-clear with its order; a notice row keeps streets and no blocks, so two documents about different blocks of one street look alike, and review showed every pairing rule tried was wrong in some case. Cost: the app shows both documents with their links and leaves the reader to the documents. Revisit if notice rows ever carry a checked area.
- **Signals are listed by code and decide nothing.** Each carries its sources and the confidence of its weakest source. `official_notice` covers orders and warnings and says which; review made me stop calling a warning an order. Whether signals add up to crisis mode is the investigator's decision.
- **Every sentence about radio names no speaker and says "That is radio traffic, not an official order" where it touches evacuation, sheltering, or an all-clear.** A radio row keeps what was said, not who said it.
- Review: five rounds (14, 6, 5, 1, 0 findings), all accepted. The recurring theme was wording that claimed more than a row shows: lift states for notices, "after" between documents, a closure's point taken from a version that closes another road.

### Redaction, conflicts, and `merge_incident` (PR #8)

- **The redaction pass is an allowlist, and a text is shown whole or not at all.** A notice reading passes only when it is made of listed ordinary words, listed names, numbers, and plain punctuation. Rejected: a blocklist or a name detector, which fail open on any name they do not know. Rejected: asking Ember to redact, which is a second unverifiable model step. Cost: it fails safe and often; a notice that names an unlisted street is not shown, and the fix is the operator's list. Known limits are in the README: it does not understand a text, and a listed name passes whatever is meant by it. Revisit when real notices show how much is withheld.
- **Nothing a model writes in Beacon's own voice is shown.** This was the largest change of the phase and came from review: my first `merge_incident` had Ember write a summary that the redaction pass then read, and the reviewer showed that "Exit the building." is made of ordinary words. So Ember now answers with points (a kind from a closed list plus the lines that show it), code checks each point against the rows it cites, and code writes the sentence. Rejected: model prose behind a filter. Why: it is the only way I found to keep "Beacon never says stay or go" as a property of the code instead of a hope about the model. Cost: stories are plain and can only say what a row says; what can be wrong is the choice of points. Revisit only with an eval that shows a filter catching instructions reliably, which I doubt exists.
- **The plan's `merge_incident` "merges" nothing.** It picks the few lines that tell an incident; grouping stays deterministic in the engine. Rejected: letting Ember decide which calls belong together, which the plan's own rule ("deterministic code decides") forbids.
- **Official sources outrank radio, and the card says why.** `conflicts` holds the two cases code can establish from times and types (an all-clear on the radio after an alert or order; a notice about another hazard), each with a sentence saying the official source holds. Rejected: asking Ember to find conflicts.
- **Stories are kept in a file of their own, keyed by incident and a digest of the lines, claimed before Ember is asked.** The file carries a shape number that a change of wording raises, because a story is shown in the words it was kept in. An earlier shape keeps its claims and loses its stories; an unknown shape or the other mode's file is refused untouched. `beacon/files.py` now holds that open-or-refuse logic for both paid files. Rejected: regenerating stories on read, which pays twice.
- **A story desk pass runs every 15 seconds inside the server**, for at most three incidents, at most every two minutes each. Rejected: making stories only when a tap matches, which leaves the incident list without them.
- Review: six rounds (11, 5, 4, 5, 1, 0 findings), all 26 accepted.

### Investigator and crisis mode (PR #9)

- **The plan's `open_incident` and `update_incident` tools are the final answer instead, and `read_notice` is folded into `get_official`.** Incidents are derived, so the investigator has nothing to open: it says which incident the tap is about and whether its signals add up to crisis mode. Notices are read once, at ingest. The tools are `nearby_incidents`, `get_radio`, `get_aircraft`, `get_official`, `nearby_taps`, `listen_clip`, and `look_photo`.
- **Ember is never told where the tap is or when it came, and no tool takes a place.** Every tool looks from the tap; arguments are picked from short lists or are an incident id an earlier tool returned; what a tool tells Ember is ids, counts, rounded numbers, and tags. Rejected: handing Ember coordinates and street names, which would put a person's location and source text into a model request and, through any free-text answer, back out. Cost: Ember reasons over less than a person would.
- **Ember answers with a form of closed lists, and code checks it.** The incident must be one `nearby_incidents` returned in this run; each ground is checked; a sound or a sight counts only for an incident it fits; a match needs `near`, or a ground that ties this tap to the incident (clip, photo, one aircraft over both) plus one other. Anything less is "unconfirmed". Confidence is code's and never above `medium`. Rejected: trusting Ember's choice, and my first rule (any two grounds), under which "it is going on" plus "others tapped" matched a tap to a distant fire; I tightened it while fixing the review's finding on grounds that did not fit the incident. Revisit the thresholds (500 m near, 250 m close, 15 minutes) with real taps.
- **The trace is stored as ids, counts, tags, and each call's tokens, latency, and cost; every sentence is written when it is read.** This is the decision the task asked for. The plan wants each round's hypothesis, tools, reasons, and results kept for Phase 4's trace view, and Phase 2's rule keeps what a person or source said off disk. So the "hypothesis" is `thinking`, `lead`, and `why` from closed lists on each tool call, a tool's result is kept as less than Ember was told, and `card.py` words it all at read time. Every Ember call of a run is `sensitive=True`. Rejected: storing Ember's reasoning text, which is free text from a model that saw source data. Cost: the trace view shows fixed sentences, not the model's own words, and a run cannot be replayed. Revisit if judges need to see reasoning; a redacted, clearly labeled excerpt would be a new design and a privacy decision.
- **A run reads the evidence as it stood when the tap came** (`Engine.at`), however long the tap queued. Rejected: reading at the tap's turn, my first version, under which an incident that began after the tap could be the answer. Cost: a tap that comes before the first radio call of what it noticed is "unconfirmed", with that incident listed in `since`.
- **One paid run per tap, ever.** The tap is claimed before Ember is asked and the claim is never released, because a run makes several paid calls and a failure seldom proves none was sent. "Keeps watching" for an unconfirmed tap is a deterministic list of incidents that began nearby in the next half hour, labeled as not investigated. Rejected: a second run when something new appears, which the plan's wording allows and which doubles cost under load. Revisit if the demo shows people tapping just before dispatch.
- **One tap's $0.01 cap is held by the Ember client.** Each call passes what is left (`respond(limit_nanousd=...)`), and the client refuses a call whose worst case is more, before the paid request. Rejected: checking what was spent before each call, my first version, which review showed is a threshold the next call can cross. This added one optional argument to the Phase 1 client; it only ever refuses, and a call with a limit sends its paid request once even on a paced client. Cost: a run can stop well short of the cap.
- **The desk bounds load**: two workers, a queue of 32, a tap older than fifteen minutes is never claimed, trouble with Ember holds the desk for ten minutes or as long as Ember asked (never shortened), and a replaced ledger stops it for the life of the process. A full queue passes a tap over. Rejected: investigating every tap, which makes a crowd of taps a crowd of paid calls.
- **Crisis mode is the investigator's decision, checked by code, and decided only when a tap is investigated.** Every signal Ember cites must be one the engine found for that incident, and a medical response is never in crisis mode. The first decision that turned it on is kept, with each signal as it was then; a later run turns nothing off; it is shown as active only while the incident is open. Its text says it is the investigator's decision and no authority's, and tells nobody what to do. Rejected: a rule that turns it on from signals, because the plan says it is an agent decision. Rejected: a periodic paid pass over open incidents. Cost: an incident nobody taps near is never in crisis mode. Revisit in Phase 4 if the crisis timeline needs to exist before a tap; a scheduled pass under its own budget is the smallest change.
- **A stand-in is never called a model.** The answer says who investigated (`investigated_by`, `investigator_text`) apart from what the evidence is (`stand_in`, `stand_in_text`), and `stand_in` is true when a stand-in investigated or when anything shown is built from a stand-in's rows.
- **Costs are reported with their gaps.** A call that ends in an error after it may have been sent has no accounting in the run; it is counted, and the routes say the totals may be incomplete. A run lost to a shutdown says the same in its own words.
- **Runs and decisions are kept for a day**, and a tap's answer is readable for a day less an hour. Rejected: keeping them for the life of the store. Revisit for the Phase 6 demo, which may want a recorded run to stay.
- Review: four rounds (14, 9, 2, 0 findings), all 25 accepted. Themes: the cap as a real cap, the moment of the evidence, sentences that claimed more than was checked, and provenance.

### Left for later phases

- A list of San Francisco blocks, and the operator's lists for the redaction pass.
- An official alert with no radio incident under it is not an incident, so a tap inside its area alone is "unconfirmed". Phase 4 can show alerts beside the answer; making one an incident is an engine change.
- Crisis mode for an incident nobody tapped near.
- Web push and saved places: nothing in Phase 3 notifies anyone. The routes are polled.
- The first real run of `merge_incident` and `investigate_tap`, and an eval of both, which need a key.

## Phase 4: app and agent trace

Landed on `main` at [`b4bf3a6`](https://github.com/andrewtea/beacon/commit/b4bf3a6) through four pull requests: [PR #10](https://github.com/andrewtea/beacon/pull/10) (the button, the answer card with its timeline and crisis mode, and the agent trace), [PR #11](https://github.com/andrewtea/beacon/pull/11) (saved places), [PR #12](https://github.com/andrewtea/beacon/pull/12) (the map of one incident), and [PR #13](https://github.com/andrewtea/beacon/pull/13) (web push). The repository's `README.md` ("The app", "The map", "Saved places", "Notifications") and `AGENTS.md` ("Working on the app", "Working on notifications") describe how the result works; this section records why.

### What runs on mocks, and what was not exercised

- **Everything the app shows by default is the invented scenario's.** With no keys the server runs the mock store, a stand-in investigates every tap, and the app says so on every view ("Invented scenario", "Invented" on anything a stand-in had a part in, "The stand-in" in the trace). A real key changes configuration only; the app reads `mode`, `investigated_by`, and `stand_in` from the server and has no mock path of its own.
- **No answer of a real Ember has been shown.** The trace view names "Muse Ember" only for a live call, which has never happened. What the trace looks like with a real model's rounds (more rounds, a clip or a photo actually judged) is unseen.
- **No push has been delivered to a real device, and no push service has checked a token Beacon signed.** The key, the signing, the subscriptions file, and the sending pass are real. In the orb a push for the invented fire went to FCM for a made-up address, which FCM answered as gone. The orb's headless Chromium denies notifications, so the app's side was exercised with the browser's permission and push manager replaced in the page, and the service worker's handlers by running them against a worker's globals in tests. A phone with the app open over HTTPS is the first real test; Firefox and Safari (which needs the app on the Home Screen) are untested.
- **A real phone's microphone, camera, and position were not used.** The app was run in a desktop Chromium with a generated tone and a generated picture. Installing to a home screen was not tried.
- **OpenStreetMap's tiles are loaded by the viewer's browser**, with no key. Nothing about the map is mocked except what is placed on it, which is the invented scenario's.

### The app (PR #10)

- **One button, and the answer to one tap is the page.** There is no feed of incidents, no city view, and no list of other people's taps. Rejected: a home screen that lists open incidents, which is the dashboard `HACKATHON.md` bans as a main feature and would make the tap optional. Cost: somebody who taps nowhere sees nothing of the fire except through a saved place. Revisit only if the rules change.
- **The app writes no sentence about an incident, an order, a match, or an investigation.** It shows the server's `_text` fields as given and adds labels for closed lists and sentences about the device and the browser. Where a view needed a sentence the server did not have, I added a field to the route. Rejected: composing sentences in the app from fields, which is where "in force", "cleared", and "stay" would creep back in outside the server's tests. Cost: the copy is plain and a wording change is a server change.
- **Hash routing with no router library, and polling with no push channel for content.** A tap's id is in the URL's fragment, which a browser sends to no server. Cadence follows what can change: a pending tap every second, an open incident every ten seconds, a closed one every minute. Rejected: path routing (the id would be in requests for the page), server-sent events or a websocket (a second long-lived channel to keep out of logs and to bound, for a demo-sized audience). Revisit if the scale run shows polling load matters.
- **A tap's id is kept in local storage for the 23 hours the server answers for it, then deleted, not just hidden.** Rejected: keeping history forever, and keeping nothing (a reload would lose the answer). Known limit: a closed app deletes nothing until it is next opened.
- **Position is rounded to about a block in the app, before it is sent**, the clip is recorded as samples and written as WAV by the app (the server takes nothing else), and a photo is redrawn on a canvas so the camera's file and its Exif never leave the phone. Rejected: sending the precise fix and letting the server round, and `MediaRecorder` output, which the server cannot decode by design.
- **A tap names the mode the person was shown (`Beacon-Mode`), and a server in the other mode refuses it unread.** This came from review: without it, a tap pressed while the app showed "invented scenario" could reach a server restarted on real sources, or the reverse. This added a required header to the Phase 2 tap route. Rejected: trusting the app's last health check.
- **A stand-in's output is marked wherever it appears**, with a dashed outline and "Invented", and the server's own sentence about who investigated is shown with the answer, the crisis decision, and the trace. Rejected: one banner at the top, which scrolls away from the claim it qualifies.
- **Crisis mode is shown ahead of everything about the tap, in the server's words, as the investigator's decision**, followed by what authorities published. A notice is shown as "Beacon's reading" with each field labeled "as read" and its document linked every time; an alert's instruction is the authority's own text. The card says whether Beacon's *record* is open, never that a place is safe or an incident over.
- **A medical response's page is its card.** No timeline, status, time, map, or saved-place listing. Rejected: showing its calls' times, which adds detail the Phase 2 rule drops.
- **The trace view shows fixed sentences written by the server from ids, counts, and tags, with each request's tokens, time, and cost.** It cannot show a model's own reasoning text, because Phase 3 stores none. Revisit if judges need to see reasoning; that is a Phase 3 storage and privacy decision, not an app change.
- **Dark only, system fonts, no component library.** Two stylesheets (`index.css` and `App.css`), inline SVG icons (`components/Icon.tsx`), and React as the only runtime dependency. Rejected: a UI kit, for bundle size and because the app has six views. Revisit for the demo video if a light theme reads better on camera.
- Review: five rounds (13, 6, 3, 1, 0 findings), all 23 accepted. Themes: a tap reaching a server in another mode, which each app-side fix narrowed and only the server-side header closed; the microphone left live on a failure path; tap ids outliving their time in storage; provenance (a stand-in's rows labeled "as Ember heard it", 511 credit missing from nearby lists); and wording that claimed more than the data shows ("Not going on now" for a record that only went quiet).

### Saved places (PR #11)

- **A saved place stays on the device; a check of it stores nothing on the server.** The name never leaves the phone, and `POST /api/places/check` takes rounded positions in the body, keeps no row, and writes no log line. Rejected: accounts, or a device id with places kept server-side, which would be the first durable record of where someone lives for a feature that needs none. Cost: places do not follow a person to another device, and the check runs only while the app is open.
- **The answer is a distance to the point Beacon has for an incident, and says it is not a zone test.** Beacon does not work out whether a place is inside an evacuation area: a notice row keeps streets and no area, and the place is known to about a block. The sentence for "nothing listed" says it is not an official all-clear. Rejected: point-in-polygon against alert areas for the saved-place answer, which would look like an authoritative "you are in the zone" from a place rounded to 100 m. Revisit if notice rows ever carry a checked area.
- **1,000 m reach, five places, San Francisco only**, chosen without data. Revisit with real incidents; a kilometre in the Sunset and in the Financial District are different things.
- **Saving and removing run under a Web Lock shared by the app's tabs.** Rejected: last-write-wins on local storage, under which a place one tab removed was put back by another tab's save (found in review). A browser without the API changes nothing and says so.
- Review: three rounds (7, 2, 0 findings), all nine accepted. The one high finding was the "nothing near" sentence saying Beacon's record had no open incident when a medical response, which is never listed, could be at the place itself.

### The map (PR #12)

- **A map of one incident, opened from its card; no map of the city.** The server decides what is drawn (`GET /api/incidents/{id}/map`): the incident's point, 511 events in force, aircraft tracks, and alert areas in force. Never a tap, a notice, or another incident. Rejected: a city map with every incident, which is the banned dashboard. Rejected: drawing taps, whose points are their senders'.
- **OpenStreetMap's standard tiles, loaded directly by the browser, with attribution on the map.** No key, and OSM's tile usage policy allows it on its terms, which `lib/tiles.ts` keeps: visible credit linked to the licence, only the tiles in view (sixteen at most), no prefetch, no offline cache. The address is a build setting (`VITE_MAP_TILES`), and `none` draws a plain grid. Rejected: Mapbox, MapTiler, or Google (keys, and terms to check), self-hosted tiles (out of scope), and a tile proxy through Beacon (hides the viewer from OSM but makes Beacon a bulk client, which the policy discourages). Cost: no service guarantee from OSM, and the tile server sees the viewer's address and which tiles around the incident were asked for. Revisit before any real launch: the policy is for light use, and a public launch should move to a paid or self-hosted source.
- **No map library: the app draws tiles and an SVG overlay itself.** Rejected: Leaflet or MapLibre. Why: the view is static around one point at three zooms, and I wanted every mark numbered and listed under the picture with its sentence and source, which is easier to guarantee in a few hundred lines than to bolt onto a slippy map. Cost: no dragging or pinch zoom, so a path or an area can run off the edge. Revisit if the demo needs panning; MapLibre with the same numbered list is the next step.
- **The picture claims nothing by itself.** Every mark has a number, and the list under it has the server's sentence, note, confidence, and sources. A dot is never moved; its number gives way. An alert's area is drawn whole or not at all, and each polygon is filled with its own holes removed (review found that parity-filling all rings together cut a hole where two polygons overlap). 511's credit is on the picture whenever something of 511's is drawn.
- Review: four rounds (7, 3, 1, 0 findings), all eleven accepted.

### Web push (PR #13)

This is the first data Beacon keeps that is tied to a device, so most of the decisions are about what is kept and how it is deleted.

- **A push carries no content.** It is a signed POST with no body; the service worker shows words the server handed the app before it subscribed. Rejected: an encrypted payload naming the incident. Why: with no payload the server needs none of the browser's keys, the push service is sent no incident, place, or text, and there is no model-adjacent text to get wrong on a lock screen. Cost: a notification cannot say which incident it is about, so it opens the saved places and a second one replaces the first. Revisit if people need the incident named; that needs `p256dh` and `auth` kept, and wording reviewed as carefully as the card's.
- **What the server keeps**: the push service's address; up to five places rounded to about a block, without names, each with when the server was first told of it; when the subscription was last renewed; for each incident a push was tried for, the id, when, how many tries, and the outcome, for 48 hours; and a short-lived random permit. No name, no browser, no address a request came from, and `/api/push` is out of the logs. `about_text` says all of it before anyone opts in. Rejected: a device id or account, and keeping places' names. A subscription lasts 30 days from its last renewal. Known cost: the `sent` rows do tie an address to an incident for up to two days; they are what stops repeats.
- **Deleting does not depend on sending.** A server with `BEACON_PUSH=0` or no contact still opens its mode's file, deletes on request and on time, sweeps the other mode's file, and sweeps each file by itself before it reads an incident. It never answers `204` without having looked in the file. Rejected: my first version, where the sweep ran inside the sending pass and stopped when sending was off, and a later one where a disabled server with no file opened none and still answered `204`.
- **A deletion is final.** An address is kept only with a single-use permit, a deletion takes away the permits of requests still on their way, and a late request keeps nothing. This came from review round 3: an aborted request is not a cancelled one, so a subscribe could land after the server had answered the deletion and restore the places for 30 days. Rejected: accepting the race and relying on expiry. Cost: one more request per telling and a third table. Known limit: the service worker's deletion of an address the browser replaced while the app was closed names no permit and is best effort; the app mends it when it is next opened. Mirroring permits to where a worker can read them was rejected as a second copy to keep true.
- **The app says "deleted" only on the owning server's `204`.** Turning off is one lock-free write of a mark that is never removed; a sync under way reads it after each wait and gives the server nothing more; an older press of On cannot undo it; no address awaiting a `204` is dropped; and what the browser did not confirm is said to be unconfirmed. Rejected: optimistic "notifications are off, nothing can arrive", which the app cannot know. Cost: `lib/push.ts` is the most intricate file in the app. Revisit if it proves fragile on real browsers; the simplification would be to drop per-mode separation.
- **Who is due a push is code's**: an open, non-medical incident with a point from the list of blocks, whose crisis decision still has a signal of a kind it cited, within 1,000 m of a place the server was told of before the decision. Rejected: a push for any incident near a place (too many, and before anyone has investigated), a push from a 511-derived point (a notification has no room for 511's credit), and a push about a decision made before the place was added. Consequence, inherited from Phase 3: **no tap near the fire, no crisis decision, no push**. Revisit with Phase 3's open question of crisis mode for an incident nobody tapped near.
- **Sending is best effort and says so.** A send is claimed before it is made and settled by the push service's status alone; an unanswered or unsettled send is tried again, three times in all, so a device can be notified twice. A pass has a 30-second budget that is not a hard end. Rejected: calling it exactly once, and waiting on reply bodies.
- **An address is a stranger's, and Beacon makes a request to it**, so only `https` addresses on Chrome's, Firefox's, Safari's, and Edge's push hosts are taken, with no redirects. Rejected: any `https` URL, which is a request-forgery tool. Cost: another browser's push service needs a code change.
- **Each mode is apart**: a VAPID key each, made by the server and kept in `data/push/`; in the browser a service worker registration, subscription, and cached words for each mode, with the worker taking its mode from its scope alone. On the mock store a real push is sent for the invented fire, and its words say first that the scenario is invented and a stand-in decided. Rejected: one key and a flag in the cache for the current mode, under which a push from the invented scenario could show a real-sounding notification.
- **A contact is required to send** (`BEACON_VAPID_SUBJECT`). RFC 8292 lets a server name nobody, and Mozilla's push service refuses one that does, so a server with no contact sends no notifications and says so. Rejected: a placeholder default, which would name an address nobody reads on Andrew's behalf.
- **New dependency: `cryptography`**, for ECDSA P-256 signing. Rejected: `pywebpush` (brings payload encryption that is not needed, and its own HTTP client, where Beacon's `fetch` already follows no redirect and bounds everything).
- Review: six rounds (13, 8, 5, 3, 1, 0 findings), all 30 accepted. Themes: deletion that depended on something else working, races between opting out and requests in flight, wording that claimed more than the server knows ("when you added it", "loses nothing"), and bounds that were not bounds.

### What runs on mocks, stand-ins, and generated audio

- **Muse Ember has been asked only about invented material.** A key arrived on Nov 27, 2026, late in the phase. With it: the audio rate was measured on tones, each kind of request was put to Ember once or a few times by hand, and one scale run of a sample was paid for. In all, 450 paid requests for $0.066957, in one ledger. Nothing a person sent, no recording of radio, and no real notice has been put to Ember.

- **Two scale runs exist, and neither is about real radio.** A stand-in's run of the whole of 2026-11-24 on generated tones (549 calls, 468 found, 85.2%, a median of 49.6 m) shows only that the pipeline keeps what it is given. Ember's run of a sample (the first 100 calls of that day as synthesized speech: 86 found, a median of 49.1 m, $0.0345 to hear 288 calls, 34 replayed taps at a mean of $0.0005 and a median of 4.5 s, a glossary that went from 4 codes to 9 of 10) gives real costs and times of Ember's for clean synthetic speech, scored against the records the speech was generated from. - **No recording of real radio has been read.** There is none Beacon has the right to use. The reader's layout comes from trunk-recorder's source.
- **adsb.lol was asked once**, on Nov 27, 2026, to read the shape of its answer. The poller has otherwise run against mocked HTTP.
- **The deployment runs the invented scenario with no key**, as the coordinating thread asked: it is open without sign-in.
- What recordings would change: `--recordings ... --paid` is the one kind of run whose numbers are about Beacon on real radio, and the plan's $1.25 for hearing is unspent for it. A Broadcastify license would be a new source and a new adapter; nothing here assumes one.

### Aircraft from adsb.lol (PR #14)

- **adsb.lol in place of OpenSky**, which Andrew approved. Rejected: OpenSky, whose terms need a written license nobody has. Why: adsb.lol's API is open to everyone under the ODbL. Revisit before Beacon is run for the public: an older page of adsb.lol's asks people who use it "for production purposes" to get in touch, which has not been done.
- **The ODbL's notice goes wherever something rests on a position adsb.lol answered with, and nowhere else.** The credit is read from the rows, never worked out from the kind of a signal or a tool, so an invented aircraft carries none. Rejected: one credit line in the footer, which would credit adsb.lol for invented positions and miss a trace or a crisis decision that rests on real ones. `docs/aircraft-data.md` says what is kept and how, as the license asks of a derived database.
- **The poller keeps to the daily allowance across restarts and across processes**, by promising in the evidence store not to ask again for one interval before it asks. Rejected: an in-memory timer, which a restart loop turns into a burst. With no key that is one request about every three minutes.

### Radio from recorded calls (PR #15)

- **OpenMHz is refused in code, not left behind a setting.** There is no client, its name is refused as a source with the reason, and `fetch` refuses its domain and Broadcastify's whoever names them. Rejected: keeping the poller behind `BEACON_OPENMHZ_PERMITTED`, which would leave a way to turn on what the owner was told not to use.
- **Radio is a reader of recorded calls in trunk-recorder's layout**, on the machine Beacon runs on, behind `BEACON_RECORDINGS_PERMITTED=1`. Rejected: a Broadcastify adapter (no license), and a downloader of any kind. Why: it serves Andrew's own recordings if he makes them and generated audio if he does not, through the same poller.
- **The operator's files are read where they lie**: into memory, through no symbolic link, never copied, changed, or deleted, and nothing of a call's JSON is kept but the talkgroup, the start, the length, and two flags. A call is claimed only once its audio plays about as long as its JSON says, so a call still being written is not paid for.
- Review: four rounds, every finding accepted. Merged as `c29c5a1`. Revisit when a real recording exists: the layout is unverified against one.

### The scale run (PR #16)

- **A command apart from the server, with stores of its own.** Rejected: running the day through the server's store, which would mix a replayed day into what the app shows.
- **Three kinds of run, and a run is one kind for good.** Generated calls heard by a stand-in, generated speech heard by Ember, recorded radio heard by Ember. A tone is never sent to a paid Ember and a recording never to a stand-in. Rejected: going on with a run under other settings, whose rows nothing could tell apart afterwards.
- **Generated calls are scored against the records they came from, and every sentence says so.** Rejected: leaving the scale run unbuilt until recordings exist, and reporting a stand-in's zero cost or a script's speed as a number. Each number has a wording for each kind of run, and a stand-in's cost, latency, and lead time are "none" with a reason.
- **Nothing is paid for twice, over every invocation.** A call and a replayed tap are claimed before Ember is asked and the claim is never given up once a paid request may have been sent. Cost: a call whose process died between the claim and the row is counted and lost. Rejected: a "retry what failed" option, because a failed call may have been billed.
- **One invocation at a time, pinned to one ledger file.** An operating-system lock for as long as the command runs, and a paid run refuses a ledger other than the one it began in. Known limit, stated and not fixed: a ledger rolled back in place cannot be told apart.
- **The hearing is closed when it is first complete**, before the first tap is claimed and before the glossary is asked for, so everything made of the whole day is of one evidence.
- **The caps are the plan's**: $1.25 for hearing (shared by `scale:radio` and `scale:speech`), $0.50 for taps, $0.25 for the glossary. An option lowers one and cannot raise it.
- **Streets, blocks, and units come from DataSF**, which also gives the server its lists. A block's point is the middle of the stretch of street its house numbers are on; nobody has checked one against the ground. The unit roster is from the thirty days before the scored day, so it is not read off the answers.
- **The matching rule is plain code, stated beside the result**: same medical-or-not kind, opened within the call's time, and one of its units or within 300 m. "Found" is a fit by that rule. Revisit the thresholds with a run on real radio, and never tune them to a run's numbers.
- **A replayed tap is not a tap.** It is never stored as one, so it adds to no incident's count.
- **Medical calls stay medical.** The columns that say how a patient was are never requested.
- Review: seven rounds (14, 9, 4, 4, 2, 1, 0 findings), every finding accepted. Merged as `9b73621`.

### The glossary (PR #17)

Ember is sent a table of counts for each unit type code and answers with a role from a closed list. Rejected: keeping transcripts for a day to learn from, which undoes Phase 2's guarantee. Cost: it can only learn what kind of unit a code names, not what a spoken code means.
- **A proposal, never applied over what a person wrote down.** The five built-in codes stand; a proposal for one is compared and counted apart.
- **Compared against DataSF's unit types, which the learner is never shown**, over codes where more than half of all of DataSF's units of the code are of one kind.

- Review: four rounds (8, 5, 1, 0 findings), every finding accepted. Merged as `8fe02ab`.

### The deployment ([PR #19](https://github.com/andrewtea/beacon/pull/19), merged as `24107d0`)

- **One process on the smallest Amp Box** (`andrewtea/beacon`, `b1.tiny`, $18 for 30 days at Amp's listed price), public, at https://beacon-sf--andrewtea.onamp.dev. `python -m beacon.serve` serves `/api` and the built app from one origin. Rejected: a static host for the app with a proxy to the API, which is a second thing to keep the private paths out of the logs of.
- **The build runs where the deploy is given and ships a Python of its own.** The Box has Python 3.12 but no uv, and a service there can install nothing. Rejected: building on the Box.
- **The invented story is told again when it is over**, about every 85 minutes, by deleting the mock store's three files in the same process. Rejected: a store that never ends (a fire that ended days ago), and a longer story. Cost: a tap's answer on this server is gone within about 85 minutes, which the mock banner and a gone tap's page say. Never touched: a live store, the ledger, a scale run, push subscriptions.
- **Before anything is deleted, every file has to be seen to be the mock store's own**: no link, nothing SQLite keeps beside it a link, saying `mock` in a shape this Beacon knows, with its kind's own table and no other kind's. A file that is not seen to be that stops the server; only a busy file leaves it running on the story as it stands. Rejected: trusting the file's name and its `mode`, which the push subscriptions' file also says. Cost: a new table or a new file of the mock story's has to be named in `beacon/serve.py`, or the server that repeats refuses to start.
- **Whatever opens a store holds the data directory's lock first** (`DataLock`), and a server that did not stop whole keeps it. Rejected: deleting under a server whose threads may still be writing. Cost: after an incomplete stop the process has to end before another can start, and the invented scenario's server ends itself.
- **The public demo takes nothing of a visitor's own** (`BEACON_FRONT_END=unverified`): only the invented scenario's two places, no accuracy, clip, photo, saved place of one's own, or push address, refused by the server and not asked for by the app. I first built it as disclosure (a sentence saying what the host might log); the reviewer rejected that, because a tap's id is in the path of its routes and with the id its holder reads the answer, and nobody has checked what Amp's and Google's front ends write down. `verified` is the operator's word that they have seen the host keep the three private paths out of its records, and nothing else. Cost: judges cannot try the microphone, the camera, their own location, or a push on the public URL. **Revisit: this is the open decision for Andrew.** Ask Amp what its front end logs, or host where the front end is ours, then set `BEACON_FRONT_END=verified`.
- **The app asks such a server for a tap only when this device knows the server took it under that rule**, and only after the health has said what the server takes; a tap that is gone stays said to be gone and is not asked for again. Rejected: asking and letting the server answer 404, which sends the id first.
- **No redirects and no WebSocket**, because a redirect behind a host that ends TLS is built with `http`, and uvicorn logs the path of a handshake it refuses.
- **Settings are defaults the deployment's environment overrides** (`deploy/python`), so a key or a source needs no code change.
- **`deploy/box-setup` is run by hand once on a Box**: ffmpeg, bubblewrap, apport off, and an AppArmor profile for `bwrap` alone. Rejected: turning the restriction on user namespaces off for the whole machine, and shipping an ffmpeg in the release. Its branch that installs the profile and the one that finishes a run cut short have been run on no machine: the Box needed neither.
- **What stands in front is only partly known.** Beacon's process writes no access log and the Box's router, as read, writes nothing. What Amp's and Google's front ends keep of a request is not known, and the repository says so.
- Review: eight rounds (10, 7, 8, 4, 2, 1, and 1 findings, then cleared), every finding accepted.

### The first real Ember calls, and a run of a sample ([PR #20](https://github.com/andrewtea/beacon/pull/20), merged as `cdeac74`)

- **Every request shape was accepted; what was wrong was the room for an answer.** Reasoning is billed as output and counts against `max_output_tokens`. At `low` effort Ember reasoned for 500 to 3,000 tokens before a form of fifty, so every call sized for its form came back `incomplete`: hearing a call, choosing a story's points, and the calls about a tap's clip and photo. Chosen: `minimal` effort with more room for those, and `low` with 8,192 tokens for the glossary's one call. Rejected: keeping `low` and only raising the room, which cost 2.2 times as much on twelve generated calls for no gain that twelve calls can show (units right on 10 against 9, category and place the same). Revisit with recordings: clean synthetic speech says nothing of what `minimal` loses on radio, and the modules say to measure again.
- **No caller reads an answer that did not end.** An answer whose status is not `completed` is no form for any call, whatever of it parses as one: hearing a call, reading a notice, a story, a glossary (counted toward the run's hold as an answer that was no form), a clip or a photo, and a tap's investigation, which ends as "no answer" with what the answer cost and runs no tool on its word. Rejected: gating only the calls the first answers broke, which was my first change; review showed the investigator could run a paid tool off a cut-short round. Cost: an answer that was cut short after a whole form is thrown away, having been paid for.
- **Of a clip or a photo, `none` is Ember's to say.** Before, an answer that ran out of room was read as "none of these can be heard", which is what came of the one clip and the one picture tried. Now `none` is kept only when the answer says `none`; a cut-short answer, an empty list, and a list that names only what is on none of Beacon's lists are "no answer". Rejected: leaving an empty list as `none`, which says Ember heard nothing when it may have heard something Beacon has no tag for.
- **A run of a sample (`--calls N`) in place of a paid whole day.** The coordinating thread asked that the scale run's $1.25 not be spent on a day of generated audio and that a sample of at most $0.15 prove the paid path. Chosen: the day's first N calls in the order they were dispatched, for generated calls only, fixed for good in the run's settings, and said before any number, beside every number, and under every heading. Rejected: capping a whole-day run at $0.15, which stops with the hearing incomplete, so no tap is replayed and no glossary learned; and a spread sample (every k-th call), which is harder to state and to check. Cost: a day's first calls need not be like the rest of it (66 of the 100 were medical), which the results say.
- **A sample is strictly fewer calls than its day, and a sampled run says so twice on disk.** The bound is checked when the run is begun, at every invocation after it against the records it kept, and in a written result. A sampled run's `run.json` has the audio `generated-sample` beside its `sample`. Rejected: `sample` alone, which a Beacon from before `--calls` would read past, and so go on with the run, and pay, as a whole day's. Cost: the one paid run was begun before that word existed, so I changed it by hand in its `run.json` and gave the same command again, which rewrote the results with no paid request (450 requests and $0.066957 before and after, all 44 values the same). README says so.
- **Three things among a sampled run's numbers are not the sample's, and each says so in its own sentence**: what of DataSF's whole answer could not be read, DataSF's unit types (the whole day's), and the cost of hearing (the total, the count of requests, and the rate, which are the spending scope's over every paid run). Rejected: "every number below is of the sample", which was my first wording and was false of those. Of generated calls, an incident that fits no record is counted and not explained, and nothing is said of a call DataSF does not list, since every generated call is of a record.
- **A whole day of generated speech was not run.** At what the sample paid it would cost about $0.18 to hear. It would add a day's worth of a number that is still not about radio, and Andrew may yet supply recordings.
- **The paid calls were made from one data directory kept in the Phase 5 thread's backup folder** (`.amp/in/orb-backup/paid-data`), so the ledger survives the orb. **Whoever pays next pays from that directory, and stops when it is not to hand.** Rejected: starting a new ledger elsewhere with `EMBER_SPENT_BEFORE_USD` set to Meta's Usage total, which I first wrote into README; review rejected it, because a second ledger admits its own $3.00, knows no scope's spend, and a run begun elsewhere knows none of the sampled run's claims, which are in the run's own files beside the ledger. Revisit when the server is to pay: the directory then has to move to where the server runs, once, with nothing paying meanwhile. Calls made by hand to read Ember's answers used scratch scripts that are not in the repository; README says what they sent and what came back, and that a reader cannot rerun them.

### Muse Ember on the invented story (PR #21)

- **Chose: a teller for the mock store, not a third origin or a third store.** `BEACON_MOCK_EMBER=live` has Muse Ember do the model's part on the invented story's evidence, in the mock store, whose rows stay `mock`. Rejected: a third origin ("invented, heard by a model") or a third store, which the Phase 2 thread had expected. Why: what makes a row unfit for the live store is that its source is invented, and that does not change with who heard it; a third origin would have needed every reader of `origin` and `stand_in` taught a new case, and a relaxed check on the live store was never on the table. What does change is who did the model's part, and each thing already says that of itself (`row.model`, a story's, a run's), so the labels were given words for it ("Generated radio calls, synthesized speech and no radio, as Ember heard them", "Invented notice, as Ember read it") and `GET /api/health` got `teller` and `teller_text`. Revisit if a second kind of non-real material appears whose rows must be told apart from the scenario's in queries, not only in labels.
- **Chose: synthesized speech made in memory when a call's moment comes, with no file written.** A tone says nothing and is never sent to a paid Ember, so each call's invented words are spoken by ffmpeg's `flite` voice on a pipe (`SpokenShelf`, `radio/speech.py`). Rejected: writing the calls as files in trunk-recorder's layout, which the first draft did; a directory of generated files next to the reader for real recordings is one mistake away from being read as recordings. Cost: while ffmpeg runs, its command line holds the invented words. Revisit if the words stop being invented.
- **Chose: a store Muse Ember worked on says so in its mode word (`mock-paid`), written before anything is paid for.** Why: an older Beacon knows no teller and would go on with such a store with its stand-ins, or delete it when the story is over, and with it the claims on what was paid for. Tried against `main` as it was before: it refused the file and deleted nothing. Rejected: a column or a side file, which an older Beacon would not read.
- **Chose: a mock store is one teller's for as long as it is kept, and a paid telling is never told again by itself.** `BEACON_MOCK_REPEAT=1` is refused with `BEACON_MOCK_EMBER=live`, and the server that tells the story again refuses to delete a store Ember worked on. Rejected: the deployed repeat with Ember, which would pay about two cents every 85 minutes for as long as the server is up and delete the record of what was paid for.
- **Chose: a budget with no default, and four scopes of its own** (`telling:radio`, `telling:notices`, `telling:stories`, `telling:taps`), so that the invented story's cost is never mixed with the scale run's or with real sources'. Every call is claimed before Ember is asked, as on real sources.
- **Chose: a clip or a photo is taken only from a sender who was shown that it goes to Meta** (`media_text`, the `Beacon-Media: meta` header, `409` otherwise). It matters only on a server that takes a visitor's own, which neither server that is up does. Revisit when one does.

### A story that can be brought to a moment (PR #22)

- **Chose: begin a new store's story at a chosen minute (`BEACON_MOCK_STORY_MINUTE`), and never hold or move a clock.** Every row before that minute is stored with the time it would have had, and the story goes on by the real clock. Rejected: a pause, a fast-forward, or a clock the operator moves. Why: the investigator reads the evidence "as it stood when the tap came", holds and sweeps are by the real time, and claims are stamped with it; a clock that can be held makes every one of those a special case, and a row's time would stop meaning when it was stored. Cost: the person filming waits for the story, and a missed moment costs a new telling (about two cents with Ember). Revisit if filming shows the wait is unworkable; the cheaper fix is a second telling begun at the missed minute, which is what `scripts/film anew N` is.
- **Chose: a told store is set aside whole (`python -m beacon.serve --set-aside`, under `told/`), and nothing of it is deleted.** Rejected: deleting the store to begin again, which is what the stand-in's repeat does. Why: a store Ember worked on holds the claims on what was paid for. The move is two-step (a second name under `told/` for every file before any loses its first), keeps a note while it is under way that keeps every server out, and has the disk confirm each step; `DataLock` asks the disk again before any store opens. That is more machinery than a demo feature deserves, and each piece answers a review finding about a half-moved store being served or paid from.
- **Chose: a paying server is given the ledger's name and never begins a ledger** (`BEACON_MOCK_EMBER_LEDGER`, `only_ledger`: generation, device, inode). Why: a client begins a ledger where it finds none, and one begun anew counts nothing of what was spent, which is how the $10 could be passed. - **Chose: `scripts/film`, in an Amp orb behind an orb portal, for the server Andrew films from.** Rejected: a private Box deployment. Why: the key is already the project's secret in the orb, and the one ledger is in this thread's backup folder there, so bringing the server up is one command or one message and nothing has to be entered or copied; a Box would have needed Andrew to enter the key in a masked prompt and the ledger copied to a second machine, which is the "second ledger" every phase warned about. Cost: an idle orb pauses, and the story goes on by the clock while it does, so a server that was left is begun anew. Revisit if the submission needs the Ember telling to stay up through judging (Dec 3 to 6): that is a private Box with the key and the paid data directory moved there once, with every other process that spends stopped.
- **Chose: the filming server takes only the two invented places, like the public deployment.** The coordinating thread's assumption was that Andrew accepts sending his own phone's location, sound, photo, and push address through Amp's portal.
