# Beacon

Beacon is a "What's that?" button for your city. You hear a siren or see a helicopter, tap once, and Beacon says what is going on, which crews are on it, roughly where, and when it cleared, with a source on every claim. Behind the button, Muse Ember listens to San Francisco's public fire and EMS dispatch radio, reads aircraft positions, alerts, and notices, and stitches them into one incident record per event.

Beacon is being built for the Meta Muse Ember Hackathon (Nov 23 to Dec 2, 2026). The rules, the $10 budget, and the submission checklist are in [HACKATHON.md](HACKATHON.md).

**Status:** scaffold, Ember client, evidence store, five pollers, the route that takes a tap, the incident engine, the redaction pass, incidents' stories, the investigator that answers a tap, and [the app](#the-app): the What's that? button, the incident card with its timeline and crisis mode, the agent trace, and [saved places](#saved-places), which stay on the device, and [a map of one incident](#the-map), opened from its card, and [notifications](#notifications) for a device that asks for them, sent as a push with no content when crisis mode is turned on near a place it saved. The server stores evidence rows and runs pollers for National Weather Service alerts, aircraft positions from adsb.lol, 511 road closures, recorded dispatch radio, each call of which Ember hears and turns into a row, and official notices, each document of which Ember reads (`read_notice`). **By default the pollers are fed an invented scenario, not real sources:** a made-up three-alarm fire in Hayes Valley, told in each source's own format, and every row from it is stored as `mock`. Its radio calls are generated tones and its notices are invented PDFs, and what was "said" in them is filled in by a stand-in for Ember, so its radio and notice rows are a stand-in's twice over. An early version of the NWS poller was run once against the real API; nothing else has been. The 511 poller has run only against mocked HTTP, because there is no token. **Aircraft come from [adsb.lol](https://www.adsb.lol), not OpenSky:** OpenSky's terms require a written license for a running service, which nobody has, so Beacon has no OpenSky poller; adsb.lol's API is open to everyone under the Open Database License. One request was made to it on Nov 27, 2026, to read the shape of its answer, and the poller has otherwise run only against mocked HTTP. **Beacon asks nobody for radio audio.** OpenMHz was asked whether Beacon may use its API and said not to, so Beacon has no client for it and no setting makes one; it was never asked for a call. Radio comes from [recorded calls on the machine Beacon runs on](#radio), in the layout trunk-recorder writes, and **no recording of real radio has been read yet**: there is none, and the layout is read from trunk-recorder's source. **No real Ember call has been made:** there is no API key, so the client has run only against a mock of the Meta Model API in tests, and its request shapes come from Meta's documentation, not from an answer of Ember's. **No real notice has been read:** Beacon knows of no San Francisco agency that lists its notices in the feed format the poller reads, so going live needs such a feed first. Nobody knows yet how well Ember hears a radio call or reads a notice. The audio token rate the budget rests on is [still a guess](#measure-the-audio-token-rate). **The [incident engine](#incidents) groups the evidence into incidents with plain code,** and on the default store every incident it shows is the invented scenario's (`stand_in`). **No model's sentence is shown about an incident:** Ember picks the few points an incident's [story](#stories) is told by, and code checks each against its rows and writes the words. On the default store a stand-in picks them, and says so. No real incident has been read, and no real Ember has picked a point. **A tap is looked into by the [investigator](#the-investigator):** Ember chooses which tools to call and answers with a form, and code checks the form and writes every word; thin evidence is "unconfirmed". On the default store a stand-in investigates, by rule, and every answer says so. No real Ember has investigated a tap. **The [scale run](#scale-run) puts a day of dispatch calls through Beacon and scores it against DataSF's public record of that day, and it has only been run on a stand-in:** the calls were generated from DataSF's records and "heard" by a stand-in that looks each one up, so its numbers show that the pipeline keeps what it is given and say nothing of Beacon's accuracy, speed, or cost on real radio.

## Run locally

You need [uv](https://docs.astral.sh/uv/), Node.js 26, and pnpm 12. uv installs Python 3.12 itself. [ffmpeg](https://ffmpeg.org) and [bubblewrap](https://github.com/containers/bubblewrap) (`bwrap`), on Linux, are needed to take a photo with a tap and to hear real radio, and for the tests of both, which are skipped without them (CI installs both). Without them the server runs, and refuses a tap's photo.

```sh
# The server, on http://127.0.0.1:8000.
cd server
uv sync
uv run uvicorn beacon.main:app --reload

# The web app, in a second terminal. It proxies /api to the server.
cd web
pnpm install
pnpm dev
```

In an Amp orb, `amp orb services ensure` starts both and prints the portal URL.

Both of those serve the web app with Vite's dev server, which leaves out the web app manifest and the app's own service worker, so the app cannot be installed from it. [Notifications](#notifications) have a service worker of their own, which the dev server does serve; they need `BEACON_VAPID_SUBJECT` set for the server, which the orb's services do. To try the installable build, keep the server running and serve the production build, then open it on `localhost` or over HTTPS:

```sh
cd web
pnpm build && pnpm preview
```

Run a Python script from `scripts/` with the server's environment: `uv run --project server python scripts/<name>.py`.

## Check

```sh
scripts/check          # everything CI runs
scripts/check web      # format, lint, tests, type check, build
scripts/check server   # format, lint, tests
```

Tests never call the Meta Model API or a live data source: the pollers' tests answer from hand-written replies and the mock scenario, and the radio tests hand generated tones to a fake Ember. Two entry points enforce the environment for that: `scripts/check`, which CI also runs, sets `REPLAY=1` and removes `MODEL_API_KEY` before it checks either side, and server pytest does the same however it is started, because `server/tests/conftest.py` does it. CI holds no key. A web test run directly with `pnpm test` keeps whatever environment the shell has; nothing in `web/` reads the key. As a backstop for the server tests, `server/tests/conftest.py` patches Python's `socket.connect` and `socket.connect_ex` in the test process to raise `NetworkBlockedError` for any address that is not this machine. It is a backstop and not a sandbox: a test that catches that error still passes, and the patch does not reach DNS lookups, subprocesses, or native code that opens sockets without Python's `socket` module.

## Configuration

Settings come from the environment. The server does not load the repository-root `.env` file: export a variable in your shell or put it in front of the command. (Vite loads `web/.env` for the web app, as it does by default, and exposes only names that start with `VITE_` to the browser. Beacon has no such file and no such setting.)

[`.env.example`](.env.example) lists the settings. The Ember client reads the first five (`EmberClient.from_env`), and the server reads the rest when it starts. The two `EMBER_` settings are read from the process's environment and nowhere else: a mapping handed to `from_env` can choose the mode, the key, and the data directory, and cannot supply or change the spending settings.

| `EMBER_STOP_USD` | The most the Ember ledger may hold in live spend, in dollars. | `3.00` |
| `EMBER_SPENT_BEFORE_USD` | The total spend against the $10 credit, for every model, that Meta's Usage page showed before Beacon's first call, in dollars. `0` is an answer; it has no default. | No live calls: a client that can spend is refused. |
| `BEACON_DATA_DIR` | Where runtime data goes. An absolute path; a relative one is refused. | The repository's `data/`. |

The Ember settings are read by the two commands under [Ember client](#ember-client), and by whatever pays Ember when it is turned on for real, each of which builds a client that can spend, under a budget of its own: the pollers `recordings` and `notices` in `BEACON_LIVE_SOURCES`, in the server or in `python -m beacon.ingest`, and in the server the story desk (`BEACON_STORY_BUDGET_USD`) and the investigator (`BEACON_INVESTIGATE_BUDGET_USD`). No route builds a client: reading an incident, a story, or a tap's answer asks Ember nothing. The server reads the source settings when it starts, and `BEACON_DATA_DIR` with them. Three places set any of them. `scripts/check`, and so CI, sets `REPLAY=1` and removes `MODEL_API_KEY`. Server pytest does the same, removes the spending settings and every source setting, and points `BEACON_DATA_DIR` at a temporary directory for each test. The orb's API service in [`.amp/services.yaml`](.amp/services.yaml) sets `REPLAY=1`.

## Evidence and ingest

Each source has a poller in [`server/beacon/ingest/`](server/beacon/ingest) that writes **evidence** rows to SQLite through [`server/beacon/evidence/`](server/beacon/evidence). A row is one thing one source said: a weather alert, one position of an aircraft, one version of a road closure, one radio call, one notice. Later phases read the rows back by kind, time, and place to build incidents and answer taps.

| Column | What it holds |
| --- | --- |
| `kind` | `radio`, `aircraft`, `alert`, `traffic`, `notice`, or `tap`. |
| `source`, `ref` | The feed (`nws`, `adsblol`, `511`, `recordings`, `notices`, and `app` for a tap) and the source's own name for the item. Together they name one row, so an item a source sends twice is stored once. |
| `occurred_at`, `until` | When it happened according to the source, and when it stops applying, for an alert. |
| `point`, `place` | A latitude and longitude, and the place in words. Either can be missing: a city-wide alert has no point. |
| `confidence` | `official` for an authority speaking for itself, else `high`, `medium`, or `low`. |
| `origin` | `mock` for the invented scenario, `live` for a real source or a person's tap. |
| `model` | Which kind of Ember client wrote the row's data, when a model did: `live`, `replay`, or `fake`. |
| `data` | What the source said, as JSON in a shape of the row's kind. Each poller's module documents its own. |
| `url` | Where a person can read the original, when it is public. |

Rows are never changed. A source that revises what it said gets a new row: an NWS update is a new message, and each version of a 511 event is stored under the event's id and its update time.

**An item that goes missing from a source's answers has not been officially ended.** NWS and 511 answer with what is active now, and mostly an alert or closure that is over is simply absent from the next answer. NWS can also cancel an alert outright, with a `Cancel` message: that is a row like any other, and it is the authority speaking, so it stays `official`. Absence is different. When an item has been missing from two answers in a row that were read in full, and for an alert before the time it said it would end, the poller stores a row whose `data` says `"change": "not_listed"` and names the row it is about. That row is what Beacon saw, not an all-clear from an authority, so its confidence is `medium` and not `official`. When the same item is listed again, as night road work is every night, a `"change": "listed_again"` row says so.

| Source | What is asked | Kept | Terms |
| --- | --- | --- | --- |
| [NWS](https://www.weather.gov/documentation/services-web-api) | Active alerts for San Francisco's forecast zone and county, every 2 minutes. No key. | Every `Actual` alert, including civil messages NWS relays, such as a shelter-in-place warning. | Open data, free to use for any purpose. |
| [adsb.lol](https://www.adsb.lol/docs/open-data/api) | Aircraft within seven nautical miles of the middle of the city, about every 3 minutes with no key, and as often as the operator says a key allows (down to every 10 seconds). | Aircraft inside the city's box that are airborne below 3,000 m, under an ICAO address, with a position no more than a minute old: what a person on the street could notice. | The API "is available to everyone" under the [Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/), with 500 requests a day for an address with no key. Beacon's aircraft rows are a database derived from adsb.lol's, and what the app shows from them is shown to the public, so the license asks three things. **A notice** wherever something made from the data is shown: every line, signal, ground, count, and map mark that rests on a position adsb.lol answered with carries "Contains information from adsb.lol, which is made available here under the Open Database License (ODbL)", with a link to adsb.lol and a link of its own to the license. **The same license for the rows**: Beacon licenses its aircraft rows under the ODbL 1.0. **An offer of how the rows differ from adsb.lol's database**: the notice links [`docs/aircraft-data.md`](docs/aircraft-data.md), which says both and gives the whole method (what is asked and how often, what is kept, each conversion, how a row is stored). Beacon gives nobody a copy of its aircraft rows; if it ever does, the copy goes out under the same license with the license's address in it. **The allowance is kept to across restarts, and by every process on one data directory**: before each request the poller promises in the evidence store not to ask again for one interval, counted from the real time at which the store let it write, and looks and writes in one transaction, so two processes on one store cannot both find the time come. A wait adsb.lol asks for (`Retry-After` on an answer that is no success, as the `429` of a spent allowance is) moves that moment on, up to a week and never back, and a server that starts keeps the promise before it asks anything. A wait the store could not be told of is kept by the running server, which writes it before it asks adsb.lol again and asks nothing until then; a server that dies first has lost it. A poll that finds the time not come asks nothing, is no failure, and leaves what `GET /api/sources` says of the last poll as it was. **The invented scenario's aircraft carry no such notice**: they are in adsb.lol's format and hold nothing of adsb.lol's, and their feed is labeled "Aircraft positions". An older page of adsb.lol's asks people who use it "for production purposes" to get in touch (info@adsb.lol): do that before running Beacon for the public. |
| [511 SF Bay](https://511.org/open-data/traffic) | The traffic events in effect now, for the whole Bay Area: one request every 2 minutes, and a poll that needs several pages waits that long for each. Needs a token. | Events inside the city, each with its schedule. | [511's data agreement](https://511.org/sites/default/files/2026-04/511_Data_Agreement_Final_2026.pdf) licenses storing, displaying, and deriving from the data. Wherever the app shows it, it must say "data provided by 511.org" with a link to 511.org. |
| Recorded calls | The calls on the fire and EMS talkgroups in a directory on this machine, as [trunk-recorder](https://github.com/robotastic/trunk-recorder) leaves them (one audio file and one JSON file a call), looked at every 30 seconds. Nobody is asked for them over the network. | One row for each call Ember heard, in the closed vocabulary described under [Radio](#radio). Never the audio or a transcript, and nothing of the radios that transmitted. | **The operator's own recordings, or ones the operator has permission to use** (`BEACON_RECORDINGS_PERMITTED=1`). **Not OpenMHz:** it was asked whether Beacon may use its API and said not to, so Beacon has no client for it and requests nothing from it. **Not Broadcastify:** Beacon has no license from it, has no client for it, and requests nothing from it. Beacon does not use a recording downloaded from either, and does not request LiveATC's audio. Beacon publishes summaries, never the audio. |
| Notices | A feed of an authority's notices, in the [JSON Feed](https://www.jsonfeed.org/version/1.1/) format, every 2 minutes, and each notice's PDF. | One row for each document Ember read, holding Ember's reading of it, as described under [Notices](#notices). Never the document. | **No feed is known yet.** The operator names one (`BEACON_NOTICES_FEED_URL`), and names only a feed whose documents Beacon may relay: an agency's notices to the public. |

### Radio

A radio call is one of the two kinds of evidence a model makes ([notices](#notices) are the other): the poller reads a call's audio from the operator's directory and Ember hears it (`extract_transmission` in [`server/beacon/radio/`](server/beacon/radio)). Dispatch radio names people, describes patients, and gives house numbers, so this is what ingest guarantees about a call, before any later redaction:

- **Nothing a call said is stored as text.** There is no transcript. Ember fills in a form, and each field is checked against a closed vocabulary before anything is kept: a category, a status, and detail tags from fixed lists, and the hundred block of an address (`1458` is kept as `1400`). A unit id or a street name is kept only when it is **on a list**: `BEACON_RADIO_UNITS_FILE` and `BEACON_RADIO_STREETS_FILE` for real radio, and the story's own units and streets in the mock scenario. A shape is not enough, because `BP 180` has the shape of a unit and `One Two Three Hayes St` the shape of a street. With no list, a row names no unit and no street. What does not fit is dropped, whatever Ember wrote.
- **A medical call is "medical response", its crews, and its block.** Its status, details, and alarm level are not kept. That holds for a call Ember hears as medical and for every call on a talkgroup named in `BEACON_RECORDINGS_EMS_TALKGROUPS`, whatever Ember made of it.
- **Beacon writes the audio to no file**, not even while ffmpeg decodes it. The recording stays where the operator put it, and Beacon neither copies, changes, nor deletes it; what is read of it is held in memory while its call is worked on, and it is handed over as a file that exists only in memory. ffmpeg runs confined by bubblewrap, with no network, no environment, and no directory to read but the ones a system keeps its programs and their libraries in (`/usr/bin`, `/usr/lib`, and the like, not `/usr/local` or `/usr/share`), with Beacon's data directory covered over wherever it is, and under limits on its memory, time, and output. Two things are left to the host. **Swap:** run real radio with swap off or encrypted; nothing checks it. **Core dumps:** Beacon and ffmpeg both run with a core size limit of nothing, which Linux ignores when cores are handed to a collector such as systemd-coredump or apport, so Beacon refuses to hear real radio on a host whose `kernel.core_pattern` begins with `|` (a pipe) or `@` (a socket). Set it to a file name, such as `core`, and leave it so: Beacon reads it once, when it starts.
- **Ember is sent a WAV file Beacon made itself**, whatever the call arrived as, so Beacon knows how long the audio really plays before it pays, and nothing else a file carried is sent.
- **The Ember call is a sensitive one**, so the Ember ledger and trace hold its tokens and cost and none of its audio or its answer, and it is never recorded for replay.
- A radio row has a place in words and no point: nothing in ingest knows where on the map a block is.

The limits of this: a name that is on a list is kept whatever Ember meant by it, so `M72` is kept as Medic 72 even if what was said was a man of 72, and the hundred block is a number Ember gave. And the form is only as good as Ember's hearing, which has not been measured: a row heard `clear` is `medium` confidence, and anything less is `low`. No list of San Francisco's streets or of its fire department's units is in the repository, and nobody has put one together yet: whoever turns real radio on supplies both and names the files. The city's open-data portal, [DataSF](https://datasf.org/opendata/), is the place to look first.

**Where the calls come from.** `BEACON_RECORDINGS_DIR` names a directory in the layout trunk-recorder writes, and `BEACON_RECORDINGS_SYSTEM` the one system in it whose calls are read: `<directory>/<system>/<year>/<month>/<day>/<talkgroup>-<start>_<freq>-call_<n>.wav`, with a `.json` file of the same name (an `.m4a` or `.mp3` is read where there is no `.wav`). `<start>` is the second the call began, in whole seconds or with its milliseconds after a dot (`1795809570.123`); both are read (trunk-recorder v5.0.0 writes the first and v5.2.1 the second, to name two versions and no boundary between them), and `<freq>` can end in a dot and a TDMA slot. Talkgroup numbers are a system's own, so a reader is of one system and reads no other system's directory. Of the JSON Beacon reads `talkgroup`, `start_time_ms` (or `start_time`), `call_length_ms` (or `call_length`, or `stop_time`), `emergency`, and `encrypted`; a call marked encrypted is passed over, and the list of radios that transmitted is never kept. **A call is found, ordered, and named by its files' name, and its time is its JSON's**, which can be later than the name's (the name is of the first transmission, and transmissions too short to keep are dropped after it is made) by up to an hour. **A call is ready when its audio plays about as long as its JSON says:** trunk-recorder writes the JSON before the audio, so a call whose audio is not there, cannot be decoded, or is shorter or longer than that (by more than half a second and a fiftieth of the length, and a second more when the JSON gives whole seconds) is not claimed, costs nothing, and is looked at again later. How close "about" has to be is a guess until a real recording has been read. The directory is opened once and held open: every file is reached from that descriptor, each directory from the one above it and none through a symbolic link, and a file is read only when it is a regular file, up to the size a call's file has. A year's or a month's directory outside the days a listing is of is not opened. **What a directory is decides what its rows are:** a directory with no mark is taken to be recordings of real radio, whose rows are `live` and are heard only by a live Ember; a directory with a file named `BEACON-GENERATED` at its top holds generated audio and no radio, and its rows are `mock` whoever hears them, so the live store refuses them and everything built on them is labeled a stand-in's. The mark is a regular file or is not there: anything else of that name, or a mark that cannot be looked at, is refused. The mark is looked at when the directory is opened, at every listing, and after every file is read and before its bytes are used, and a directory whose mark has changed is read no further until Beacon is started again. The mock scenario's calls are in no directory: they are tones on a shelf of the scenario's own. The layout and the fields are read from trunk-recorder's source (`call_concluder.cc`, v5.2.1), and no real recording has been through this code.

A call that is ready and worth hearing is paid for at most once. The poller hears only the talkgroups it is given, passes over a call that is encrypted, or shorter than a second or longer than two minutes by its JSON, reads the audio of at most 20 calls every 30 seconds, and makes its calls under a budget of its own (`BEACON_RECORDINGS_BUDGET_USD`, the spending scope `ingest:recordings`) inside the client's spending stop. Before Ember is asked about a call, the call is **claimed** in the evidence store under its system and file name, and a claimed call is never asked about again, by this process or another: not after a crash, a row that could not be stored, or an answer that was no form. The claim is given up only when the paid request is known not to have been sent. So a process that dies between Ember's answer and the row loses that call, and does not pay for it twice, and a run over a day of recordings that is stopped goes on from the calls it had not claimed.

When the spending stop or the budget refuses a call, or Ember fails on one, the poller asks nothing for ten minutes, counted from the failure and kept in the store, so a restart does not shorten it; the same after three answers in a row that were no form. If the Ember ledger is replaced while it runs, the poller stops until Beacon is started again.

The listing is read in passes, a page of 500 calls at a time, each page the calls next after a place in the order of the second a call began (by its files' name) and then of that name: calls that began in the same second do not hide one another, and within a second they are in the order of their names, not of their milliseconds. A poll reads at most 20 pages and reports itself as partial when it has not reached the end; the next poll goes on from that place. A day's directory with more than 200,000 entries fails the poll and is not read in part. A poller that follows a recorder begins each pass five minutes before the moment the last one ended, because a call's files turn up after the call: calls it has already taken are told apart by their names and are not read again, a call that was not ready (its JSON or its audio) is counted as unreadable, left unclaimed, and looked at again for as long as that reaches it, and one that becomes ready later than that, or grew older than fifteen minutes while the poller was held, is missed. A poller that is handed a backlog (`backlog=True`, which no setting of the server's turns on) makes passes over every call there is, the oldest second first. A poll's `unreadable` count is that poll's, and puts two things together that a pass keeps apart over all its polls (`RecordedRadio.last_pass`): calls that were **unready** (a JSON or audio that could not be used as it was), which nobody claimed and every later pass looks at again, and calls that were **unusable** (claimed, and Ember's answer came to nothing), which are never asked about again. So a clean last poll does not make a clean pass: a run over a backlog is finished when a pass has ended with nothing unready in any of its polls. A poll that a failure ended adds nothing to that count, and what it stored or claimed is in the store.

Shutting the server down admits nothing new: a conversion or a token count is called off unpaid, and a call the Ember client had already admitted is waited for, for up to about two minutes, so that its answer is stored. If that wait runs out, the server logs it and exits: the request can still be sent and paid for, it is settled in the Ember ledger, its row is lost, and the call is not asked about again.

### Notices

A notice is a document an authority published: an evacuation order, a shelter-in-place order, a road closure, an all-clear, a press release. The poller ([`server/beacon/ingest/notices.py`](server/beacon/ingest/notices.py)) reads a feed that lists them, downloads each PDF it has not read, and has Ember read it (`read_notice` in [`server/beacon/notice/`](server/beacon/notice)), which fills in a form: what kind of notice it is, the hazard, who issued it, when, the areas and streets it names, what it tells the public to do, and a short summary.

- **What is kept is Ember's reading of the notice, in words.** Unlike a radio call, a notice is about what an authority told the public, so the title, areas, instruction, and summary are stored as Ember gave them, on one line. They are a model's reading and not the notice: they can be wrong or leave something out, and how well Ember reads has not been measured. So the row's confidence is **`high`, not `official`**, it says a model read it (`model`), and it links the document (`url`), which is the authority speaking. Whoever shows the row says it is a reading and sends people to the document for what to do. The confidence is `low` when Ember says the document is no notice at all.
- **A text is kept whole or not at all.** An instruction cut short can say the opposite of the instruction ("residents may return" without "except to these addresses"). A text longer than Beacon keeps (1,500 characters for an instruction), or a list of more than twelve areas, is left out, and `data.incomplete` names the fields that are not all there.
- **Text is kept only of a notice that tells the public something:** an order, a warning, a closure, an advisory, an all-clear. A press release is where a victim is named and a home described, so of a press release, and of anything Ember does not take for a notice, the row keeps what it is, the hazard, and its times, and nothing a model could write a name or an address into: no text, no issuer, no streets.
- **An order names addresses**, which is what an order is, and they stay in its words (`data.areas`, `data.instruction`). A notice row has no `place` and no `point`: nothing in ingest turns its words into a place no finer than a block, or knows where on the map its streets are. Ember is told not to give a private person's name, age, or condition; that is an instruction to a model and not a guarantee, and the redaction pass of the next phase still reads a notice's text before it is shown.
- **Nothing in Beacon's process parses a PDF, and the document is not stored.** It is fetched only over HTTPS from the feed's own host or one named in `BEACON_NOTICES_HOSTS`, held in memory, checked for how it begins and for its size (5 MB), and sent to Ember as bytes. The Ember call is a sensitive one, so the ledger and trace hold its cost and none of the document or the answer. The process that reads notices marks itself as one of which no core dump is made, and where it cannot on a host with a core collector, live notices are refused, in the server and in `python -m beacon.ingest` alike.
- **A notice has to say when it was published, at a plain address.** The row's time is the feed's `date_published`, never the moment Beacon saw the item, so an item with no readable date is not read, and one dated later than now waits. The document's address may have no query: it names the document in the store and is shown as its source, so a link that is signed for a while is not read. Such items are counted as unreadable, once; when the poll that found them ended in an error, the next report counts them.
- **A document is paid for once**, by the same rules as a radio call ([`server/beacon/ingest/paid.py`](server/beacon/ingest/paid.py)): it is claimed before Ember is asked, under a name made of the feed item's id and the document's address, and never read again, so a document that is changed where it lies is not re-read; a revision has to be listed under a new item or address. A notice dated more than a day ago is not read, at most four are read in a poll, the newest first, under a budget of its own (`BEACON_NOTICES_BUDGET_USD`, the spending scope `ingest:notices`), and trouble with Ember holds the poller for ten minutes as it holds radio. A poller is not built on a client that can spend under no scope or under the other poller's.
- A document that cannot be had as a PDF just now (not there yet, a host that is down, a page in its place) is asked for again at a later poll, after the documents that have not been tried, and the poll is reported as `partial`. A host that answers `429` or asks for a wait ends the poll and is left alone for as long as it asked. A document longer than 5 MB is finished with unread.

**The feed is the part nobody has yet.** The poller reads a JSON Feed in which a notice is an item with a PDF among its `attachments`. Beacon knows of no San Francisco agency that publishes one, so `notices` can go live only with a feed an agency offers or one an operator writes for an agency's pages; reading an agency's HTML pages or an RSS feed is not built.

### Taps

`POST /api/taps` takes what the app sends when somebody presses "What's that?" ([`server/beacon/taps/`](server/beacon/taps)), and answers `201` with the tap's id and `investigating`, which says whether the tap was handed to the [investigator](#the-investigator). The answer is read at `GET /api/taps/<id>`.

```json
{
  "location": { "lat": 37.7763, "lon": -122.4244, "accuracy_m": 12 },
  "photo": "<a JPEG file, in base64>",
  "clip": "<a WAV file, in base64>"
}
```

`accuracy_m`, `photo`, and `clip` are optional, and any other field is refused.

**Every tap names the mode its sender was shown**, in a `Beacon-Mode` header: `mock` for the invented scenario, `live` for real sources (`GET /api/health` says which a server is in). A server in the other mode answers `409` and one that is told none answers `400`, **before it reads the body, holds a place for the tap, stores a row, or hands anything to the investigator**. That is what keeps an invented place from being stored and investigated, at a price, as a real one, and a clip meant for a real server from going to the scenario: an app, or a script written for the scenario, can outlive the mode it was started in. It is a refusal before processing and not a promise about the wire: the request's bytes can have reached the host by the time it is refused. The header says nothing of who sent the tap.

```sh
curl -X POST localhost:8000/api/taps -H 'Content-Type: application/json' -H 'Beacon-Mode: mock' \
  -d '{"location": {"lat": 37.776, "lon": -122.424}}'
```

A tap is the one thing in the evidence store that is about a person, so this is what is kept of it:

- **Where, to about a block.** The position is rounded to three decimal places of a degree (a box about 110 m by 90 m) before it is stored. The position the phone sent is not stored, logged, or repeated in an error.
- **When, by the server's clock**, and nothing the phone says about the time.
- **Who: nothing.** No address, browser, cookie, or account is read (the one header read for what it says is `Beacon-Mode`, which is `live` or `mock`), and two taps cannot be told to be from one person. The tap route is left out of uvicorn's access log, whose lines name the address a request came from, and out of FastAPI's own telemetry, whose spans would carry the address, the browser, and the query; what uvicorn writes at its `trace` level, a line with the address for every connection and every ASGI message, is silenced for every route (`PRIVATE_PATHS` and the filters in `server/beacon/main.py`). That covers uvicorn and FastAPI. A proxy in front of Beacon, or another server or tracer, keeps its own log, which is its operator's to turn off.
- **The photo and the clip, cleaned, for an hour.** A photo must be a JPEG of at most 4 MB. **What is kept is a new JPEG that Beacon drew from it**, no larger than 2048 pixels on a side: the file is cut down to the segments a decoder needs, decoded by ffmpeg in the same confinement radio audio is decoded in, and encoded again, so nothing of the file that was sent is copied into the file that is kept. Exif, the GPS position, the thumbnail, comments, a second picture, and bytes tucked where a decoder does not look are gone, and a file that does not decode is not a photo. The new file loses two more things: the note of which way up the picture is, and the colour profile, without the colours being converted, so a picture in a wider gamut than sRGB comes out a little flat. The app must send a picture it has already drawn to a canvas, which makes it upright and sRGB. A clip must be a WAV file of plain samples, at most 15 seconds and 3 MB, and is written out again as its samples alone; a browser's own recorder writes other formats, so the app has to record samples and write the WAV itself. The files are kept under `data/taps/<mock or live>/`, readable by Beacon's user only, deleted an hour after the tap by a sweep that runs every minute, and never handed out past the moment the tap's row says they are kept until, whatever the file's own age. The sweep and the 500 MB that all of them together may take cover both directories, so media kept while Beacon ran on the other store does not outstay its hour. **One server process takes taps in a data directory**: it holds a lock on `data/taps/.lock`, because the 500 MB and the sweep are counted by one process, and a second server pointed at the same directory does not start, and says why. Run one worker, and do not give a second server a data directory of its own: the Ember ledger and the claims on what was paid for are in the data directory, and are one server's.

**Taking a photo needs ffmpeg and bubblewrap, on Linux, on a host that hands no core dump to a collector** (`kernel.core_pattern` beginning with `|` or `@`; see [Radio](#radio)): ffmpeg holds the photo while it draws it, and nothing Beacon sets keeps a collector from being handed a crashed ffmpeg's memory. Where any of that is not so the server says so in its log when it starts, takes taps without photos, and refuses a tap that sends one with `503`: a photo is never kept as it was sent. The same `503`, with `Retry-After`, answers a photo the host had no memory, process, or thread to draw just then; it says nothing against the photo.

The row is of kind `tap`, from the source `app`, with the confidence `low`: it says only that somebody noticed something. Its origin is `live` in either store, because a person's tap is nobody's stand-in; the receipt's `mode` says which store it went to, and in `mock` whatever Beacon later answers the tap with is drawn from the invented scenario and has to be labeled so. `row.data` holds `accuracy_m`, the size of the photo and of the clip, and `media_kept_until`. Nothing in ingest looks at a photo or listens to a clip: that is the investigator's, with Ember, and only as evidence for the tap it came with.

A tap from outside San Francisco is refused with `422` and nothing of it is kept. So is anything that is not a tap, in a fixed sentence that repeats nothing that was sent. What a tap costs the server is bounded in the order the work is done:

- At most 8 taps are being received at once (`503`). A body is at most 10 MB (`413`) and has 20 seconds to arrive (`408`), after which its place is given back.
- A body with more JSON structure than a tap has is refused before it is parsed, and parsing happens off the event loop.
- The place is checked first, then the tap takes its place among the 120 a minute that are taken from everybody together (`429` with `Retry-After`), and only then is its photo or clip decoded. The limit is one for everybody because nothing tells one sender from another, so one sender can use up a minute. A tap whose photo turns out not to be one has used its place.

A tap is taken whole or not at all. A file is written and synced to the disk before its row is stored, and deleted if the row cannot be; when the row cannot be stored and the file cannot be deleted either, the answer is the same `503` and the log says so without naming the tap. If the server dies between the file and the row, the file is left with no row: no file is handed out without its row, and the sweep deletes one that has had none for five minutes. When what is stored cannot be counted, no more media is kept. A file that should be gone and cannot be deleted is reported in the log at every sweep, and is still handed to nobody.

The server process holds what a tap sent in memory, the position as the phone gave it included, while it takes it. Before it takes one it sets its core-dump limit to nothing and, on Linux, marks itself not dumpable (`PR_SET_DUMPABLE`), so the kernel makes no core of it for a file or for a collector, and no other process of the same user can read its memory ([`server/beacon/radio/audio.py`](server/beacon/radio/audio.py) says why both are needed). The HTTP server has read a request before any route can refuse it, so this is settled before a request is served: a server that cannot be marked, on a host that hands core dumps to a collector, **does not start**, and says what to change. One that cannot be marked where a core would be a file runs, on its limit alone, and says so in its log. Off Linux the limit is all there is. Swap is the operator's to turn off or encrypt.

Media outlives its hour only while nothing sweeps it. When the server is not running, or cannot start, `uv run python -m beacon.taps` (in `server/`) deletes what is over in both stores' directories, once, and exits; it reads no file and takes no tap, and leaves a running server's directory alone.

### Mock and live

**With `BEACON_LIVE_SOURCES` unset, which is the default, no real source is asked anything.** The pollers are the real ones, and where the network would be stands the mock scenario in [`server/beacon/scenario/`](server/beacon/scenario): an invented three-alarm fire on the 400 block of Hayes St, told as what NWS, adsb.lol, 511, and a feed of official notices would have answered minute by minute, and as the calls a recorder of the radio would have left. Twenty radio calls dispatch the first alarm, call a second and a third, order an evacuation, send a medic to a block nearby, and clear the units; a helicopter circles, 511 closes Hayes St and widens the closure, a shelter-in-place warning is issued, narrowed, and dropped, the closure stops being listed, and three notices are published: an evacuation order for the block, an all-clear that says it lifts the order for part of the block, and a press release. Nothing in it happened; its texts say "Invented for Beacon's mock scenario", and its rows have the origin `mock`. The radio calls are tones, and a stand-in for Ember (`beacon.scenario.stand_in_ember`) fills in what was "said" in each, so a radio row also has the model `fake`. The notices are one-page PDFs written by `beacon.scenario.pdf`, and another stand-in fills in the form for each (`beacon.scenario.notices`); the one for the press release holds a name and a house number, to show that a press release's row keeps neither. The story begins twenty minutes before a mock store is first opened and is played in real time for 105 minutes, after which nothing more is stored. A restart goes on from where the story had been played to, and a step in which a poller failed is played again ten seconds later, not passed over. To play it again, stop the server and delete `data/evidence/mock.sqlite3` with its `-wal` and `-shm` files.

There are two store files, `data/evidence/mock.sqlite3` and `data/evidence/live.sqlite3`, and **the live store refuses any row a stand-in had a part in**: one from the mock scenario, or one a fake Ember wrote. So a source that is not named in `BEACON_LIVE_SOURCES` does not run beside the live ones; it is off. Anything read from the mock store is a stand-in's, and has to be labeled as one wherever it is shown.

To poll a source for real, name it and set what it needs. No code changes:

```sh
BEACON_LIVE_SOURCES=nws,511 BEACON_511_API_KEY=... \
  uv run uvicorn beacon.main:app
```

`adsblol` needs nothing: `BEACON_LIVE_SOURCES=nws,adsblol` polls it with no key, about every three minutes. A key lets it ask more often only when Beacon is told what the key allows (`BEACON_ADSBLOL_API_KEY` with `BEACON_ADSBLOL_REQUESTS_PER_DAY`): what a key allows is not in the key, and one had without an account allows no more than no key does. How often adsb.lol is asked cannot be set any other way, and a restart does not make Beacon ask sooner: the moment before which it will not ask again is kept in the evidence store, so run one server for each data directory and each address. How often matters: an aircraft is said to circle once it has been seen on most sides of a circle, which takes six positions or more, so about a quarter of an hour at the least with no key, where positions half a minute apart, as the mock scenario's are, take three minutes. **OpenSky is not a source**: its terms require a written license for a running service, and Beacon has no poller for it.

`recordings` needs a directory of recorded calls and the right to use them, and it spends the Ember credit, once for each call:

```sh
BEACON_LIVE_SOURCES=nws,recordings BEACON_RECORDINGS_DIR=/path/to/trunk-recorder/captures \
  BEACON_RECORDINGS_SYSTEM=... BEACON_RECORDINGS_PERMITTED=1 \
  BEACON_RECORDINGS_TALKGROUPS=... BEACON_RECORDINGS_EMS_TALKGROUPS=... BEACON_RECORDINGS_BUDGET_USD=0.25 \
  BEACON_RADIO_STREETS_FILE=/path/to/streets.txt BEACON_RADIO_UNITS_FILE=/path/to/units.txt \
  REPLAY=0 MODEL_API_KEY=... EMBER_SPENT_BEFORE_USD=... \
  uv run uvicorn beacon.main:app
```

**`openmhz` is not a source.** OpenMHz was asked whether Beacon may use its API and said not to. Beacon has no client for it, and naming it in `BEACON_LIVE_SOURCES` is refused with that sentence whatever else is set. No poller sends a request to an address under `openmhz.com` or `broadcastify.com` either, whoever names the address: `beacon.ingest.http.fetch` refuses one before anything is sent, and a notices feed or document host that names one is refused when the server starts, before any client that can spend is made. The host is read as the client that sends the request reads it, so another spelling the client takes for the same name is refused too, and so is an address whose host that client cannot read. It goes by the name of the host: a host named by a number, or by another name for the same machine, is not known to be one.

`notices` needs a feed, and spends the Ember credit too, once for each document:

```sh
BEACON_LIVE_SOURCES=nws,notices BEACON_NOTICES_FEED_URL=https://.../feed.json \
  BEACON_NOTICES_BUDGET_USD=0.50 \
  REPLAY=0 MODEL_API_KEY=... EMBER_SPENT_BEFORE_USD=... \
  uv run uvicorn beacon.main:app
```

The talkgroup numbers are the recorder's for the San Francisco fire and EMS channels, which whoever makes the recording knows. Run [the audio-rate measurement](#measure-the-audio-token-rate) before the first real poll: what a call costs is still a guess.

The server runs the pollers on a thread of its own, so run one server process: two would ask every source twice as often. `GET /api/sources` says which mode the server is in and how each poller's last poll went, including whether it was `partial`: a 511 answer that ran past four pages, or whose pages did not say plainly where they stood, is stored as far as it was read, and events on the pages that were not read are missing until a later poll reads them. To poll without the server:

```sh
cd server
uv run python -m beacon.ingest            # poll once, print what the store holds
uv run python -m beacon.ingest --follow   # keep polling
```

A request to a source is given 60 seconds from the lookup of its name to the last byte of its reply, however slowly the source sends, and a reply that is cut short is refused whole. A source that asks for a wait gets it, counted from when it answered and up to a week: `Retry-After` as a number of seconds or as a date, which is what adsb.lol sends when a day's allowance is spent. The one thing a deadline cannot call off is the lookup of a source's name, which goes on until the system's resolver gives up; Beacon keeps at most two such lookups waiting however many requests time out. When the server shuts down, a request that is out is cancelled and a write that is waiting gives up, so nothing is asked or stored after shutdown; a poll is stored whole or not at all, and is made again at the next start.

The store files are SQLite in write-ahead mode, so each has a `-wal` and a `-shm` file beside it while it is in use, and the newest rows can be in the `-wal` file alone. Do not copy the files of a store that is in use: copies made one after another can each be from a different moment. To copy one while Beacon runs, let SQLite do it, `sqlite3 data/evidence/live.sqlite3 ".backup copy.sqlite3"`; otherwise stop every process that uses the store first. Stop them as well before deleting the mock store to play its story again, and delete its `-wal` and `-shm` files with it.

A poller's failure is logged as one fixed sentence, such as `511 answered HTTP 401.`, and never with the address that was asked, which for 511 holds the token, or with anything the source replied. The HTTP libraries' own request and header logs are switched off for the same reason, at every level.

## Incidents

The incident engine ([`server/beacon/incident/`](server/beacon/incident)) reads the evidence rows as **incidents**: the radio calls that are about one thing, and what the other sources said about the same place at the same time. It is plain code. No model is asked, the same rows give the same incidents, and **nothing it works out is stored**: an incident is derived from the evidence each time it is read, and kept in memory for a few seconds.

```sh
curl localhost:8000/api/incidents            # going on now, or ended in the last two hours
curl localhost:8000/api/incidents?all=true   # every incident of the last twelve hours
curl localhost:8000/api/incidents/<id>       # one, with its timeline
```

Both answers begin with `mode` (`mock` when the evidence is the invented scenario's), `as_of`, and `partial` (true when there was more evidence than the engine reads at once: an incident can then lack its oldest lines, count fewer taps than there were, or show an old alert as `unknown`). An answer is one reading of the store: its incidents, its `as_of`, and its `partial` belong together, and a row stored while it was being made is in none of it. An incident has an `id`, a `title` (`Fire at the 400 block of Hayes St`), a `category`, a `status`, `status_text` (the status as a sentence, said as what the radio said and by nobody in particular, such as `The radio said: crews at work.`; null for a medical response, of which no status is shown, and when the radio gave none; for `clearing` it says only that a clearance or a cancellation was reported, because a row does not keep which units a call released), whether Beacon's record of it is `open` (its radio has not cleared it and was heard from in the last 45 minutes, or an alert for its place is in force: **a closed record says nothing of what is happening at the place**, since the radio can only have gone quiet), `radio` (the least `confidence` among its radio calls and a source for each: what its title, status, place, units, alarm, and `opened_at` rest on, for a card to show with them), a `place` no finer than a block, a `point`, its `units`, its `alarm` level, how many `taps` came from near it (taps, not people: nothing tells one sender from another; `taps_more` says the count is a lower bound), its `signals`, each with its own `confidence` and `sources`, `stand_in`, and `crisis`, which is null until the [investigator](#the-investigator) has decided on crisis mode for it. One read by its id also has:

- **`timeline`**: one entry for each thing a source said, oldest first. Every entry has a `text` written by code from the row's own fields, a `confidence` (`official`, `high`, `medium`, `low`), and `sources`: the feed, a label for a person (which says "as Ember heard it" or "as Ember read it" only of a row an Ember wrote: a stand-in's row is labeled by its feed alone, in a kept story too), the evidence row's id, a link when the original is public, whether a stand-in produced it, and for 511 the credit its data agreement requires. `details` holds the fields the text was written from, for an app that draws the line its own way.
- **`official`**: the alerts and notices authorities issued for the place, each with how it stands: `in_force`, `replaced`, `cancelled`, `not_listed`, `ended`, `unknown` (the rows that could have ended it were not all read), and for a notice `published`, or `ended` once the time its own document gave has passed. An alert's `incomplete` names the texts that are left out because the stored text may have been cut.
- **`aircraft`**: the aircraft that circled or came low over it.
- **`conflicts`**: where the radio and an official source do not agree, each with a `text` that says the official source holds and why, a `confidence` that is the weakest row's it rests on, and the `official` and `radio` sources. Code finds two kinds, and only where the order of their times makes the two disagree: an all-clear was reported on the radio *after* an alert that is in force was issued or an order was published (`all_clear_on_radio`), and a notice that names a street of the incident, published *after* the radio's call, is about another hazard than the call's (`hazard`). An all-clear on the radio before the alert said nothing about the alert, and is no conflict. It is in the list too.
- **`story`**: the few points Ember chose to tell the incident by, in sentences code wrote, or null ([Stories](#stories)).

How calls are grouped ([`calls.py`](server/beacon/incident/calls.py)):

- A call that names a street joins the incident at that street and block, and never one somewhere else, whatever units they share. Two blocks of one street are two places; an intersection is one place whichever of its streets is named first, with or without a block; and a call that gives only the street goes to the incident on that street its units are on.
- A call that names only units, as most do, joins the incident those units are on. A unit is on one incident at a time: named on a second, it has left the first.
- **Medical calls are grouped only with medical calls**, even at a fire's block with a fire's engine.
- An incident that has not been heard from for 45 minutes takes no more calls. A new dispatch to a block whose incident was cleared is a new incident.
- A call nobody could make out, housekeeping traffic, and a call that names no unit and no street belong to no incident.

What is attached to an incident ([`build.py`](server/beacon/incident/build.py)): a 511 event created while it was going on, on a road its calls name or within 300 m; an NWS alert whose drawn area holds its point, holes left out (being near an area's middle is not being in it, and a city-wide alert is the city's, not the incident's), with a line of the timeline for each later message that updates or cancels it, which says only that and links the message, because the later message can be drawn for another area (a message that revises only such a later message is said to have revised that, and not an alert that applied here); a notice that names one of its streets, and a press release when exactly one incident of its hazard is in its time; the taps from within 400 m, counted; and aircraft that circled or came low. Once the radio has cleared an incident it takes no more closures, taps, or aircraft, which can be the next incident's; a notice still follows. A medical response gets none of these: it is its crews and its block.

**Where an incident is.** A radio call gives a place in words and no point. The engine takes the point from a list of blocks: the story's own in the mock scenario, and the file `BEACON_BLOCKS_FILE` names for real radio. Nobody has made that file for San Francisco yet. Without it an incident gets its point from a version of a 511 event that lists a road of its as closed, and has none otherwise. That point is approximate: the poller keeps the middle of the box around what 511 drew for the event, which need not lie on the road, and the radio need have named no block. A point from 511 comes with `point_source`, the row it is from with 511's credit, in the list and in the single incident: show the credit with the point.

**What is in force.** The evidence store keeps history, and the engine reads it as a state ([`inforce.py`](server/beacon/incident/inforce.py)): an alert a later message replaces or cancels is not in force, only the latest version of a 511 event can be, and something a source stopped listing is `not_listed`, which the timeline words as what Beacon saw and never as an all-clear. A notice is a document that was `published`, and the engine says no more of it: never that an order is in force, and never that an all-clear lifts one. A notice's row keeps the streets a document names and no blocks, so an order for the 400 block and an all-clear for the 1800 block of one street look alike, and an all-clear can leave part of an order standing in a sentence only the document has. The order and the all-clear are both listed, each with its link, and what the all-clear covers is read in the documents.

The engine's wording keeps the product's rules:

- A medical call is "Medical response", its units, and its block. Whatever else a row held is not read.
- What is said on the radio about an evacuation, sheltering, or an all-clear is written as radio traffic, with "That is radio traffic, not an official order." No line, signal, or conflict says who said it: a radio row keeps what was said and the units that were named, not the speaker, and a dispatcher relaying an all-clear leaves the same row as a crew giving one.
- An official alert's `instruction` is the authority's own words and is shown as its own. Beacon writes no instruction. A text as long as the poller keeps (8,000 characters for an instruction) may have been cut, and a cut instruction can lose its exception, so it is left out whole and the alert says `incomplete`.
- **A notice's words are shown only as a reading, and only when they pass the redaction pass.** A notice row is a model's reading of a document. A line of the timeline says that an authority published a notice of a type, that this is Beacon's reading, and where the document is (`source.url`), and shows none of its words. An entry of `official` with `reading: true` carries the reading's `issuer`, `headline`, `instruction`, `summary`, and `areas`, each only when the whole text passed ([Redaction](#redaction)); the fields that did not are named in `withheld` and left out whole. Show them labeled as Beacon's reading, beside the link, and never as the authority's words or as what to do. Nothing is read of a press release.
- Taps are counted and never listed: a tap's id is what its sender reads the answer with.

**Signals** are what code can say makes an incident more than an everyday call. Each has a `kind` (`alarm`, `evacuation_on_radio`, `many_units`, `official_notice`, `official_alert`, `closure`, `aircraft_circling`, `taps`); `official_notice` covers orders and warnings alike and says which in its text, so do not word it as an order. They are: an alarm level of two or more, an evacuation mentioned on the radio, eight or more units, an official order or warning, named as the type it is (a warning is never called an order; when an all-clear was published too the signal says so, without saying which came first, and cites every document), an official alert in force, a road closed in the version of a 511 event that is in force, when the road is one of the incident's or the closure is within 300 m of its point, a circling aircraft, three or more taps. Each carries the sources it rests on, with 511's credit and a notice's link, and a confidence that is its weakest source's, so a signal shown by itself still says where it is from. The engine lists them and decides nothing from them; whether they add up to crisis mode is the investigator's decision.

Limits: the engine reads the last twelve hours and at most 20,000 rows, the newest first; an incident's `id` is a digest of the row of its that was stored first, so it is this store's own (another store that took the same calls in another order can name it differently) and an incident that runs longer than twelve hours changes its id; at most 5,000 taps and 5,000 aircraft positions are read for one incident; two incidents on one block within 45 minutes are taken for one; and an aircraft is "circling" when it stayed three minutes and went most of the way round, whoever it belongs to.

### Redaction

One kind of text reaches a person from a model: Ember's reading of an authority's notice. The redaction pass ([`server/beacon/redact/`](server/beacon/redact)) reads it first (`reading`). The pass is an allowlist: a text passes only when it is made of the ordinary words in [`vocabulary.py`](server/beacon/redact/vocabulary.py), names somebody listed (the radio's streets and units, public bodies, and the public places in `BEACON_PLACES_FILE`), numbers, and plain punctuation. A word that is not on a list, which is what a person's name is, fails the whole text, and so does an ordinary word written with a capital in the middle of a sentence. An acronym of a public body passes in capitals only, a month only beside a number, and a day only in front of such a date. A notice's issuer is shown only when the whole of it is one listed public body, written plainly (`Names.public_body`). A name on an operator's list is listed whole or not at all: one that holds anything besides plain letters, digits, spaces, hyphens, apostrophes, and the full stop of an abbreviation is left out, and the log says how many were. **A text is shown whole or left out, never cut.** The vocabulary leaves out the words for who a person is and what happened to them (age, man, injured, hospital).

**Nothing a model writes in Beacon's own voice is shown at all.** A list of words cannot keep a sentence from telling a reader what to do ("Exit the building." is made of ordinary words), so the pass is not asked to. Where Ember has a part in what Beacon itself says, it chooses from closed lists and code writes the words ([Stories](#stories)). That is how "Beacon never says stay or go" is kept.

What the pass cannot do: it does not understand a text, a listed name passes whatever is meant by it, a name that is also an ordinary word passes at the start of a sentence, a month that is somebody's name passes beside a number, and a person can be described without a word the list lacks. It fails safe and often: a notice that names a street nobody listed is not shown, and the fix is the operator's list. On the live store with no lists, no reading that names a street passes.

### Stories

An incident that has gone on for an hour has dozens of lines. `merge_incident` ([`server/beacon/story/`](server/beacon/story)) has Ember pick the few points that tell it. It decides nothing, and **no word Ember writes is read, kept, or shown**:

- **Ember answers with points, not prose.** A point is a `kind` from a closed list (`status`, `alarm`, `units`, a detail a call gave such as `evacuation` or `knocked_down`, `closure`, `aircraft`, `taps`) and the numbers of the lines that show it. The form has no field for a sentence, and anything else in an answer is not read.
- **Code checks each point against the rows of the lines it cites.** An `evacuation` point is kept only when every call it cites holds that detail, an `alarm` point only when each gave the same alarm level, a `closure` point only for one closure line. A point that cites nothing, a line that is not there, or a line that does not show it is left out, and the story says how many were (`left_out`).
- **Code writes the sentence**, from the rows' own fields, as what was said or seen then: a story's sentence is read apart from its line, so it is in the past tense and carries its time. It names no speaker: a radio row keeps what was said and not who said it, so a request for police that a dispatcher relayed reads "Radio traffic reported a request for police." and never "Crews requested police." What was said about an evacuation, sheltering, or an all-clear reads "An evacuation was mentioned on the radio. That is radio traffic, not an official order." The version of a 511 event that is in force is told in the timeline's own line, as 511's words. A version that is no longer the one in force is told only as "511 listed a traffic event.", which is all its row shows: not that it was here, because every version of an event is among an incident's lines once one of them is about its place, and not what came after it, which is told by the row that shows it when a point cites that row. A row that records 511's list changing is told as what Beacon saw at that check ("When Beacon checked, 511 was no longer listing a traffic event it had listed. That is what Beacon saw then, not an official reopening."), never as how things stand now.
- **Code gives it its sources, its confidence, and its time**: the sources of the lines it cites, the least confidence among them, and when the newest of them is from (`at`).
- **Ember is given only the lines of radio, 511 events, aircraft, and taps**, and no alert or notice; there is no kind of point about one. What an authority said is shown by code (`official`).
- **A medical response has no story.**

So a story is a choice among true lines, and what can be wrong with it is the choice: a point that matters can be missing, and an older status can be picked over a newer one, which is why each sentence carries its time.

A story is kept in `data/story/mock.sqlite3` or `data/story/live.sqlite3`, under the incident's id and a digest of the lines it was made from, and holds only what code wrote. A story is shown in the words it was kept in, so the file carries a number for what its stories hold and say, and a change to a sentence code writes raises it. A stories file of an earlier number keeps its claims and none of its stories when it is opened: lines that were paid for are not paid for again, and nothing in the old shape or the old words is read. A file of a number this Beacon does not know, which a newer one wrote, and a file of the other mode are refused, and nothing of a refused file is written: the look and the change happen under one write lock, and the journal mode is set only for a file that was accepted. **Do not delete a live stories file or move it away to get past a refusal:** it is the only record of which lines were paid for, and without it the same lines are paid for again. Run a Beacon that knows the file. The call is `sensitive=True`, so the Ember ledger keeps its tokens and cost and none of its text. The server looks over the incidents every 15 seconds and has a story made for one that is open, is not medical, has at least three lines, and has lines no story was made from: once for the same lines, at most every two minutes for one incident, and Ember is asked about at most three incidents in a pass, whatever it answered ([`desk.py`](server/beacon/story/desk.py)). Reading an incident never asks Ember anything. `story.current` is false while the incident has lines its story has not read.

**In mock mode a stand-in chooses the points** ([`stand_in.py`](server/beacon/story/stand_in.py)), by rule from the lines, and a story says so: `model` is `fake` and `stand_in` is true. No real Ember has chosen any. On the live store stories are made only when `BEACON_STORY_BUDGET_USD` is set, by a live Ember that pays under the spending scope `story:merge`; a refusal or a failure holds the desk for ten minutes, as it holds a paying poller. Shutting the server down first closes everything that pays, the story desk and the paying pollers alike, before it waits for anything, then waits for an answer that is out. A refresh that reaches a closed desk claims nothing.

## The investigator

A tap says only that somebody noticed something. The investigator ([`server/beacon/investigate/`](server/beacon/investigate)) finds out what: Ember is told that a tap came in, chooses which tools to call, and after at most four rounds of calls answers with the incident the tap is about, or with "unconfirmed". `POST /api/taps` hands the tap in and does not wait; the answer is read with the tap's id.

```sh
curl localhost:8000/api/taps/<id>       # the answer: pending, an incident, or unconfirmed
curl localhost:8000/api/taps/<id>/run   # the run: each round, each tool call, what each cost
```

A tap's id is what its sender was given, and whoever has it reads the tap's answer. Nothing Beacon shows of an incident names a tap. Both routes are private as the tap route is (no access log line, no telemetry), answer `404` with a fixed sentence for an id Beacon does not have, and are kept for a day less an hour, after which a tap is one Beacon does not have.

**What Ember decides, and what it does not** ([`loop.py`](server/beacon/investigate/loop.py)):

- **Ember chooses where to look.** The tools ([`tools.py`](server/beacon/investigate/tools.py)) are plain code over one reading of the incident engine and the evidence store, **as the evidence stood when the tap came** (`Engine.at`), however long the tap waited for its turn: `nearby_incidents`, `get_radio` (the radio calls of the incidents `nearby_incidents` returned in this run, and of no other), `get_aircraft`, `get_official` (an incident's alerts, notices, and signals, and how many 511 events in force list a road as closed on a street of its or near it, which is the count the engine's own `closure` signal rests on), `nearby_taps`, and, for a tap that sent one, `listen_clip` and `look_photo`. **Every tool looks from where the tap is, and Ember is never told where that is, or when the tap came.** No tool takes a place; a radius and a number of minutes are picked from short lists. What a tool tells Ember is ids, counts, tags from closed lists, and rounded numbers: no street, no unit, no word an authority wrote. A medical response is an id, its category, and its distance, and no more: not whether it is going on, no radio call, and nothing official.
- **The clip and the photo are looked at once each**, by a call of their own that answers with tags from a list (`siren`, `smoke`, ...), and only the tags are kept. A photo adds evidence to a tap's investigation and is analyzed for nothing else.
- **Ember answers with a form, not prose**: an incident's id or "unconfirmed", the grounds for the match from a closed list (`near`, `going_on`, `heard_in_clip`, `seen_in_photo`, `aircraft_overhead`, `other_taps`), and whether the incident's signals add up to crisis mode, with the signals it rests that on. **No word Ember writes is read, kept, or shown.** With each tool call it says what it is thinking and why it calls, from closed lists too.
- **Code checks the answer.** The incident has to be one `nearby_incidents` returned in this run, so it has a known place within reach of the tap. Each ground is checked against the run's reading, and one that does not hold is dropped and counted. `going_on` holds when the incident was open when the tap came or had an update in the fifteen minutes before, and its sentence says that and not more; a clip's or a photo's sentence says that at least one of the things made out fits, not that all do. An answer that is not the whole form (a field missing or of the wrong shape, or "incident" with none named) is `no_answer`, not a match that failed. A sound or a sight is a ground only for an incident it fits: smoke for a fire and not for a medical response, a blocked road where the incident has a closure, a helicopter only where a rotorcraft was over the incident. `aircraft_overhead` needs **one** aircraft that circled or came low over the incident and was, in the fifteen minutes before the tap, within a kilometre of the tap: not one aircraft over each. A match stands when it is `near` (within 500 m), or when a ground that ties this tap to the incident holds (`heard_in_clip`, `seen_in_photo`, `aircraft_overhead`) together with one other ground. That an incident is going on and that other taps came are true whoever tapped, and are no match by themselves. **Anything less is "unconfirmed": thin evidence is not a guess.**
- **How far to trust a match is code's to say**: `medium` when the incident is within 250 m, going on, and both grounds hold, else `low`. A match is the investigator's reading of the evidence and is never `high` or `official`.
- **Every sentence is written by code when the answer is read** ([`card.py`](server/beacon/investigate/card.py)), from the run's ids, counts, and tags. None tells anybody what to do. The sentences call a conclusion "the investigator's", and who the investigator was is said in a sentence of its own (`investigator_text`): a model, whose reading can be wrong, or a stand-in that works by rule. A stand-in is never called a model.

**Crisis mode is the investigator's decision, on grounds code checks.** Every signal it cites has to be one the incident engine found for that incident (`alarm`, `evacuation_on_radio`, `official_notice`, `official_alert`, `closure`, `many_units`, `aircraft_circling`, `taps`), and a medical response is never in crisis mode. **The first decision that turned it on is the one kept**: a run that decided against it keeps nothing, and a later one turns nothing off. It is shown with the incident as `crisis` (in the list, the single incident, and a tap's answer), and is read whether or not this server investigates taps: `active` while the incident is open, `decided_at`, `text` ("... That is the investigator's decision, not an authority's. Beacon relays what authorities publish and tells nobody what to do."), `decided_by` (`model` or `stand_in`) with `decided_by_text`, `cited` (each signal the decision rested on **as it was then**: its `kind`, `confidence`, and `evidence_ids`, 511's `credit` for a `closure`, to be shown with it because the incident may have no closure signal left to carry one, and `now`, which is `same` when the incident's signal of that kind still rests on those rows, `changed` when it rests on others, and `gone` when it has none), `signals` (the signals of those kinds the incident has **now**, with their sources) with `signals_text`, which says that is what they are, `model`, `stand_in`, and `stand_in_text`. Crisis mode changes what the app shows. It is not an instruction, and an official order is shown as what its authority published, with its link.

**The answer** (`GET /api/taps/<id>`) has `mode`, `as_of`, and `partial` as the incident routes do, and:

- `status`: `pending` for as long as the tap waits for the investigator or its run is being made, which the desk says and no timer guesses (go on asking), `incident`, or `unconfirmed`; `reason` says why it is unconfirmed (`nothing_near`, `not_looked`, `not_sure`, `not_grounded`, `no_answer`, `cut_short`, `not_investigated`), and `text` says it in a sentence.
- `incident`: the incident as it is **now**, in the shape the list of incidents has, with its `crisis`. `incident_gone` is true when Beacon no longer has it under that id.
- `match`: `confidence`, a `text` that says the match is the investigator's reading, how many grounds were dropped, and the `grounds` that held, each with its `kind`, a sentence (`text`) written from what the run found **then** (the distance is the one the run measured, whatever the incident's place is now), its `basis` (the tool of the run whose answer shows it), and a `credit`: 511's, to be shown with the ground, when the distance was measured from a point 511 gave.
- `nearby`: the other incidents the investigator's tools found near the tap, which it did not take the tap to be about, with `nearby_text`, and `nearby_credit`: 511's credit when the place one of them was found near the tap by was a 511 closure's, as the tool had it then.
- `watching` and `since`: for half an hour after an unconfirmed tap, the incidents within a kilometre whose first radio call came after the tap. Code finds them by place and time, **nobody investigates again**, and `since_text` says so. `since_credit` is 511's credit when one of them is placed by a 511 closure.
- `investigated_by` (`model`, `stand_in`, or null when nobody did) with `investigator_text`, and `model` (`live`, or `fake` for a stand-in). `stand_in` is true when a stand-in investigated, or when anything the answer shows (the incident, `nearby`, `since`) or the run looked at is built from a stand-in's rows; `stand_in_text` says which of the two, or both, and is shown with the answer.
- `investigated_at`, `cost_usd`, and `ember_calls`. `cost_incomplete` is true, and `cost_text` says so, when a call to Ember ended in an error after it may have been sent, or nothing was kept of the run: the totals may then be incomplete. `cost_text` says which of the two, and does not say where the rest is, because Beacon does not know that there is one.

**The run** (`GET /api/taps/<id>/run`) is what the agent trace view is built from. `state` is `pending` (for as long as the desk has the tap), `finished`, `none` (no run was made and none is coming), or `lost` (one was begun, nothing was kept of it, and none is being made: the server was stopped under it). `evidence_as_of` is the moment of the evidence the run read, which is when the tap came. `rounds` holds, for each request that came back with tool calls, its accounting (`ember`: `source`, the four token counts, `cost_usd`, `latency_ms`) and its `calls`: the `tool`, `thinking` and `why` with sentences for them, the `lead` incident, the `args`, whether it ran (`ok`), `text` (what it asked), `returned` (ids, counts, tags) and `returned_text`, the `credits` its answer requires where it is shown (511's, for a count of closures and for an incident placed by one), and for the clip and the photo the accounting of the Ember call that looked. `final` is the request that answered, `outcome` what stood of the answer (with `crisis_cited`, the signals a decision rested on as they were, each closure with 511's `credit`, and `crisis_refused` when code refused the decision), `cut_short` why a run ended early (`budget`, `tool_failed`, or the kind of error Ember raised), and the totals are at the end, with `unaccounted_calls`, `cost_incomplete`, and `cost_text` as in the answer. `investigated_by`, `investigator_text`, `stand_in`, and `stand_in_text` are as in the answer.

**What is kept** ([`store.py`](server/beacon/investigate/store.py)): one row for each tap in `data/investigate/mock.sqlite3` or `live.sqlite3`, holding ids, counts, tags, times, and each Ember call's tokens, cost, latency, and ledger row. **It holds no sentence, nothing the tap sent, not where the tap came from, and nothing a source said**; every Ember call of a run is `sensitive=True`, so the ledger and the trace keep its accounting and none of its text. Runs and decisions are deleted after a day, by a sweep every minute, whether or not another tap comes. The file is opened by the same rules as the stories file (`beacon/files.py`): a file of another mode or of a shape this Beacon does not know is refused and left as it was, and **a live investigations file is never deleted or moved away to get past a refusal**, because it is the record of which taps were paid for. The file's shape is its `user_version`, now 2: a file an earlier shape wrote keeps its claims, so no tap is paid for twice, and loses its runs and decisions, which this Beacon cannot read.

**What it may cost** ([`desk.py`](server/beacon/investigate/desk.py)): a tap is claimed before Ember is asked anything and is investigated once; the claim is never given up. **One tap's calls cannot come to more than $0.01**: before each call, a tool's own included, the loop hands the Ember client what is left of the tap's cap (`limit_nanousd`), and the client refuses a call that could cost more (no cache hit, every output token used) before its paid request, so a run stops short of the cap, sometimes well short, and never over it (`cut_short` is `budget`, and its sentence says the next call could not fit). A call held to a limit sends its paid request once: a client with a pacer does not try it again after a 429, because the attempt that was refused keeps what was held back for it. A tap that is more than fifteen minutes old when its turn comes is passed over and never claimed, which also keeps a tap whose claim is no longer kept from being paid for again. On the live store taps are investigated only when `BEACON_INVESTIGATE_BUDGET_USD` is set, by a live Ember that pays under the spending scope `investigate:tap`; unset, a tap is taken and its answer says it was not investigated, and what was investigated before is still read. Taps wait in a queue of 32 for one of two threads, and a tap that finds the queue full is passed over, so a crowd of taps is not a crowd of paid calls. After Ember refuses or fails the desk passes taps over for ten minutes or for as long as Ember asked, across a restart, and a later failure never shortens that; a replaced ledger stops it for the life of the process. Shutting down closes the desk with everything else that pays, before anything is waited for, then waits for the runs that are out. Reading an answer or a run never asks Ember anything.

**In mock mode a stand-in investigates** ([`stand_in.py`](server/beacon/investigate/stand_in.py)), by rule: it asks what is near, takes the incident that is going on with the most signals as its lead, among those near enough to be matched by their place when there are any, checks it, and answers with the grounds its reading of the tools' answers gives, or with "unconfirmed" when that gives none; asked about a clip or a photo it answers `none`, because it hears and sees nothing. Its runs say so (`model` is `fake`, `investigated_by` is `stand_in`, `stand_in` is true), and code checks its answer as it checks Ember's. **No real Ember has investigated a tap**, and whether Ember accepts this request shape (function tools together with a JSON schema for the answer, and a last request that carries earlier tool calls and offers no tools) is unverified.

Known limits: crisis mode is decided only when a tap is investigated, so an incident nobody taps near is never in it; an official alert with no radio incident under it is not an incident, so a tap inside its area alone is "unconfirmed"; a tap is not investigated a second time when an incident begins after it, and a tap that came before the first radio call of what it was about is "unconfirmed" with that incident listed in `since`; a call that ends in an error after it may have been sent is counted (`unaccounted_calls`) and has no cost in the run, so its totals may be incomplete; and a decision is kept under the incident's id, which changes if the incident's first call is regrouped.

| The button | `#/` | **What's that?**, what can be added to a tap (five seconds of sound, a photo), and the taps this device sent. |
| A tap's answer | `#/tap/<id>` | "Looking into it" while the tap is pending; then the incident card, why the investigator matched the tap to it, and the incident's timeline; or "unconfirmed", in the server's sentence, with no incident shown as a guess. |
| The agent trace | `#/tap/<id>/trace` | Each round of the investigator's run: the tools it called and why, what each came back with, and each request's tokens, time, and cost. |
| An incident | `#/incident/<id>` | The card and timeline of an incident opened from another card. |
| The map of an incident | `#/incident/<id>/map` | What Beacon can place of that one incident, on a street map, each thing numbered and listed under the picture with its source. Opened from the incident's card; there is no map of the city. See [The map](#the-map). |
| Your places | `#/places` | The places a person saved on this device, each with the open incidents Beacon has within a kilometre of it, or the server's sentence that it has none. Opened from the button's page. See [Saved places](#saved-places). Notifications are turned on and off here: see [Notifications](#notifications). |

`GET /api/health` says which `mode` the server is in. **The button takes no tap until that is known**, and none while the latest asking failed, whatever the server said before (the one that comes back can be on other sources). **A tap that is still waiting** for the phone's place, the microphone, or a photo's bytes **when the app sees the mode change or stop being known is called off and sends nothing**; what was added to it stays chosen for the next one. The app sees a change only when it asks, every half minute, so what holds between two askings is the server's own check: **a tap names the mode that was on the screen when the button was pressed** (`Beacon-Mode`), and a server in the other mode refuses it before processing any of it (see [the tap route](#taps)). The app then shows the server's sentence and asks for the mode again at once. So, as far as the app and the server can make it so: nobody sends where they are, a clip, or a photo to the invented scenario without having been told that is what it is. In `mock` the app says so on every view before anybody taps, and offers two places in the invented scenario to send a tap from, for somebody who is not in San Francisco: one near the invented fire, which is answered with the fire and turns crisis mode on, and one across town, which is answered "unconfirmed".

**What a tap sends.** The phone's position, rounded in the app to three decimals of a degree (about a block) before it is sent, so nothing finer leaves the phone; the accuracy sent with it is never less than 70 m, which is how far rounding can move a position. A clip is five seconds of the microphone, recorded as samples and written as a WAV file by the app ([`lib/recorder.ts`](web/src/lib/recorder.ts), [`lib/wav.ts`](web/src/lib/wav.ts)), because the server takes no other format; it is recorded while the phone finds where it is, and the microphone is let go of when the recording ends or the tap fails. A photo is drawn to a canvas first ([`lib/photo.ts`](web/src/lib/photo.ts)), which makes it upright, no larger than 2048 pixels on a side, and a new JPEG: the camera's own file, with its Exif and its GPS position, never leaves the phone. While a chosen picture is being drawn the button takes no tap and no other picture, so a tap never goes without the photo its sender chose, or with an earlier choice. **A photo is only ever attached to a tap.** Nothing in the app sends one by itself or asks what is in it.

**A tap's id stays on the device.** The server lists taps for nobody, so the app keeps the ids of the taps it sent in the browser's local storage ([`lib/tapStore.ts`](web/src/lib/tapStore.ts)), for the 23 hours the server answers for one, and forgets one when the server says it no longer has it or the person removes it. An id that has run out is **deleted from storage**, not only left off the list: when the app is opened, at the moment it runs out while the app is open, when the page is looked at again, and when another tab of the app changes what is kept, which the browser's `storage` event tells this one (`sweepTaps`). What is shown and what is stored are kept apart: a tap is off the list from the moment it runs out, and the view is told then, whether or not storage let the id be deleted. When storage refuses the write, deleting it is tried again at the next of those moments, not on a timer. An app that is closed runs nothing, so an id that runs out then stays in the browser's storage until the app is next opened. The views are named in the URL's fragment (`#/tap/<id>`), which a browser sends to no server, so a tap's id is not in the address of any page the app's own server is asked for. Somebody who is given the address of a tap's answer can read it: that is what the id is. A tap's id is taken only by the tap's own views (`#/tap/<id>`): the incident's page and its map take only an incident's id (`inc-` and sixteen hex digits), so an id put after `#/incident/` by mistake is never sent in an incident route's path.

**The request for a tap's answer does name it** (`GET /api/taps/<id>`), so whatever stands between the app and Beacon's server has to keep that path out of what it writes down, as the server itself does (`PRIVATE_PATHS`). Vite's proxy, which the dev server and `vite preview` use, logs the path of a request whose upstream failed; [`vite.config.ts`](web/vite.config.ts) gives Vite a logger that leaves out whatever follows `/api/taps/` ([`lib/logging.ts`](web/src/lib/logging.ts)). It does not cover `DEBUG=vite:proxy`, which prints every proxied path: do not set it on a server other people use. **A reverse proxy or a host in front of a deployed Beacon must do the same**: turn off its access and error logging for `/api/taps` and everything under it, or have it leave the path out.

**Whose words are shown.** Every sentence about an incident, an official order, a match, or an investigation is the server's (`text`, `status_text`, `investigator_text`, `stand_in_text`, `nearby_text`, `since_text`, `cost_text`, a crisis's `text`, `decided_by_text`, and `signals_text`), shown as it is given. The app adds short labels for the server's closed lists ([`lib/labels.ts`](web/src/lib/labels.ts)) and the sentences that say whose words a text is:

- Every line has a confidence label (`Official source`, `High`, `Medium`, `Low confidence`), its feed, a link when the original is public, and **511's credit** wherever a line, a ground, a cited signal, a tool's answer, or a list of incidents near a tap (`nearby_credit`, `since_credit`) is from 511. **The notice adsb.lol's license asks for** is shown the same way wherever something rests on a position adsb.lol answered with: a line of the timeline, the circling-aircraft signal, a tap's ground that an aircraft was overhead or that a helicopter was made out in a clip or a photo (which fits an incident only by a rotorcraft recorded over it), the grounds as the trace lists them, the trace's count of aircraft and its list of an incident's signals, and a signal a crisis decision cited. Its three links go where their words say: adsb.lol, the license, and [what Beacon keeps of the data](docs/aircraft-data.md). An invented aircraft carries none of it.
- **An alert's instruction is shown as the authority's own words.** A notice is shown as **Beacon's reading of a document**, each field labeled "as read", with the document linked beside it every time, and with a line that says so when the redaction pass or Beacon's limits left part of it out. A notice's state is "Published" and never "in force".
- **Anything a stand-in had a part in is marked "Invented"**, with a dashed outline wherever it appears, and the server's own sentence about it is shown with the answer, the crisis decision, and the trace. The trace names who answered each request: "The stand-in", and "Muse Ember" only for a live call.
- **Crisis mode** is shown in the server's words, as the investigator's decision and no authority's, ahead of everything about the tap while it is on, followed by what authorities published. What the decision rested on is one press away, with each signal as it was then and as it is now.
- **An incident's card shows what its radio calls gave, with those calls as its source**: its title, the status in the server's sentence, its place, the units named, the alarm level, and when the first call came, under the least confidence among the calls (`radio`). What rests on another source, such as how many taps came or when the newest line is from, is in the timeline, each line with its own source. The card says whether **Beacon's record** of the incident is open or closed, and nothing about the place: a record also closes when the radio has only gone quiet.
- A medical response is its title, its crews, and its block, with their source. Its card shows no status, no time, and not whether its record is open, and its page is that card: no timeline, which would add the times of its calls.
- **An incident the server says it does not have is taken off the screen**, the last reading of it included: its "crisis mode is on" and "in force" would be standing with nobody checking them. A tap keeps the match that was made for it.

**Live updates.** What is on the screen is kept current by asking again, not by a push, which carries no content (see [Notifications](#notifications)) ([`lib/cadence.ts`](web/src/lib/cadence.ts)): a pending tap every second, an incident whose record is open every ten seconds, one whose record is closed every minute (a line or a notice can still follow), and an unconfirmed tap every fifteen seconds for the half hour the server lists what begins near it. A request that fails is tried again after five seconds, and the last answer stays on the screen with a line that says it may be out of date.

To see it: `amp orb services ensure` in an orb, or the two commands under [Run locally](#run-locally). The microphone, the camera, and the phone's position need `localhost` or HTTPS.

What the app has not been tried on: a push delivered to a real device (see [Notifications](#notifications)); a real phone's microphone, camera, and position (it was exercised in a desktop Chromium with a generated tone for a microphone and a generated picture), and an answer of a real Ember, of which there is none.

### The map

The map is secondary. It is **opened from an incident's card** (`Open the map of this incident`, shown only for an incident Beacon has a point for and never for a medical response), it shows **that incident and nothing else**, and no view maps the city or lists incidents on one.

`GET /api/incidents/{id}/map` answers with `mode`, `as_of`, `partial`, the `incident` as a card has it, and `features`: what Beacon can place, the place first. Each feature has a `kind`, a `text` written by code, `at`, a `confidence`, its `sources` (with 511's credit on a 511 row), and where it is.

| `kind` | What is drawn | Its words and its source |
| --- | --- | --- |
| `place` | The point Beacon has for the incident (`point`). | A sentence that says which point it is: the one Beacon's list of blocks has for the block named on the radio, under the radio calls and the least confidence among them; or **an approximate point Beacon took from a 511 event** that listed a street of the incident's as closed, under that 511 row with its credit. The second is the middle of what 511 drew for the event, which Beacon worked out: the sentence says that it need not lie on the road and that Beacon has no point of its own, and it does not say the radio named a block. Either way it marks no address. |
| `traffic_event` | A 511 event of the incident's, at the point its row has. | The timeline's own line for the **version in force**, in 511's headline, which is 511's report and keeps its `official` label. Where the mark stands is Beacon's working out, and `note` says so: the middle of what 511 drew for the event, which need not lie on the road. An earlier version, or one 511 no longer lists, is not drawn. |
| `aircraft` | The positions an aircraft of the timeline's was seen at (`path`, oldest first, the newest 240). | The timeline's line for it. Its `sources` are the rows that line rests on and **the row of every position that is drawn**, so each bend of the path has its row. `note` says when positions were left out. |
| `alert_area` | The area an authority drew for an alert that is **in force** for the place (`polygons`: each a list of closed rings, its outline first and then the holes in it). | The timeline's line for the alert, in the authority's words. An alert that is replaced, cancelled, past its time, no longer listed, or of unknown standing is not drawn, and neither is one issued for a whole zone. **An area is drawn whole or not at all.** One of more than 600 points is left out, and `note` says so: a thinned area could leave a street out. So is one with any ring Beacon cannot read (not closed, fewer than four positions, a position that is not one), a hole included: an area drawn without one of its holes shows a place as inside it that the alert leaves out. The alert stays in the list with its sentence, its source, and the note. **A place is in the area when it is inside the outline of some polygon and in none of that polygon's holes**, which is how the incident engine reads it, so the polygons are handed on apart and the app fills each with its own holes taken out. The rings are never read together by parity: a second polygon would then cut a hole in the first where they overlap. |

**Not drawn:** a tap, ever (its point is its sender's); a notice, which has no place; another incident. A medical response has no map: the route answers `404` with a fixed sentence. An incident with no point is answered with no features and `text`, the sentence that says why.

**The picture claims nothing by itself.** Every thing on it carries a number, and the list under it has, for each number, the server's sentence, its note, the confidence label, and the sources. **A thing that has a point is a dot at that point, and the dot is never moved.** Its number stands beside the dot, joined to it by a line, and it is the number that gives way: it stays whole inside the picture, and is put clear of the other numbers and off every dot, around its own point first and then wherever in the picture there is room. That is best effort only in a picture with no room left (more than about two hundred numbers), where one number stands on another. Things at one point (an incident and a 511 event on its block) share a dot and have a number each. **An area's number is about a point of its own outline that is in view**: it stands on the outline, or is joined to it by a line when it has to give way, and is never put where there is neither outline nor fill. **An aircraft's number is about the newest position it was seen at that is in view**, with its dot. When none is in view and the line between two positions still crosses the picture, the number is on that line, with no dot: a point between two sightings is no sighting. An area that holds the whole picture has no outline in view and so no number on it: the picture says, under it, which numbered area holds all of the view, which is the one sentence the app writes there, about the picture and not the incident. **The credit a source's terms ask for is in the picture's own frame**, in a strip along its lower edge that covers nothing that is drawn, whenever something of that source is drawn: for 511 an event or a place taken from one, and for adsb.lol an aircraft's path, with a street map under it or not. The tiles' credit is in the same strip. On the invented scenario the picture says "Invented scenario", whatever it is drawn on, and the words under a street map say that the streets are real and what is drawn on them is invented.

**The street map** is OpenStreetMap's standard tiles, loaded by the browser from `tile.openstreetmap.org`. They need no key, and [OSM's tile usage policy](https://operations.osmfoundation.org/policies/tiles/) allows this use on its terms, which [`lib/tiles.ts`](web/src/lib/tiles.ts) keeps: "© OpenStreetMap contributors" is in the map's frame, along its lower edge, linked to the licence; only the tiles in view are asked for (sixteen at most, at one of three zooms), none ahead of time and none for offline use; the browser's own cache and `Referer` are left as they are (the tile requests send the site's origin and never the page's address, so never a tap's id). The map data is under the Open Database License. The policy gives no guarantee of service and asks that the address be a setting, so a build can name other tiles:

| Build variable | What it does |
| --- | --- |
| `VITE_MAP_TILES` | The tiles' address, with `{z}`, `{x}`, and `{y}` (`https` only). `none` draws no street map: what Beacon places is then drawn on a plain grid. Unset, OpenStreetMap's. |
| `VITE_MAP_TILES_CREDIT`, `VITE_MAP_TILES_CREDIT_URL` | The words those tiles' terms require on the map, and their link. Another address without both draws no tiles: tiles are not shown without their credit. |

What the tile server learns is what any site a browser loads from learns: the address of the device, the site it came from, and which tiles around **the incident** were asked for. The app sends it nothing of a tap or a saved place, and a tile that does not arrive leaves a plain ground with everything Beacon places still drawn.

Known limits: the map cannot be dragged, only made wider or closer around the incident, so an aircraft's path or an alert's area can run off its edge; the service worker does not cache tiles, so the street map needs a connection; and a place from the list of blocks is as good as that list.

### Saved places

"Does this affect me?" is asked about a place a person names, such as home. **A saved place stays on the device**: its name and where it is are kept in the browser's local storage ([`lib/placeStore.ts`](web/src/lib/placeStore.ts)), at most five of them, rounded to about a block when they are saved. Beacon's server has no account to keep a place under and is given none: it keeps where a place is only for a device that turned [notifications](#notifications) on, without its name. To say what is near a place, the app asks the server each time the view is open, and every half minute while it stays open:

```sh
curl -X POST http://127.0.0.1:8000/api/places/check \
  -H 'Content-Type: application/json' -H 'Beacon-Mode: mock' \
  -d '{"places": [{"lat": 37.776, "lon": -122.424}]}'
```

**What is sent** is where each place is, rounded to three decimals of a degree in the app, and nothing else: never its name. **What the server keeps of a check is nothing**: no row, no file, and no log line (`/api/places` is one of `PRIVATE_PATHS`, as the tap route is). The places are in the body, not the address, and the body is read by the route itself and repeated in no error. Like a tap, the request names the mode its sender was shown (`Beacon-Mode`), and a server in the other mode refuses it unread (`409`; `400` for no header); the app then asks for the mode again at once. No place is sent before the mode is known. A request is one to five places inside San Francisco, in two kilobytes at most; anything else is refused with a fixed sentence. Only eight requests are worked on at once, from before a body is read until its answer is made (`Admission`); one more is answered `503` with its body unread, and nobody waits in a queue holding a place. A sender that goes away mid-request is answered `400` by `read_body`, so the server has no unhandled error to log.

| Field | What it holds |
| --- | --- |
| `mode`, `as_of`, `partial` | As on the incident routes: one reading of the store answers for every place. |
| `reach_m` | How far from a place an incident is listed: 1,000 m. |
| `caveat_text` | What a distance is and is not, shown with every answer: it is between the point Beacon has for an incident (its block's, or an approximate one taken from a 511 event that listed a closure) and the place as saved, it is rough, and **says nothing of whether the place is inside the area of an official order or alert**. |
| `places[]` | One entry for each place sent, in the order sent. The place is not repeated. |
| `places[].near[]` | The open incidents Beacon has within reach, nearest first: `incident` (the same summary as a card's), `distance_m` (rounded to 50 m), and `text`, the distance in a sentence. When the point Beacon has for the incident is one it took from a 511 event, `text` says the distance is measured from an approximate point Beacon took from that event, and `incident.point_source` is that row, with its confidence and 511's credit: the app shows both beside that distance, and beside no other. |
| `places[].text` | When nothing is listed, the sentence that says so and that it is **not an official all-clear**. It says what the reading lists, never that there is no incident: it is the same sentence when a medical response is at the place itself, and when the reading was partial. |

Not listed, and the sentence says so: a medical response, of which nothing is made; an incident whose record in Beacon is closed; and one Beacon has no point for. The answer is a distance and no more. Beacon does not work out whether a saved place is inside an evacuation zone or an alert's area: a notice's row keeps streets and no area, and the place is known to about a block. What an authority published is on the incident's own page, with its link.

**On the device.** A place outside the area Beacon covers is not saved (`covered` in [`lib/geo.ts`](web/src/lib/geo.ts), the server's own box, which a server test holds it to): sent with the others, it would have the whole request refused. A place can be removed whatever the server is doing, the time before its mode is known included, and a place removed then is never sent. Saving and removing are a reading and a writing of the whole list, so each is done under a lock the browser shares among the app's tabs (the Web Locks API, `beacon.places`), and reads the list only once its turn has come: a place one tab removed is not put back by another tab's save. A browser without that API changes nothing: the save or the removal fails without reading or writing the list, and the page says so. The API is there wherever the app can find where a phone is, on `localhost` and over HTTPS.

Known limits: the address a request comes from is seen by whatever carries it, as with any request, so a proxy in front of Beacon should keep `/api/places` out of its logs as it does `/api/taps`; an official alert with no radio incident under it is not listed, because it is not an incident; and the check itself asks nothing while the app is closed. What reaches a device then is a notification, for a device that asked for them: see [Notifications](#notifications), which is the one case where the server keeps where a saved place is.

### Notifications

A device can ask to be notified when crisis mode is turned on near a place it saved. **This is the one thing Beacon keeps that is tied to a device**, so it keeps as little as sends a notification, and says all of it before anyone turns notifications on ([`server/beacon/push/`](server/beacon/push)).

**What the server keeps** ([`store.py`](server/beacon/push/store.py), `data/push/mock.sqlite3` or `live.sqlite3`):

- **A subscription**: the address the browser's push service made for this device and this site; the saved places, at most five, each rounded to about a block, without its name, with when this server was first told of it (which can be long after the person saved it); and when the subscription was last renewed.
- **What was sent to it**: for each incident a push was tried for, the incident's id beside the address, when the latest try was claimed, how many tries there were, and what came of the latest. This is what keeps a device from being sent a push for one incident over and over, and it does tie a device's address to an incident for as long as it is kept: 48 hours at most.
- **A permit**, while a device is giving its address: a random number the server handed it, tied to no address and no place, for two minutes at most (see below).
- Nothing else: no key of the browser's, no address a request came from, no browser's name, and no log line about a request to `/api/push`.

**A subscription is deleted** when the server receives the request a device sends when its person turns notifications off (the device sends it again until the server answers), when the push service says the address is gone (`404`, `410`), and 30 days after its last successful renewal, which the app makes when it is opened with notifications on and when a place is saved or removed. What was sent to it goes with it. With no place saved, the app has the server delete it. **Deleting goes on whether or not the server sends anything**: a server started with `BEACON_PUSH=0`, whatever its contact is, or with no contact to name, still opens its mode's subscriptions file (and makes an empty one when there is none, so that it never answers that an address is deleted without having looked), deletes a subscription when its device asks and when its time is over, and it sweeps the other mode's file too, when the data directory has one. Each pass sweeps each file by itself before it reads an incident, so a file that is busy, or incidents that cannot be read, keep nothing that ran out in the other; a file that could not be swept is a warning in the log, and the next pass tries again. Only a file of the other mode that this Beacon cannot open (a newer one wrote it) is left, and the server's log says so. **A file in an earlier shape** (a place without its time, or an address taken without a permit; neither was ever on `main`) has its subscriptions and what was sent to them deleted when it is opened: a device gives its address again when its app is next opened.

**A deletion is final: a request that was already on its way puts nothing back.** A request to be notified can reach the server late, after its sender gave up on it, turned notifications off, and was answered that the address is deleted. So an address is kept only with a permit (`POST /api/push/permit`), which is good once and is used up in the write that keeps the address. The app notes the permit before it sends the request, and names the permits of the requests it has out when it asks for a deletion; the server takes them away in the write that deletes. Whichever of the two arrives first, the file ends without the address. The request for the next permit takes the earlier one away too, so an older list of places cannot follow a newer one. The other way round, a deletion that arrives late deletes an address that was given again since, and the server then keeps nothing of the device until its app next tells it. **This holds for a deletion the app asks for. It does not hold when the browser replaces an address while the app is closed**: the service worker asks the server to delete the old address and can name no permit, because it reads nothing the app keeps, so a request to be notified that was still on its way can put the old address and its places back after the worker was answered. The app has the server delete it when it is next opened; until then it is kept as any address is, until a push to it is refused as gone or 30 days after its last renewal.

**A push carries no content.** It is a POST with no body to the push service, signed with the server's key (VAPID), and it wakes a service worker of the app's, which shows a sentence the app was handed before it subscribed ([`web/public/push-sw.js`](web/public/push-sw.js)). So the push service, which is the browser maker's, is sent no incident, no place, and no text. It does learn that Beacon sent this device a message, and when. Because nothing is encrypted to the browser, none of its keys is needed.

**A push is sent only to a push service.** The address is whatever a stranger posts, and Beacon makes a request to it, so it is taken only when it is `https` on a host of Chrome's, Firefox's, Safari's, or Edge's push service (`fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.push.apple.com`, `*.notify.windows.com`), on the usual port, written with nothing that reads two ways ([`endpoint.py`](server/beacon/push/endpoint.py)). That checks where a push goes, not that the push service ever made the address. The request follows no redirect.

**When a push is sent** ([`desk.py`](server/beacon/push/desk.py)). Every 15 seconds code looks over one reading of the incidents, and asks no model. A device is due a push when all of these hold:

- the incident is open, is no medical response, and has a point that is its block's. **An incident whose only point Beacon took from a 511 event brings no push**: a notification says an incident is near a place and has no room for a credit, and a point of 511's is shown only with 511's credit, as the saved places' page shows it;
- the investigator's decision turned crisis mode on for it, and the incident still has a signal of a kind the decision cited;
- one of the device's places is within 1,000 m of the incident's point, as the saved-place check measures it, **and this server had been told of the place before the decision was made**. A place keeps that time for as long as the device goes on naming it under the same address, so adding a place brings no push about a decision already made (the page shows what is near it). **An address the browser replaced starts again**: its places count from when the server is given the new address, which is when the app is next opened, so a decision made before then brings no push.

**Sending is best effort: once for an incident as a rule, and neither certainly nor only once.** A send is claimed before it is made, in the same write that checks the device still names the place and that its subscription's time is not over (so a subscription that ran out is sent nothing even when the sweep that would have deleted it failed), and settled by the push service's status alone: the body of its reply is not waited for. A send the push service did not say it took (not reached, no answer in ten seconds, `429`, `5xx`) is tried again, three times in all and a minute apart at the least. So is a claim that was never settled because the server was stopped under it, once it is five minutes old. A push service that took a push and whose answer was lost is therefore asked again, and the device is notified twice; a notification shows nothing of which incident it is about, so a later one takes the earlier one's place and alerts again. A refusal that trying again does not mend (`400`, `403`) is not tried again. A pass sends at most 200 pushes and **has a budget of 30 seconds, which is not a hard end**: it runs from before anything is swept or read, and it is looked at before each subscription, before a send is claimed, and again after the claim, so no push service is waited for longer than the pass has left (half a second at the least for a send that was claimed). A step itself is not cut off: a write waits for the subscriptions file at most five seconds, and reading the incidents takes what it takes. A pass that stopped before it had looked at every subscription says so in its counts. What was sent before takes none of a pass's sends, so the devices kept last are reached. A pass is logged as counts and never with an address, a place, or an incident: as a warning when a push service refused a push, which is the operator's to look at, and otherwise at `INFO`, which a server whose logging is as it comes does not print.

**What a notification says** is the server's ([`notice.py`](server/beacon/push/notice.py)): that Beacon's investigator turned crisis mode on for an incident Beacon has within about a kilometre of a place the device gets notifications for, that this is the investigator's reading and no authority's, and that the distance is rough. It tells nobody what to do. Pressing it opens the saved places, which list what Beacon has near each place at that moment, with its sources. The incident the notification was about may not be among them: its record can have closed since. **On the invented scenario it says first that the scenario is invented and that a stand-in decided.**

**Each mode is apart, on the server and on the device.** The mock store and the live store sign with a key each (`data/push/mock.vapid.key`, `live.vapid.key`), and a subscription takes a push only from the key it was made for. In the browser each mode has a service worker registration of its own (`/push/mock/`, `/push/live/`), with its own subscription and its own words, and which words a worker shows is decided by its scope and by nothing that is kept: the invented scenario's worker reads only the invented scenario's words, and says "invented scenario" even when it has none. Turning notifications on is for the mode the app is showing. When the app finds the server in the other mode, it lets go of the subscription and the person chooses again.

**The key** is an ECDSA P-256 key Beacon makes itself the first time it is needed, kept in the push directory for the server's user only, and written whole or not at all: a key that could not be kept is not used. It is no outside service's key and needs no account. Keep `data/push/` across restarts: the subscriptions made for a key take a push from no other.

**The contact.** Every push names whom the push service may write to about this server (`BEACON_VAPID_SUBJECT`, a `mailto:` or `https://` address). RFC 8292 lets a server name nobody, and Mozilla's push service refuses one that does, so **a server that is given no contact sends no notifications**: `GET /api/push` says so, nobody can subscribe, and no key is made. `.amp/services.yaml` names this repository's page for the orb's development server.

| Route | What it does |
| --- | --- |
| `GET /api/push` | Whether this server sends notifications (`enabled`, and `text` when it does not), the `public_key` a browser subscribes with, `about_text` (everything that is kept and for how long, when a push is sent, and what the push service is and is not sent: shown before notifications are turned on), the `notice` (`title`, `text`) a device shows when a push arrives, `reach_m`, `max_places`, and `kept_days`. |
| `POST /api/push/permit` | A permit for one request to be notified: `{"revoke": [...]}`, the permits of the sender's earlier requests that were never answered, which are taken away. Needs the `Beacon-Mode` header. Answers with `mode`, `permit`, and `seconds` (120). `503` when 2,000 permits are out, and from a server that sends none. |
| `POST /api/push/subscribe` | Keeps or renews a subscription: `{"endpoint": "...", "places": [{"lat": ..., "lon": ...}], "permit": "..."}`, one to five places, which take the place of any the server had. Needs the `Beacon-Mode` header, as a tap does. Answers with `mode` and `kept_until`. `410` when the permit is used, withdrawn, or over, with nothing kept; `422` for an address that is no push service's and for places it cannot use, in a fixed sentence that repeats nothing; `503` when the file holds as many subscriptions as it takes (2,000), and from a server that sends none. |
| `POST /api/push/unsubscribe` | Deletes the subscription kept under `{"endpoint": "..."}` and what was sent to it, and takes away the permits in an optional `"permits": [...]`. Needs the `Beacon-Mode` header. **`204` means this mode's file does not hold the address**, whether or not it did, and is only ever said by a server that looked in the file. Any other answer means nothing was deleted: `409` from a server in the other mode, whose file is another one, and `503` from one that is busy, stopping, or has not the file open. |

**In the app** ([`lib/push.ts`](web/src/lib/push.ts), [`components/Notifications.tsx`](web/src/components/Notifications.tsx)) notifications are turned on and off on the saved places' page, under the server's `about_text`. Turning them on asks the browser's leave, registers the mode's service worker, keeps the server's words on the device, asks the server for a permit, notes the address and the permit on the device, and only then gives the server the address. **A press of On that is older than a press of Off never undoes it**: turning on takes note of the latest turning off when it is pressed, and turns nothing on when there is a later one by the time it writes. **They can be turned off whatever the server is doing**, unreachable or holding a request open included: turning off is one write on the device that waits for no server and for no telling under way, after which the address is one for its server to delete and the browser is asked to let go of its subscription. A telling that was under way gives the server nothing more, and when its request had already given the server the address, has the server delete it. A telling asks once more whether notifications are still wanted immediately before it sends where the places are, so a turning off in another tab that it has read sends nothing. **The app says an address was deleted only when the server of its mode answered `204`**; until then it says the server has not answered, keeps the address, and asks again every half minute while it is open, and when it is next opened. No address is dropped to make room: with ten unanswered, the server is given no new address until one is answered, and the page says so. A telling waits at most twenty seconds for the server and the browser together, and its requests are aborted then; a request that was cut off can still reach the server, and keeps nothing once its permit was taken away. Of that time the browser has five seconds in all to say what it holds, let go, and delete the kept words, so a browser that does not answer keeps neither the lock nor the request that has the server delete. **A browser that would not let go of its subscription, did not answer, or could not say what it holds is said to maybe hold one**, with what that means: a notification can be sent through it only while the server has the address, and one already sent can still arrive (a push is kept by the push service for up to an hour). **A server that sends none is asked to delete what an earlier one kept for this device** when the app is opened with notifications on: it takes no change of places, so its copy could otherwise keep a place that was removed; the address is given again, with the places as they are then, when the server sends again. The server is told again whenever a place is saved or removed, in any tab; each telling runs under the browser's lock, reads the places at the last moment before it sends them, and keeps no memory of an earlier telling, because another tab may have told the server otherwise. When the browser replaces an address while the app is closed, the mode's worker asks the server to delete the old one, and the new one is given when the app is next opened. `Show a preview of one` shows the kept words on the device, marked as a preview in its title and its text: no push is sent.

**What is mocked, and what was not tried.** The key, the signing, the subscriptions, and the sending pass are real, and on the mock store a push for the invented fire goes to a real push service for a device that subscribed. **No push has been delivered to a real device**: the orb's headless Chromium denies notifications and has no push service to subscribe with, so the server side was exercised against a stand-in for the push services, the app's side with the browser's permission and push manager replaced, and the service worker's handlers by running them against a worker's globals. No push service has checked a token Beacon signed: the tests check the signature themselves. On an iPhone or iPad, web push works only for an app added to the Home Screen.

## Scale run

The scale run puts one day of dispatch calls through the same code the server runs (the recorded-calls poller, `extract_transmission`, the incident engine, the investigator) and compares what Beacon made of the day with the fire department's own record of it. It is a command, not part of the server:

```sh
uv run --project server python scripts/scale_run.py --name first --day 2026-11-24
```

**What that command does, with no key: a stand-in run on generated calls.** It downloads DataSF's record of the day, makes lists of San Francisco's streets, blocks, and units from DataSF, generates a call for each dispatch, arrival, and clearing in the record (tones, in trunk-recorder's layout, in a directory marked `BEACON-GENERATED`), has a stand-in "hear" each by looking it up in the generator's script, groups the rows into incidents, matches them to DataSF's calls, replays taps against the day, and writes `data/scale/first/results.json`. It costs nothing and asks Muse Ember nothing.

**A number from that run is not a measurement of Beacon.** The calls say what the records say, a stand-in reads them back, and the result is scored against the same records. So the run shows that the pipeline keeps what it is given: that a call is heard once, grouped, placed, and matched. It does not show how well Ember hears radio, how soon the radio tells of a call, or what anything costs. The results begin with a sentence that says which kind of run they are (`basis_text`), every number carries a sentence that says what was counted and what the count does not show, and a stand-in's run reports **no cost, no time per investigation, and no lead time at all**: those are `null` with a sentence beginning "Not measured". Anything that shows a result shows those sentences with it.

There are three kinds of run, and a run is one kind for good (its directory keeps what it is, and the command refuses to go on with it as another):

| Kind | Command | What its numbers are |
| --- | --- | --- |
| Generated calls, heard by a stand-in | the command above (add `--voice speech` for synthesized speech in place of tones) | A check of the pipeline. No accuracy, no speed, no cost. |
| Generated speech, heard by Muse Ember | `--voice speech --paid` | The cost is a real cost, of clean synthetic speech. The calls were generated from the records they are scored against, and a match is a fit by rule between a record and an incident: it is no proof that Ember made out a call (a record whose call was never generated can fit an incident too), and it does not say that Beacon finds a real city's calls. Lead time is still not measured: each call is placed at DataSF's time. |
| Recorded radio, heard by Muse Ember | `--recordings DIR --system NAME --talkgroups LIST --paid`, with `BEACON_RECORDINGS_PERMITTED=1` | The one kind whose numbers are about Beacon on real radio. **It has never been run:** there is no key and no recording Beacon has the right to use. |

A tone is never sent to a paid Ember, and a recording is never handed to a stand-in, whose answer would be an invention about a real call.

**Once there is a key**, a paid run of generated speech is one command. It needs ffmpeg with the `flite` voice on the host (`ffmpeg -filters | grep flite`):

```sh
REPLAY=0 MODEL_API_KEY=... EMBER_SPENT_BEFORE_USD=... \
  uv run --project server python scripts/scale_run.py --name speech-1 --day 2026-11-24 --voice speech --paid
```

**Once there are recordings** that the operator made or has permission to use, in [the layout trunk-recorder writes](#radio), a run over them is:

```sh
REPLAY=0 MODEL_API_KEY=... EMBER_SPENT_BEFORE_USD=... BEACON_RECORDINGS_PERMITTED=1 \
  uv run --project server python scripts/scale_run.py --name radio-1 --day 2026-11-24 --paid \
  --recordings /path/to/trunk-recorder/captures --system sfd --talkgroups 1201,1203,1301 --ems-talkgroups 1301
```

`--talkgroups` names every channel to hear and `--ems-talkgroups` the ones among them that carry EMS only. Only the calls of that day are heard: those whose files' names say they began on San Francisco's day, by the city's clock, or in the two hours after its end, and the run is refused until those two hours are over, before anything of the day is fetched, because a pass made sooner would be taken for the whole day's. The recordings are read where they lie and nothing is written to their directory. Run [the audio rate measurement](#measure-the-audio-token-rate) before either paid run: a day is about 1,500 transmissions, and what one costs is still a guess.

**Spending.** A paid run pays under scopes of its own in the one Ember ledger, inside the spending stop. Hearing is paid under `scale:radio` for recordings and `scale:speech` for generated speech, so that the cost reported for one kind of audio is never mixed with the other's, and **the two together are held to $1.25**: a run's scope gets the budget less what the other scope already holds, read when the run starts from the ledger file the run is pinned to (below), and the client that hears has to have been made on that same file. A run whose hearing is closed makes no client to hear with and needs nothing left of that budget, since it can only pay for taps. **One invocation is made at a time under a data directory**, a stand-in's too: the command takes a lock there for as long as it runs and a second one is refused, so two paid runs cannot each read the other's scope before either has spent, and two of one name cannot write one run's files. Replayed taps are paid under `scale:taps`, at most **$0.50**. Both figures are the build plan's; `--radio-budget` and `--taps-budget` lower them and cannot raise them. A scope is counted over every invocation and every run directory, so a second paid run starts with what the first left, and the cost of hearing a run reports is its scope's: every paid run of that kind of audio, which the number's sentence says. Each replayed tap is also held to one tap's own cap, and a tap is not begun, and so not claimed, when `scale:taps` has less left than that cap. Both caps are checked before anything is fetched or heard. **A paid run goes on only in the Ember ledger file it began to pay in** (its directory keeps the file's generation, device, and inode): the caps are counted in the ledger, and in one that was begun again, or put back from an older copy, they would be counted from less than was spent. Every paying client is made before anything is heard, the taps' first, with which the file is pinned, so a ledger replaced part of the way stops the taps as it stops the hearing, and both are asked once more when everything is done, whether or not either had a request left to make. A run that finds its ledger replaced reports no cost of hearing, says to compare Meta's Usage page with the ledger, and is refused when the command is given again. **What it cannot tell is a ledger rolled back in place**, as a copy written over the same file is: the file is the same one and holds less, as [the spending stop](#the-spending-stop) cannot either.

**The same command, given again, goes on with the run, and nothing is paid for twice.** A call on radio audio is a sensitive Ember call, which is never recorded for replay, so the run keeps its own account of what was done: a call is claimed in the run's evidence store before Ember is asked and the claim is never given up once the paid request may have been sent, and a replayed tap is claimed in the run's investigations file the same way. A run that stops (at its cap, at the spending stop, on a failure, or because it was interrupted) exits with status 1 and says so; given again, it hears only the calls nobody claimed. A call that was claimed and has no row (Ember failed on it, or the process died meanwhile) is counted in the results and is not asked about again. After Ember refuses or fails, on a call or on a tap, the whole run leaves it alone for ten minutes, or as long as Ember asked when that is longer: the command given sooner asks nothing, for a call or for a tap, and while the hold is the replay's it leaves the run's results as they were. A result names no length for a hold, because it is read long after; the command says how long the hold has to run when it is given. Three paid answers in a row that are no form hold it the same way. The holds are kept in the run's own files and are [the pollers' own code](server/beacon/ingest/paid.py). Taps are replayed only when a pass over the calls has ended with none of them unready, because a tap investigated against half a day is claimed for good with the answer it got. **When the replay first begins, the hearing is closed for good:** a call that turns up among the run's calls after that is not heard in this run, so every tap of a run is answered against the same evidence, and the result says so. Calls that turn up later want a new run under another name. Exit status 0 is a complete run, which means nothing is left that the same command would still do: no call is waiting to be heard, the replay did not stop, and no planned tap is waiting. It does not mean every call has a row or every tap an answer: one that was claimed and came to nothing is counted in a number of its own and is not done again. Status 2 is a run that could not be made as asked.

**What is scored against.** [Fire Department and Emergency Medical Services Dispatched Calls for Service](https://data.sf.gov/d/nuek-vuh3), which the City and County of San Francisco publishes on DataSF under the Open Data Commons Public Domain Dedication and License and updates daily. Beacon asks only for the columns it keeps: the call's number and type, its times, its intersection and point, its units, and the number of alarms. **More than half the calls are medical, and the rules for EMS hold here as for radio:** a medical call is kept as "medical" with DataSF's number for the call, its crews, its intersection, and its times, and the columns that say how a patient was (the disposition, the priority, the call type group) are never requested. The streets and blocks come from [Streets - Active and Retired](https://data.sf.gov/d/3psu-pn9h), under the same license, and the unit roster from the dispatched calls of the thirty days before the scored day, so that it is not read off the answers. What is downloaded stays in the run's directory under `data/`, which Git ignores. A call in DataSF's answer that lacks a type or the time it was received or dispatched is counted and is in no other count, and so is a row that is not shaped as one or has no call number, as a row and not as a call, because several can be of one call. The counts and the share are of the calls Beacon could read. Generated medical calls are on a talkgroup of their own that the run hears as an EMS-only one, so a paid Ember that mishears generated speech cannot have a medical call kept as anything else.

**How a call is matched** is plain code ([`server/beacon/scale/score.py`](server/beacon/scale/score.py)), the same for every kind of run. The incidents are the incident engine's, read at moments from the run's first radio row to its last, whenever DataSF's last dispatch was; the engine looks back twelve hours, so readings that share a row, or are joined by readings between them that do, are counted as one incident, which is scored by its fullest reading. An incident is named by the first of its rows in view, so at a tap's moment it can have a name that none of those readings has: an answer's incident is taken for the one whose row gives it that name. An incident is a DataSF call's when both are medical or neither is, the incident opened within the call's time (from two minutes before DataSF says it was received to five after its last unit was available), and the incident names one of the call's units or lies within 300 m of DataSF's point. Each call takes one incident, closest in time first, and a call so paired is counted as **found**: a pair is a fit by that rule, and nothing checks that it is the right one. What is left is told apart as far as code can: a call with no incident of its own is **taken to be inside another's incident** when an incident that is another call's own, of the same medical-or-not kind, and names one of its units or lies within 300 m has a radio call in its time (Beacon groups a second call at one block with the first; nothing checks that this is what happened, and an incident that was only near by at the time is counted the same), any other has **no incident**, an incident that fits a call and was paired with none is counted as a **further incident** (that is what is left when Beacon opens a new one for a unit heard from after 45 quiet minutes, and an incident that merely fits is counted the same), and an incident that fits no call is counted as that. The rule cannot tell a call DataSF does not list from a wrong incident, two calls that share a unit and overlap can be swapped, and nothing checks what an incident says beyond its kind and its place.

**What the numbers are.** `results.json` holds, each with its sentence: the calls of DataSF's that Beacon could read, and those it could not; the transmissions heard, the calls claimed with no row, and the calls not ready or unusable; the incidents made; the calls found, their share, those taken to be inside another's incident, and those with no incident; further incidents and incidents no call fits; the calls found under another category; the distance from an incident's point to DataSF's, as a median and a 90th percentile; the time from DataSF's dispatch to the first call heard (recordings only: it is the radio's timing against DataSF's clock, not how long Beacon took); what hearing cost and the cost per 1,000 transmissions (paid runs only, read from the ledger); and for the replayed taps how many ran to an answer, how many were cut short or answered with no form (kept as "unconfirmed", and in no count of answers), how many were claimed with no run kept, how many of the answered ones placed at a call were answered with its incident, how many placed away from every call were answered "unconfirmed", the cost per answered investigation, and the 95th percentile of its time (paid runs only). The distance is between the two points of a pair: the incident's and DataSF's. A generated dispatch names the listed block nearest DataSF's point when one is within 250 m, an arrival or a clearing names no place, and an incident's point is of a block some call grouped into it was heard to name. So for a pair that is right and whose point is its own dispatch's, the distance is from DataSF's intersection to the middle of that block; nothing checks that a pair is either. It checks the list of blocks and the pairing and is no location error of Beacon's hearing.

**Replayed taps** are questions a script puts to the investigator: a place and a moment of the day, read against the run's evidence as it stood then. Up to 300 are planned from DataSF's calls by rule (`--taps`), spread evenly over the day's calls that are no medical ones, from the first dispatched to the last: one at each chosen call, three minutes after its dispatch, and one in five at a place and a moment such that, for every call DataSF lists within a kilometre of the rounded place the tap is put at, the moment is more than an hour before the call was received or more than an hour after the last time DataSF records for it (its dispatch, a unit on scene, or its last unit available). That control is what the record says and no more: a call can have gone on past the last time recorded for it. A tap is one question, put once: two controls of one moment can find the same place, and are then one tap, so a plan can hold fewer taps than were asked for. **No person tapped, and none is stored as a tap:** the run's evidence holds no tap row, so a replayed tap adds nothing to an incident's count of taps. A replayed tap is named by what it asks, so the command given again with another `--taps` investigates only the taps that are new; one that the new plan no longer holds stays in the run's file, paid for, and is not counted.

**The run from this repository, on Nov 27, 2026** (`--day 2026-11-24 --taps 40`, a stand-in on generated tones): 549 calls in DataSF's record, 359 of them medical; 1,525 generated calls, each heard once; 589 incidents; 468 calls found (85.2%); 48 taken to be inside another's incident and 33 with no incident; 30 calls that name no unit Beacon keeps an id for and so had no call generated, none of them counted as found and 5 of them among the 48, counted as inside another's incident only because an incident of another call's was near them at the time, which shows how loose that count is; 121 further incidents; none that fits no call; 66 calls whose generated dispatch names no block, because no listed block is within 250 m of DataSF's point; a median of 49.6 m and a 90th percentile of 90.4 m from DataSF's point; all 40 replayed taps answered, 31 of the 32 at a call with its incident and 8 of the 8 away from every call "unconfirmed". **Every one of those is a stand-in's number on generated calls: a check that the pipeline keeps what it is given, and nothing about Beacon on real radio.** The run took about a minute, most of it DataSF's downloads.

**The lists the run makes serve the server too.** `data/scale/<name>/lists/` holds `streets.txt`, `units.txt`, and `blocks.csv` in the forms `BEACON_RADIO_STREETS_FILE`, `BEACON_RADIO_UNITS_FILE`, and `BEACON_BLOCKS_FILE` take. Nobody has checked a block's place against the ground: it is the middle of the stretch of street its house numbers are on, by DataSF's centerlines.

## Ember client

Every model call goes through `EmberClient` in [`server/beacon/ember/`](server/beacon/ember), which calls `muse-ember-1.0` on the Meta Model API's Responses API through the OpenAI SDK. It is ported from the client of Forte, an earlier project by the same author for this hackathon.

```python
from beacon.ember import EmberClient

ember = EmberClient.from_env()
answer = ember.respond(
    task="extract_transmission",
    effort="low",
    max_output_tokens=1024,
    sensitive=True,  # the request or the answer can hold what Beacon must not store
    input="...",
)
```

| Mode | Selected by | What it does |
| --- | --- | --- |
| Replay-only | `REPLAY=1`, the default | Answers from recordings and never calls the API. A request with no recording fails. |
| Live | `REPLAY=0`, `MODEL_API_KEY`, and `EMBER_SPENT_BEFORE_USD` | Answers from a recording when there is one. Otherwise it calls the API and records the answer, so the same request costs $0 the next time. A [sensitive call](#what-is-stored) is never recorded and is paid for every time. |
| Fake | `EmberClient.fake(storage, responder)` | Answers from a function you supply, such as a `Script` of `fake_response(...)` objects. It needs no key and no recordings, and its calls are booked with the source `fake` at no spend. |

Around each call the client:

- **refuses a live call that could pass the spending stop** (see below), and one with more than **150,000** input tokens. It counts them with Meta's token-counting endpoint (`POST /v1/responses/input_tokens`), so the whole input, media included, is sent to Meta once to be counted before the request that generates an answer is sent or refused. The count is not billed;
- requires a `task` label, a reasoning effort, and `max_output_tokens` from 16 to 524,288 (Ember's largest output), because Ember reasons at `max` when no effort is sent and reasoning bills as output;
- requires `sensitive`, True or False, and keeps the content of a sensitive call out of everything it writes (see [What is stored](#what-is-stored));
- allows only function tools, because a hosted tool such as web search bills outside the token prices;
- takes media as inline bytes (a `data:` URL or base64, such as `input_audio`) or an uploaded `file_id`, and refuses a remote URL, because the bytes behind it can change after they were counted or recorded;
- refuses a call that could cost more than its caller allows for it (`limit_nanousd`, which the investigator uses to hold one tap to its cap): a live call whose worst case is over the limit is refused with `CallLimitError` before its paid request, and any client refuses a limit of zero or less. A limit only refuses, beside the spending stop and a scope's budget, and a call with one sends its paid request once, pacer or no pacer;
- writes one ledger row, from which the token trace is exported.

A failed call is not retried, with one exception: a client given a `Pacer` spaces its requests under a rate limit and tries a call again after a 429. A client given a `SpendScope` books its calls under the scope's name and holds them to a budget of their own under the stop, which is how one tap's investigation or the scale run gets a cap.

The client writes under `data/ember/` (or `$BEACON_DATA_DIR/ember/`), which Git ignores:

| File | What it holds |
| --- | --- |
| `ledger.sqlite3` | One `ember_calls` row per call: task, tokens, cached tokens, cost, latency, model, effort, scope, whether the call was `live`, `replay`, or `fake`, and its request and response, or for a sensitive call the sizes of them. Spend is the sum of the `live` rows. A row is named from outside by its response's `ledger_ref`: the file's generation, the row id, and a random token of the row's own. |
| `trace.jsonl` | The submission's token trace: every ledger row as one JSON line. It is written from the ledger on request, by the command below. |
| `replay/<request hash>.json` | Recorded responses, keyed by a SHA-256 of the request. A sensitive call has none. |

```sh
cd server
uv run python -m beacon.ember   # writes trace.jsonl and prints the live spend and the stop
```

### What is stored

Every call says whether it is `sensitive`: whether its request or its answer can hold what Beacon must not store, such as a patient's details, a name, or a house number in EMS radio traffic.

- **An ordinary call** (`sensitive=False`) is stored in full. The ledger, the trace, and the recordings hold the request's text and Ember's response as it wrote it, including the arguments of its tool calls, which can be free text. Audio, images, and files are replaced by a length and a digest in all three, so no radio audio is stored, but the words of a transcription or an extraction are.
- **A sensitive call** (`sensitive=True`) leaves its accounting and nothing of what was said. Its ledger row and trace line hold the task, scope, tokens, cost, latency, model, effort, the response's status, the SHA-256 of the whole request, and the size of each field in place of its content. Everything kept is a number, a value the client wrote itself, or one of a fixed set of words: no string the API or the caller chose is copied, so the response's id is not kept, and a failure is stored as `HTTP 400` without the API's error type. The answer is not recorded for replay and is never replayed, so the same call is paid for every time, and replay-only mode refuses it. The caller still gets the full answer, and what the caller stores from it is the caller's to strip. When a sensitive call fails, whether at the API, in a stand-in, or in the client's own check of the request, the caller gets one of the client's errors with a fixed text: the kind of failure, and the HTTP status as a number when there is one. It does not carry the API's message, the value that was refused, or another error chained under it, including one the caller was handling when it made the call, so its message and its printed traceback repeat nothing that was sent. A traceback captured with local variables still holds the request, as the caller's own frames do for any call: do not log locals.

**Any call whose input is EMS radio traffic, or anything else that can name a person or a home, must be made with `sensitive=True`.** The request's SHA-256 is still stored, and someone who holds the exact request can confirm it was made. The `task` label and a `SpendScope`'s label are stored as given for every call, so they must name the kind of work (`extract_transmission`, `tap:1842`) and never what it is about.

An API error is stored without its message: as its HTTP status and error type for an ordinary call, and as its HTTP status alone for a sensitive one. Read the trace before sharing it. The client uses POSIX file locks, so it runs on Linux and macOS.

### The spending stop

The plan's hard stop is $3 above what Meta's Usage page showed on Nov 26, 2026, the day the ledger began. The ledger counts only Beacon's own calls, so that is **$3.00 of live spend in the ledger** (`EMBER_STOP_USD`), whatever the page showed. The client reserves each call's most before sending it, in one transaction, so calls made at once cannot pass the stop together.

The ledger cannot see what the account had spent before it began, and the credit can: the stop and the earlier spend together may not pass $9.00 of the $10.00 credit. So `EMBER_SPENT_BEFORE_USD` has no default. It is the total for every model with no model filter, because every model is paid for from the one credit; the submission's screenshot, filtered to Muse Ember, can show less. **Nobody has read that total off the Usage page yet**, and until someone sets the variable, to `0` if that is what the page shows, every client that can spend is refused when it is built. Spend made outside Beacon after the ledger began is as invisible to it: add it to the variable. A client reads both settings once, when it is built, and keeps that stop, so **after changing either one, restart every process that makes paid calls**. A guess of $0.00 would let an account that had already spent $8.00 spend $3.00 more. Replay-only and fake clients need neither the key nor this setting.

The stop is the process environment's for every live client. `EmberClient.from_env`, `EmberClient.live`, and the constructor all read both settings from `os.environ`, none takes them as an argument, and `stop_nanousd` can lower the stop for one client and cannot raise it. So `EMBER_STOP_USD=0` stops all paid calls whichever way a client was built and whatever mapping it was built from.

**Every process that can spend must use the same ledger file, and the file must outlive the process.** The stop is counted in one ledger: a second ledger is a second $3.00. That is why a relative `BEACON_DATA_DIR` is refused, as is a live client handed a relative ledger path (either would name a different file from each working directory), and why a deployment must put the data directory on storage that survives a restart.

A live call that was sent and did not come back with a usable answer, such as a timeout or any error response, may still have been billed, so the ledger keeps it at the most it could have cost. Only a call that never left the machine is booked at $0. That makes the ledger an upper bound on Beacon's spend; compare it with Meta's [Usage page](https://dev.meta.ai/usage) every evening.

The ledger is the only record of what was spent. When its file is deleted or replaced under a client that is already built, that client logs calls that spend nothing in the new file and refuses every paid call with `LedgerReplacedError`, because the stop would otherwise be counted from zero. It checks before a call's first request, when it reserves the call, and again immediately before the request that costs money. A file that goes while that request is out cannot be caught in time: the call may have been billed and is in no ledger, the client raises `LedgerReplacedError` saying so instead of returning the answer, and **Meta's Usage page has to be compared with the ledger by hand before any more paid calls are made**. A client built after the file was deleted counts from zero: deleting the ledger forgets its spend, so do not delete it during the hackathon.

A running client tells its ledger file by the generation written in it and by which file is at the path, so it also refuses paid calls after an older copy is put back by renaming it over the ledger. **It cannot tell a ledger rolled back in place**, as a filesystem snapshot or a copy written over the same file does: the file is the same one and holds less than was spent. Restoring a ledger by any means needs every process that spends stopped first, and the ledger compared with the Usage page before they start again.

### Measure the audio token rate

**Not done yet: it needs a key.** The budget rests on a guess of 25 to 30 input tokens per second of audio. This command makes the plan's first ten real calls to check it, one per clip of a known length, and fits the rate from what each was billed:

```sh
REPLAY=0 MODEL_API_KEY=... EMBER_SPENT_BEFORE_USD=... \
  uv run --project server python scripts/measure_audio_rate.py
```

Its calls are booked under one scope in the ledger, `measure-audio-rate`, which is the same on every run. `--budget` (default $0.05) is therefore the most the measurement may spend **over all its runs** in one ledger, not new money for each run: once the scope holds that much, raise `--budget` to measure again.

The clips are generated tones, which tell the rate only if Ember bills audio by its length. Their answers are recorded, so a rerun with the same clips replays them at no cost; a clip with no recording is a new paid call, and without `REPLAY=0` the command stops and says so. `--clips DIR` sends a folder of WAV files instead: use recordings of the kind Beacon will send, and only ones we have the rights to send. Because those can be radio traffic, their calls are sensitive ones: nothing of them is recorded, and every run pays for them again, under the same budget. The command prints such clips as `clip-1`, `clip-2`, numbered in the order of their file names, and never prints a file's or the folder's name. A WAV file that is cut short of the length its header declares is refused.

## Rules Beacon is built under

- Every model call goes through Muse Ember on the Meta Model API, from one client that tracks tokens and spend and stops before the budget is passed.
- The answer to a tap is the product. The map is secondary.
- A photo only adds evidence to an incident. Beacon is not an image analyzer.
- EMS traffic is described as "medical response" with crews and a block-level location, never the patient.
- Beacon relays official orders and never tells anyone to stay or go on its own.
- Beacon publishes summaries, never raw radio audio, and uses only data it has the rights to use.
